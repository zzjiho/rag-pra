# Phase 0 — 개념 토대 & 환경

> RAG의 심장은 "의미로 검색하기"다. 그 심장을 뛰게 하는 부품이 **임베딩**과 **유사도**다.
> 이 장에서는 코드 한 줄 없이도 이해되도록 개념부터 잡고, 마지막에 직접 돌려보는
> 스크립트(`main.py`)로 눈으로 확인한다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "왜 키워드 검색으로는 부족하고 의미 검색이 필요한가?"
- "임베딩이 대체 뭔데 검색을 가능하게 하나?"
- "코사인 유사도, L2 거리, 내적 중 뭘 언제 쓰나?"
- "벡터 DB는 기존 DB랑 뭐가 다른가?"
- "내 노트북에서 임베딩 모델을 어떻게 돌리나?"

---

## 0. 큰 그림 먼저

### 그래서 RAG가 뭔데?

한 문장으로 먼저 못 박자.

> **RAG(Retrieval-Augmented Generation)** = 질문에 관련된 문서를 **① 검색해서(Retrieval)**,
> 그 문서를 **② LLM에게 함께 건네(Augmented)**, LLM이 그걸 참고해 **③ 답을 생성하는(Generation)** 기법이다.

왜 이런 게 필요한가? LLM(ChatGPT 같은 모델)은 아는 게 많지만
**우리 회사 문서·최신 정보·사내 규정**은 모른다. 그냥 물으면 그럴듯하게 **지어낸다.**
그래서 질문과 관련된 **진짜 문서를 찾아 LLM 앞에 놓아준 뒤** "이걸 근거로 답해"라고 시키는 것이다.

그 "**찾아주는**" 부분이 바로 RAG의 **R(검색)**이고, **Phase 0은 이 검색을 가능하게 하는 토대**—
즉 **임베딩과 유사도**—를 다룬다. 검색된 문서를 실제로 LLM에 물려 답을 만드는 ②③단계는
뒤 Phase에서 붙인다. 지금은 **"어떻게 뜻으로 문서를 찾아내는가"** 한 조각에 집중한다.

### 우리가 Phase 0에서 만들려는 조각

우리가 만들려는 건 결국 이런 기능이다.

> 사용자가 **"환불 언제 돼요?"** 라고 물으면,
> 수백 개 문서 중에서 **"결제 취소 후 3~5영업일 내 입금됩니다"** 같은
> **의미가 통하는** 문단을 찾아오는 것.

문제는 이 질문과 정답 문장에 **겹치는 단어가 거의 없다는 것**이다.
("환불" vs "결제 취소", "언제" vs "3~5영업일"). 단어로 맞춰 찾는 옛날 방식으론 이걸 못 잡는다.

그래서 필요한 게 **의미를 숫자로 바꾸는 기술 = 임베딩**이다.
Phase 0은 이 한 문장을 몸으로 이해하는 단계다.

## 1. 임베딩이란 무엇인가 — 그리고 키워드 검색은 왜 부족한가

### 왜 필요한가: 키워드 검색의 벽

전통적인 검색(예: 데이터베이스 `LIKE '%환불%'`, 검색엔진의 단어 매칭)은
**글자가 겹치는지**를 본다. 이게 무너지는 순간이 너무 많다.

| 사용자가 친 말 | 문서에 적힌 말 | 키워드 검색 |
| --- | --- | --- |
| 자동차 | 승용차, 차량 | ❌ 못 찾음 |
| 환불 | 결제 취소, 반품 | ❌ 못 찾음 |
| 노트북 안 켜져요 | 전원이 들어오지 않을 때 | ❌ 못 찾음 |

사람은 "같은 뜻이잖아"라고 바로 안다. 하지만 컴퓨터에게 글자는 그냥 글자라서,
**뜻이 같아도 철자가 다르면 남남**이다. 이게 키워드 검색의 근본적 한계다.

### 임베딩 = 의미에 좌표를 붙이는 일

임베딩(embedding)은 **문장을 숫자 목록(벡터)으로 바꾸는 것**이다.
핵심은 이 규칙이다.

> **뜻이 비슷한 문장은 서로 가까운 좌표를 갖는다.**

비유하자면, 모든 문장에 **GPS 좌표**를 하나씩 찍어주는 것이다.
- "강아지가 뛴다" → 어떤 위치
- "개가 달린다" → 바로 옆 위치 (뜻이 비슷하니까)
- "환율이 급등했다" → 저 멀리 다른 동네

이렇게 해두면 검색이 **"글자 맞추기"에서 "가까운 좌표 찾기"로** 바뀐다.
질문도 좌표로 바꾸고, 그 주변에 있는 문장들을 집어오면 된다.
단어가 안 겹쳐도 **뜻이 가까우면 좌표가 가깝기 때문에** 잡힌다.

> 💡 **한 줄 요약:** 임베딩은 "의미 → 숫자 좌표" 변환기다.
> 이 좌표계 위에서는 '가깝다 = 뜻이 비슷하다'가 성립한다.

## 2. 임베딩 모델은 어떻게 텍스트를 숫자로 바꾸나 (직관 버전)

수식으로 파고들면 끝이 없다. 여기선 **직관 3개**만 챙기자.

### (1) "같이 다니는 단어"로 뜻을 배운다

임베딩 모델은 인터넷의 방대한 문장을 읽으며 이런 걸 학습한다.
- '강아지' 근처엔 '산책', '사료', '짖다'가 자주 온다.
- '주식' 근처엔 '환율', '급등', '시장'이 자주 온다.

"어떤 단어들이 서로 붙어 다니는가"를 엄청나게 많이 보다 보면,
모델은 **비슷한 맥락에서 쓰이는 단어/문장을 비슷한 좌표에 놓게** 된다.
"강아지"와 "개"는 늘 비슷한 이웃 단어들과 등장하니 좌표도 가까워진다.

### (2) 문장 전체의 뜻으로 좌표가 정해진다

요즘 임베딩 모델은 단어를 하나씩 따로 보는 게 아니라 **문장 전체를 읽어** 좌표를 정한다.
그래서 **같은 글자가 들어가도 문장의 뜻이 다르면** 서로 다른 동네에 놓인다.
- "**배**가 고프다" (신체)
- "**배**를 타고 간다" (교통수단)

똑같은 글자 "배"가 들어갔지만, **문장 전체의 뜻**이 달라서 이 둘은 멀리 떨어진 좌표에 놓인다.
단어 하나가 아니라 **문장이 통째로 의미를 만든다**는 것이 핵심이다.

### (3) 결과물은 "고정 길이 숫자 목록"

문장이 길든 짧든, 임베딩 결과는 **항상 같은 길이의 숫자 목록**이다.
우리가 쓸 `bge-m3`는 **1024개의 숫자**를 뱉는다.
이 목록의 **칸 하나하나를 "차원(dimension)"**이라고 부른다. 숫자가 1024개면 곧 **1024차원**이다.

```
"안녕하세요" → [0.021, -0.14, 0.11, ...]  ← 숫자 1024개
"반갑습니다" → [0.019, -0.13, 0.10, ...]  ← 역시 1024개, 그리고 위와 비슷한 값
```

이 1024개 숫자를 **1024차원 공간의 한 점**이라고 보면 된다.
사람은 3차원까지밖에 상상 못 하지만, 수학적으로 1024차원의 "거리"와 "각도"는
똑같이 계산된다. 그 계산이 바로 다음 절의 유사도다.

> 💡 각 숫자(차원)가 "귀여움 정도", "긍정/부정" 같은 딱 떨어지는 뜻을 갖진 않는다.
> 사람이 해석할 수 없는, 모델이 알아서 잡은 의미 축들이다. 그냥 **"의미 좌표"**로 받아들이면 된다.

## 3. 유사도 측정 — 코사인 / L2 / 내적

문장을 좌표(벡터)로 바꿨으면, 이제 **"두 좌표가 얼마나 가까운가"**를 숫자로 재야 한다.
방법이 세 가지 있다. 먼저 감부터 잡자.

### 세 가지 감 잡기

두 벡터를 "원점에서 뻗어나간 화살표 두 개"라고 상상하자.

- **코사인 유사도 (cosine similarity)** — 두 화살표가 이루는 **각도**만 본다.
  같은 방향을 가리키면 1, 직각이면 0, 정반대면 -1. **화살표 길이는 무시**한다.
  → "방향(=주제)이 같은가?"

- **L2 거리 (유클리드 거리)** — 두 화살표 **끝점 사이의 직선 거리**.
  가까울수록 작다(0이 가장 가까움). → "실제로 얼마나 떨어져 있나?"

- **내적 (dot product)** — 방향이 얼마나 맞는지 × 길이. **각도와 크기를 함께** 반영한다.
  → "방향도 맞고 크기도 큰가?"

### 표로 정리

| 측정 | 무엇을 보나 | 값의 방향 | 값 범위 |
| --- | --- | --- | --- |
| **코사인 유사도** | 각도(방향) | **클수록** 비슷 | -1 ~ 1 |
| **L2 거리** | 직선 거리 | **작을수록** 비슷 | 0 ~ ∞ |
| **내적** | 방향 + 크기 | **클수록** 비슷 | -∞ ~ ∞ |

⚠️ 헷갈리기 쉬운 지점: **코사인·내적은 클수록 좋고, L2 거리는 작을수록 좋다.**
"유사도"는 높을수록, "거리"는 낮을수록 가깝다. 이 방향을 반대로 읽으면 검색 결과가 뒤집힌다.

### 왜 텍스트 검색은 코사인이 기본인가

가장 중요한 실무 감각이다. 이유는 크게 두 가지다.

**① 임베딩 모델이 대개 코사인을 기준으로 학습된다.**
"뜻이 비슷한 문장은 코사인 유사도가 높아지도록" 훈련되는 경우가 많다.
그래서 모델이 만든 좌표 공간은 **코사인으로 잴 때 의미가 가장 잘 정렬**된다.
말하자면 모델이 "나는 코사인으로 재라고 만들어졌다"고 전제하는 셈이다.

**② 코사인은 벡터의 크기(길이)에 영향을 받지 않는다 (크기 불변, scale-invariant).**
벡터마다 크기가 서로 다를 수 있는데,
- L2 거리·내적은 이 **크기 차이에 값이 휘둘릴 수 있다.**
- **코사인은 방향(각도)만 보므로** 크기가 달라도 흔들리지 않는다.

그래서 "뜻이 같은가?"만 알고 싶은 텍스트 의미 검색에선 **코사인이 기본값**이다.

> 📝 참고: "긴 문장일수록 벡터 크기가 크다"처럼 **크기 = 문장 길이**라고 딱 잘라 말하긴 어렵다
> (모델마다 다르다). 확실한 건 **"코사인은 크기가 어떻든 방향만 본다"**는 성질 하나다.
> 이거 하나만 붙잡아도 충분하다.

> 🔧 **실무 팁:** 많은 임베딩 모델은 벡터를 **정규화**(길이를 1로 맞춤)해서 내보낸다.
> 이렇게 길이가 모두 1이면 **코사인·내적·L2의 순위가 사실상 똑같아진다.**
> 그래서 실제 벡터 DB는 속도가 빠른 내적이나 L2를 내부적으로 쓰기도 한다.
> 하지만 "왜 가까운가"를 설명할 때의 **기준 개념은 항상 코사인**이라고 기억하면 된다.

## 4. 벡터 DB vs 기존 DB (개념만)

> 실제 벡터 DB(ChromaDB) 사용은 **Phase 1**에서 한다. 여기선 "왜 다른 도구가 필요한가"만 이해한다.

### 기존 DB가 잘하는 일: 정확일치와 범위

MySQL, PostgreSQL 같은 전통 DB는 이런 질문에 최적화돼 있다.
- "id가 42인 사용자" → **정확일치**
- "가격이 1만~2만 원 사이 상품" → **범위 질의**
- "이름이 '김'으로 시작하는 사람" → **접두사 매칭**

공통점: **답이 딱 떨어진다.** 조건에 맞으면 포함, 아니면 제외. 예/아니오의 세계다.

### 벡터 DB가 잘하는 일: 근접이웃 검색

의미 검색의 질문은 성격이 다르다.
- "이 질문과 **가장 뜻이 가까운 문서 5개**를 다오."

여기엔 "정확히 일치"라는 개념이 없다. **정답이 얼마나 가까운가의 문제**다.
이렇게 **"주어진 좌표에서 가장 가까운 k개"**를 찾는 걸
**근접이웃 검색(Nearest Neighbor, NN)** 이라고 한다. 벡터 DB는 바로 이걸 위해 만들어졌다.

| | 기존 DB | 벡터 DB |
| --- | --- | --- |
| 저장하는 것 | 행/열 값 | 임베딩 벡터 |
| 대표 질문 | "조건에 정확히 맞는 것" | "이것과 가장 가까운 k개" |
| 검색 방식 | 정확일치 · 범위 | 근접이웃(NN) |
| 결과 | 맞다/아니다 | 가까운 순 정렬 |

### "그냥 전부 계산하면 되잖아?" — 그리고 왜 별도 DB가 필요한가

문서가 10개면 질문 벡터와 10개를 전부 코사인 계산해서 정렬하면 된다.
(사실 `main.py`가 하는 게 딱 이거다 — **전수 비교, brute force**.)

문제는 문서가 **100만 개**가 되는 순간이다. 매 검색마다 100만 번 계산하면 너무 느리다.
그래서 벡터 DB는 **ANN(근사 근접이웃, Approximate NN)** 이라는 색인 기술로
"전부 안 보고도 가까운 것들을 빠르게 찾는" 지름길을 만든다.
(대표적으로 HNSW라는 그래프 색인 — **개념은 Phase 3, 파라미터 튜닝은 Phase 5**에서 자세히 다룬다.)

> 💡 정리하면: 벡터 DB = **"임베딩 벡터를 저장하고, 근접이웃을 빠르게 찾아주는 전용 창고."**
> Phase 0은 창고 없이 손으로 전수 비교를 해보며 원리를 체감하는 단계다.

## 5. Ollama와 로컬 임베딩 모델 (bge-m3)

### Ollama가 뭔가, 왜 로컬인가

**Ollama**는 큰 AI 모델(LLM, 임베딩 모델 등)을 **내 컴퓨터에서 손쉽게 돌리게** 해주는 도구다.
`ollama pull 모델이름` 한 줄로 모델을 받고, 백그라운드 서버가 떠서 요청을 받아준다.
**앱스토어에서 앱 하나를 받아 실행해두면, 백그라운드에서 계속 돌며 요청을 처리해주는 것**과 비슷하다.
(Docker에 익숙하다면: 이미지를 `pull` 받아 컨테이너를 띄우는 느낌과 같다.)

**왜 (유료 API 대신) 로컬인가?** 학습 단계에선 장점이 크다.
- **공짜 · 무제한** — 호출할 때마다 과금되지 않으니 마음껏 실험한다.
- **데이터가 밖으로 안 나감** — 문서를 외부 서버로 보내지 않는다.
- **인터넷 없이도** 돈다.

실무에선 품질·속도 때문에 상용 임베딩 API를 쓰기도 하지만,
**원리를 배우는 지금은 로컬이 정답**이다.

### bge-m3 소개

우리가 쓸 임베딩 모델이다. 알아둘 점만.
- **텍스트 임베딩 전용** 모델 (문장을 벡터로 바꾸는 게 유일한 임무).
- 출력은 **1024차원** 벡터.
- **다국어(multilingual) 모델** — 한국어를 포함해 100개 넘는 언어를 잘 다룬다. **한국어 RAG의 표준 선택지.**

> ⭐ **왜 하필 bge-m3? (실제로 겪은 실무 교훈):**
> 이 강의는 처음에 영어권에서 유명한 `nomic-embed-text`로 만들었다가 **갈아엎었다.**
> nomic은 **영어 중심 모델**이라, 한국어로 "환불은 언제 돼요?"를 검색하니
> 정답 문장을 **1위가 아니라 꼴찌권(5~6위)**으로 내놓았다. (영어로 같은 실험을 하면 완벽히 1위.)
> 모델만 **다국어인 bge-m3로 바꾸자 곧바로 정답이 1위**가 됐다. 코드는 한 줄도 안 바꾸고 모델만.
> → 앞에서 말한 **"성능은 실행기(Ollama)가 아니라 어떤 모델을 쓰느냐가 결정한다"**를
> 실제로 목격한 사례다. **한국어 데이터라면 반드시 다국어 임베딩 모델을 골라야 한다.**

> 🔧 **참고 (지금은 몰라도 됨):** 어떤 임베딩 모델은 문장 앞에
> `search_query:` / `search_document:` 같은 **접두어**를 붙여야 제 성능이 나온다(예: nomic).
> `bge-m3`는 **접두어가 필요 없어서** `main.py`도 문장을 그대로 임베딩한다.
> 모델마다 이런 사용 규약이 다르다는 것만 알아두면 된다 — 검색 품질 튜닝은 **Phase 2~3**에서 다룬다.

## 설치 & 실행

### 1) 파이썬 패키지 설치

가상환경을 만들어 그 안에 설치하는 걸 권장한다 (시스템 파이썬을 안 건드리게).

```bash
# 이 폴더(phase-0-foundations)에서 실행
python3 -m venv .venv
source .venv/bin/activate        # 매번 새 터미널을 열면 이 줄로 활성화

pip install -r requirements.txt  # ollama 클라이언트 + numpy 설치
```

### 2) Ollama 설치 (macOS 기준)

둘 중 편한 방법으로.

```bash
# 방법 A) Homebrew
brew install ollama
brew services start ollama   # 백그라운드 서버 자동 실행

# 방법 B) 공식 사이트에서 앱 다운로드
#   https://ollama.com/download  → 받은 앱 실행 (실행하면 서버가 자동으로 뜬다)
```

설치가 됐는지 확인:

```bash
ollama --version
```

### 3) 임베딩 모델 내려받기

```bash
ollama pull bge-m3
```

한 번만 받아두면 로컬에 저장된다. 잘 받았는지 확인:

```bash
ollama list   # 목록에 bge-m3 가 보이면 성공
```

### 4) 스크립트 실행

```bash
python main.py
```

## `main.py`가 보여주는 것

이 스크립트는 앞에서 배운 개념을 **네 단계로 눈앞에서 재현**한다.

1. **[1] 문장 → 벡터 변환**
   한 문장을 `bge-m3`로 임베딩해 **1024차원 벡터**가 나오는 걸 보여준다.
   (숫자 앞부분 몇 개를 미리보기로 출력 — "의미가 숫자가 됐다"를 체감)

2. **[2] 유사도 3종 비교**
   "비슷한 문장"과 "상관없는 문장"에 대해 **코사인 · L2 · 내적**을 각각 계산한다.
   → *비슷하면 코사인 ↑ / L2 ↓* 라는 방향 감각을 숫자로 확인.

   > ⚠️ 이 데모는 **정규화하지 않은 원시 벡터**를 전제로 한다(그래야 코사인·L2·내적이
   > 서로 다른 값으로 나와 셋을 비교할 수 있다). `main.py`가 쓰는 Ollama 호출
   > (`ollama.embeddings`)은 벡터를 정규화하지 않는다. 다만 **Ollama 버전/엔드포인트에 따라**
   > 벡터가 정규화되어 나올 수 있는데, 그러면 **내적이 코사인과 거의 같은 값**으로 보인다
   > (§3 실무 팁 참고). 이는 오류가 아니라 정규화의 효과다.
   > `main.py`는 [1]에서 벡터의 크기(norm)를 출력하니, 그 값이 1.0에 가까우면 "정규화된 것"이라고 읽으면 된다.

3. **[3] 의미 검색 데모**
   문장 6개를 두고 질문 하나를 던져, **코사인 유사도가 높은 순으로 정렬**한다.
   (문서 전체와 전수 비교 = brute force NN — **Phase 1에서 배울 벡터 DB(ChromaDB)의 원리**를 손으로 해보는 것)

4. **[4] 키워드 검색이었다면?**
   1위로 뽑힌 문장에는 **질문의 단어가 (단어 단위로) 그대로 등장하지 않음**을 보여준다.
   → 키워드 검색은 절대 못 하고 **의미 검색만 할 수 있는 일**을 눈으로 못박는다.
   (실제 1위 문장은 실행할 때 모델이 정한다. 먼저 `python main.py`를 돌려 순위를 직접 확인하자.)

> ⚙️ **동작 원리 한 줄:** `main.py`는 벡터 DB 없이, 모든 문서를 직접 임베딩해
> 질문과 하나씩 코사인 유사도를 계산하고 정렬한다. 이게 벡터 검색의 **가장 밑바닥 원리**다.
> Phase 1부터는 이 일을 ChromaDB에게 맡긴다.

## Phase 0 완료 체크리스트

- [ ] RAG가 무엇이고(검색 → 증강 → 생성), Phase 0이 그중 어느 조각(검색 토대)을 다루는지 안다.
- [ ] 키워드 검색이 왜 부족한지 예시로 설명할 수 있다.
- [ ] "임베딩 = 의미를 좌표로"를 내 말로 설명할 수 있다.
- [ ] 코사인/L2/내적의 차이와, 텍스트 검색에 왜 코사인이 기본인지 안다.
- [ ] 벡터 DB가 근접이웃(NN) 검색을 위한 도구임을 안다.
- [ ] `ollama pull` 로 모델을 받고 `python main.py` 를 성공적으로 돌렸다.

전부 체크됐다면 **Phase 1 (ChromaDB 기본기)** 로 넘어갈 준비가 된 것이다.
Phase 0에서 손으로 하던 "전수 비교 검색"을, Phase 1부터는 진짜 벡터 DB가 대신 해준다.
