# Phase 7 — 고급 RAG 패턴 (재랭킹 · Multi-Query · HyDE)

> Phase 6에서 R(검색)에 G(생성)를 붙여 **RAG 전체 루프**가 처음 돌았다. 질문 하나가 검색 → 증강 →
> 생성 → 인용을 거쳐 답 한 문장이 됐다. 그런데 그 루프의 답 품질은 **첫 단계인 검색이 관련 문서를
> 얼마나 잘 뽑느냐**에 그대로 매여 있다. 엉뚱한 청크를 검색하면 LLM은 엉뚱한 근거로 성실히 답한다.
>
> 지금까지 검색은 "질문을 벡터로 바꿔 가까운 문서를 뽑는" 단 하나의 방식이었다. 이 방식(벡터 검색,
> = bi-encoder)에는 구조적인 약점이 있다 — 정확한 토큰(`E-402`)을 놓치고, 짧고 애매한 질문에 약하며,
> 질문과 문서가 **같은 뜻을 다른 단어로** 쓰면 못 잇는다. 기본 RAG는 이 약점을 그대로 물려받는다.
>
> Phase 7은 검색 단계를 보강하는 세 가지 패턴이다. **Multi-Query**(질문을 여러 표현으로 바꿔 누락을
> 줄임), **HyDE**(질문 대신 가상 답변을 임베딩해 어휘 불일치를 메움), **재랭킹**(빠른 검색으로 넓게
> 뽑고 정확한 재랭커로 정밀 정렬). 재랭킹에서는 실제로 지표가 오른다 — 벡터 검색만으로 4위였던
> E-402가 재랭킹으로 1위로 올라온다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- 기본 RAG가 물려받는 벡터 검색의 세 약점(정확 토큰 · 짧고 애매한 질문 · 질문–문서 어휘 불일치)은 각각 무엇인가?
- Multi-Query는 무엇을 여러 개로 바꿔 검색하고, 그 결과를 어떻게 합치나?
- HyDE는 왜 "질문"이 아니라 "가상 답변"을 임베딩하나? 사실이 아닌 문단이 검색에 도움이 되는 이유는?
- 재랭킹의 2단계(넓게 뽑기 → 정밀 정렬)에서 각 단계가 무엇을 맡나?
- bi-encoder와 cross-encoder의 근본 차이는? 왜 하나는 빠르고 하나는 정확한가, 비용–정확도 트레이드오프는?
- 우리는 왜 전용 cross-encoder 대신 이미 있는 LLM으로 재랭킹했나(LLM-as-reranker), 실무에서는 무엇을 쓰나?
- 벡터 검색만으로 E-402가 4위였다가 재랭킹으로 1위가 된 이유는? (Phase 3의 하이브리드와 무엇이 같고 다른가)
- 코드로 안 다룬 Self-Query와 Conversational RAG는 각각 무슨 문제를 푸나?

## 1. 복습 — 왜 고급 패턴이 필요한가 (벡터 검색의 약점)

기본 RAG의 검색은 한 문장으로 요약된다. **질문을 임베딩 모델(bge-m3)로 벡터 하나로 바꾸고, 저장된
문서 벡터 중 코사인 거리가 가까운 순으로 top-k를 뽑는다.** 이 방식을 **bi-encoder** 방식이라 부른다 —
질문과 문서를 **따로따로** 벡터로 만들어(두 개의 인코딩), 그 두 벡터의 거리만 잰다는 뜻이다.

빠르고 싸다. 문서 벡터는 인제스트 때 미리 다 만들어 두고, 질문이 오면 질문만 한 번 임베딩해서
가까운 걸 찾으면 된다. 문서가 수백만 개여도 감당된다. 하지만 질문과 문서가 서로를 **직접 보지 못하고**
각자 벡터로 압축된 뒤 거리로만 만나기 때문에, 다음 세 경우에 약하다.

| 약점 | 무슨 일이 벌어지나 | 이 장의 대응 |
| --- | --- | --- |
| **정확한 토큰** | `E-402` 같은 코드·품번은 임베딩에 묻힌다. `E-401`·`E-403`·`E-404` 문서가 문장 구조까지 거의 똑같아, 벡터 거리로는 어느 게 진짜 `E-402`인지 잘 못 가른다. | 재랭킹 (§4) |
| **짧고 애매한 질문** | "돈 언제 돌려받아요" 처럼 핵심어가 적은 질문은 벡터가 흐릿해 관련 문서를 놓치기 쉽다. | Multi-Query (§2) |
| **질문–문서 어휘 불일치** | 질문은 "노트북 배터리 얼마나 가요", 문서는 "완충 시 약 10시간 지속". 뜻은 같아도 쓰는 단어가 달라 벡터가 멀어질 수 있다. | HyDE (§3) |

표의 예시는 벡터 검색이 **구조적으로 약한 질문 유형**을 보여주는 것이지, 이 10개짜리 코퍼스에서
반드시 실패한다는 뜻은 아니다. 실제로 "돈 언제 돌려받아요"는 §4 측정에서 벡터 검색만으로도 1위로 잘
잡힌다(코퍼스가 작고 환불 문서가 하나뿐이라서). 요점은 "이런 유형에서 벡터 검색이 흔들릴 수 있고, 각
패턴이 그 축을 보강한다"는 것이다.

세 패턴은 검색을 **더 정밀하게** 바꾸는 서로 다른 각도다. 정확 토큰 문제는 이미 Phase 3에서 한 번
만났다 — 그때는 키워드 하이브리드 검색으로 E-402를 살렸다. Phase 7의 재랭킹은 같은 문제를 다른
도구로 푼다(§4에서 둘의 관계를 짚는다). Multi-Query와 HyDE는 **질문 쪽**을 손보고, 재랭킹은 **뽑은
뒤 순서**를 손본다.

> **작은 코퍼스의 정직한 한계.** 이 장의 코퍼스는 문서 10개(`corpus.py`)다. Multi-Query·HyDE는
> "이런 원리로 검색을 보강한다"는 **메커니즘을 눈으로 보는 데모**다 — 문서가 10개뿐이라 지표가
> 극적으로 오르진 않는다. 그래서 이 둘은 지표 표 대신 **무엇이 생성되고 무엇이 후보로 합쳐지는지**를
> 화면에 펼쳐 보인다. 지표가 실제로 움직이는 건 재랭킹(§4)이다.

## 2. Multi-Query Retrieval — 한 질문을 여러 표현으로

**아이디어.** 사용자가 던진 질문 문장 하나에만 의존하면, 그 문장의 표현이 문서와 조금만 어긋나도
관련 문서를 놓친다. 그래서 **LLM에게 같은 질문을 서로 다른 표현으로 여러 개 바꿔 쓰게 한** 다음,
**각 변형으로 따로 검색**하고, 나온 결과를 **합친다(중복 제거)**. 여러 각도로 물어 하나라도 걸리게
하는 그물이다.

변형 질문을 만드는 부분(`advanced.multi_query`):

```python
def multi_query(question, n):
    prompt = (
        "다음 질문을 검색이 잘 되도록 서로 다른 표현으로 %d개 바꿔 써라.\n"
        "한 줄에 하나씩만 쓰고, 번호나 설명은 붙이지 마라.\n\n"
        "질문: %s"
    ) % (n, question)
    text = _chat(prompt)

    variants = []
    for line in text.split("\n"):
        line = line.strip()
        if not line:
            continue
        line = re.sub(r"^\s*\d+[.)]\s*", "", line)
        line = re.sub(r"^\s*[-*]\s*", "", line)
        line = line.strip()
        if line:
            variants.append(line)
    return variants
```

LLM 응답을 줄 단위로 쪼개고, 모델이 습관적으로 붙이는 `1.` · `2)` · `-` 같은 머리 기호를 정규식으로
떼어 낸 뒤, 빈 줄을 버리고 변형 질문 리스트를 만든다. "한 줄에 하나씩, 번호·설명 금지"라고 못박아도
LLM이 번호를 붙이는 경우가 있어, 받는 쪽에서 한 번 더 정리하는 방어 코드다.

각 변형으로 검색해 합치는 부분(`advanced.multi_query_search`):

```python
def multi_query_search(collection, question, n, k):
    variants = multi_query(question, n)

    merged_ids = []
    seen = set()
    for variant in variants:
        ids, docs = embed_search(collection, variant, k)
        for doc_id in ids:
            if doc_id in seen:
                continue
            seen.add(doc_id)
            merged_ids.append(doc_id)
    return merged_ids
```

변형마다 `embed_search`(= §1의 벡터 검색)로 top-k를 뽑고, `seen` 집합으로 이미 본 id를 걸러 가며
`merged_ids`에 처음 보는 id만 쌓는다. 결과는 **여러 표현이 각자 끌어온 후보의 합집합**이다. 하나의
표현으로만 검색했으면 놓쳤을 문서가, 다른 표현의 검색에서 걸려 후보 안으로 들어온다.

`main.py`의 `[1]` 블록이 이걸 보여 준다(질문 `"환불하고 싶은데 어떻게 해요"`, `N_VARIANTS=4`,
`TOP_K=3`). 화면에는 이런 형태로 찍힌다.

```
[1] Multi-Query Retrieval: 한 질문을 여러 표현으로 물어 검색 누락을 줄인다
  질문: 환불하고 싶은데 어떻게 해요
  생성된 변형 질문:
    - (LLM이 만든 변형 1)
    - (LLM이 만든 변형 2)
    - ...
  변형 질문들의 검색 결과를 합친 후보 id (중복 제거): [...]
```

변형 질문의 실제 문장은 실행할 때 LLM이 생성하므로 여기 고정해 적지 않는다 — **직접 실행해 무엇이
나오는지 보는 게 이 데모의 요점**이다. 확인할 것은 두 가지다. (1) 같은 뜻인데 표현이 다른 질문 여러
개가 나온다, (2) 그것들의 검색 결과가 하나로 합쳐진다. 코퍼스가 작아 후보 수 자체가 크게 늘진
않지만(§1의 한계), "여러 표현으로 물어 그물을 넓힌다"는 동작은 그대로 확인된다.

## 3. HyDE — 질문 대신 가상 답변을 임베딩

HyDE = **Hy**pothetical **D**ocument **E**mbeddings(가상 문서 임베딩). §1의 세 번째 약점,
**질문과 문서의 어휘 불일치**를 정면으로 노린다.

**문제.** "노트북 배터리 얼마나 가요"라는 질문과 "ZX-9 노트북은 완충 시 배터리가 약 10시간 지속됩니다"
라는 문서는 뜻이 같다. 하지만 질문은 짧고 구어체("얼마나 가요")고, 문서는 "완충 · 지속 · 약 10시간"
같은 단어를 쓴다. 임베딩 공간에서 둘이 생각만큼 안 가까울 수 있다. 질문은 원래 **답보다 어휘가 빈약**
하다.

**HyDE의 뒤집기.** 질문을 그대로 임베딩하지 말고, **LLM에게 "이 질문의 그럴듯한 답을 상상해서 한 문단
써라"** 라고 시킨다. 그 가상 답변은 실제 문서와 **비슷한 어휘·문체**를 쓰게 된다(답변끼리는 서로
닮으니까). 그 가상 답변을 임베딩해 검색하면, 질문보다 실제 문서에 더 가깝게 붙는다.

여기서 핵심은 **가상 답변이 사실일 필요가 없다**는 점이다. ZX-9 배터리가 실제로 몇 시간인지 LLM이
몰라도 된다. 심지어 "약 8시간"이라고 틀리게 지어내도 상관없다 — 우리가 쓰는 건 그 문단의 **내용의
진위**가 아니라 **어휘·형태**다. 검색은 "실제 문서 중 이 문단과 어휘가 비슷한 것"을 찾을 뿐이고, 답은
결국 검색해 온 **진짜 문서**에서 나온다(생성 단계는 Phase 6 그대로).

가상 답변을 만드는 부분(`advanced.hyde`):

```python
def hyde(question):
    prompt = (
        "다음 질문에 대한 그럴듯한 짧은 답변 문단을 상상해서 써라.\n"
        "사실 여부는 상관없다. 한 문단으로만 써라.\n\n"
        "질문: %s"
    ) % question
    return _chat(prompt).strip()
```

그 가상 답변으로 검색하는 부분(`advanced.hyde_search`)은 §1의 벡터 검색과 똑같다 — 다만 임베딩하는
텍스트가 질문이 아니라 **가상 답변 문단**이다.

```python
def hyde_search(collection, hypo_text, k):
    result = collection.query(query_texts=[hypo_text], n_results=k)
    ids = result["ids"][0]
    docs = result["documents"][0]
    return ids, docs
```

`main.py`의 `[2]` 블록(질문 `"노트북 배터리 얼마나 가요"`)이 **LLM이 상상한 가상 답변 문단**과 **그
문단으로 검색한 결과 id**를 나란히 찍는다. 실행하면 가상 답변이 "노트북 · 배터리 · 완충 · 시간" 같은,
실제 문서와 겹치는 단어들을 담고 나오는 걸 볼 수 있다. 이것도 어휘를 맞추는 **메커니즘 데모**다 —
가상 답변 문단은 실행할 때 생성되므로 고정해 적지 않는다.

## 4. 재랭킹 (2단계 검색) — 넓게 뽑고 정밀 정렬

### 2단계 검색이라는 발상

검색을 한 번에 정확하게 하려는 대신 **두 단계로 나눈다.**

1. **1단계 (넓게 뽑기, recall).** 빠르고 싼 bi-encoder(벡터 검색)로 후보를 넉넉하게 top-N 뽑는다.
   정답이 이 안에만 들어 있으면 된다 — 순서는 아직 안 따진다.
2. **2단계 (정밀 정렬, precision).** 느리지만 정확한 **재랭커(reranker)** 로 그 N개만 질문과 다시
   대조해 순위를 새로 매긴다.

전체 코퍼스를 정확한 방법으로 훑으면 너무 느리다. 그래서 싼 방법으로 후보를 좁혀 놓고, 비싼 방법은
그 좁은 후보에만 쓴다. "많이 걸러 낼 땐 싼 자로, 마지막 줄 세우기는 정밀한 자로"가 2단계 검색의 요지다.

### bi-encoder vs cross-encoder — 질문·문서를 언제 만나게 하느냐

두 재랭커 방식의 근본 차이는 **질문과 문서를 언제 만나게 하느냐**다.

| | **bi-encoder** (1단계, 벡터 검색) | **cross-encoder** (2단계, 재랭커) |
| --- | --- | --- |
| 입력 방식 | 질문과 문서를 **따로** 인코딩해 벡터 두 개를 만든다 | 질문과 문서를 **한 입력에 함께 넣는다** `[질문, 문서]` |
| 관련도 판정 | 두 벡터의 코사인 거리 | 모델이 둘을 같이 읽고 관련도 점수 하나를 출력 |
| 속도·비용 | 빠르다. 문서 벡터는 미리 계산해 두고 질문만 한 번 임베딩 | 느리다. **(질문, 문서) 쌍마다** 모델을 한 번씩 돌려야 함 |
| 정밀도 | 낮음. 둘이 벡터로 압축된 뒤에야 만나 미세한 관련도를 놓침 | 높음. 둘이 서로를 보며 채점해 `E-402` 같은 정확 일치도 잡음 |
| 확장성 | 수백만 문서 OK (미리 인덱싱) | 후보 몇~수십 개에만 쓸 수 있음 (전체엔 너무 느림) |

한 문장으로: **bi-encoder는 질문·문서를 따로 임베딩해 거리로 만나고, cross-encoder는 함께 넣어
채점한다.** 함께 넣으면 모델이 질문의 `E-402`와 문서의 `E-402`가 같은 토큰임을 직접 보므로 정확
일치에 강하다. 대신 미리 계산해 둘 수가 없어(질문마다 문서마다 새로 돌려야 하니) 전체 코퍼스엔 못
쓰고, **1단계가 좁혀 준 후보에만** 쓴다. 이게 비용–정확도 트레이드오프이고, 2단계 파이프라인이
존재하는 이유다.

### 우리 코드 — LLM을 재랭커로 쓴다 (LLM-as-reranker)

이 장에서는 전용 cross-encoder를 설치하지 않고, **이미 있는 채팅 LLM(qwen2.5:7b)에게 후보를 다시
정렬시킨다.** LLM은 질문과 후보 문서들을 **한 프롬프트에 함께** 받아 순서를 매기므로, cross-encoder와
같은 자리(질문·문서를 함께 보고 채점)에서 일한다 — 다만 전용 재랭킹 모델이 아니라 범용 LLM을
프롬프트로 시킨 것이다.

```python
def llm_rerank(question, cand_ids, cand_docs):
    lines = []
    for i in range(len(cand_docs)):
        lines.append("%d. %s" % (i + 1, cand_docs[i]))
    candidate_block = "\n".join(lines)

    prompt = (
        "아래 후보 문서들을 질문에 관련 있는 순서대로 다시 정렬해라.\n"
        "문서 번호만 콤마로 나열하고, 설명은 절대 하지 마라.\n\n"
        "질문: %s\n\n"
        "후보:\n%s"
    ) % (question, candidate_block)
    text = _chat(prompt)

    order = re.findall(r"\d+", text)

    ranked_ids = []
    used = set()
    for token in order:
        idx = int(token) - 1
        if idx < 0 or idx >= len(cand_ids):
            continue
        if idx in used:
            continue
        used.add(idx)
        ranked_ids.append(cand_ids[idx])

    for i in range(len(cand_ids)):
        if i not in used:
            ranked_ids.append(cand_ids[i])
    return ranked_ids
```

읽는 법:
- 후보에 `1.` `2.` … 번호를 붙여 프롬프트에 나열하고, "관련 있는 순서대로 번호만 콤마로 나열,
  설명 금지"라고 시킨다.
- LLM 응답에서 `re.findall(r"\d+")`로 숫자만 뽑아 순서(`order`)로 삼는다. 설명을 섞어 답해도 숫자만
  긁어 오니 견딜 수 있다.
- 그 순서대로 `cand_ids`를 재배열한다. `used`로 중복 번호를 거르고, 범위를 벗어난 번호는 건너뛴다.
- **마지막 for-loop이 안전장치다.** LLM이 응답에서 빠뜨린 후보(번호를 안 부른 후보)를 원래 순서대로
  뒤에 붙인다. 재랭킹이 후보를 **잃어버리지 않게** 보장한다 — 순서만 바꿀 뿐 목록에서 빠지는 문서는 없다.

지표 함수 `recall_at_1`(1위가 정답인가, 0/1)과 `mrr`(첫 정답의 역순위 `1/rank` 평균)은 Phase 4에서
쓰던 것과 같다. 재랭킹 전후를 같은 자로 재기 위해 여기 다시 둔다.

### 실측 — 벡터 검색만 vs LLM 재랭킹 후

`main.py`의 `[3]` 블록이 골든셋 6개(`corpus.GOLDEN`)마다 (a) 벡터 검색 top-5와 (b) LLM 재랭킹 후를
나란히 찍고, 두 방식의 지표를 비교한다(`RERANK_K=5`).

```
  === 지표 비교 (recall@1 / MRR) ===
    벡터 검색만  : recall@1=0.833  MRR=0.875
    LLM 재랭킹 후: recall@1=1.000  MRR=1.000
```

- **벡터 검색만(bi-encoder):** recall@1 = 5/6 = **0.833**, MRR = 5.25/6 = **0.875**. 6개 중 5개는
  정답이 이미 1위지만, **E-402 하나가 4위**로 밀린다(그래서 그 질문의 기여가 `1/4 = 0.25`).
- **LLM 재랭킹 후(cross-encoder 자리):** recall@1 = **1.000**, MRR = **1.000**. **E-402가 4위 → 1위**로
  교정됐다. 나머지 5개는 원래 1위였으니 그대로다.

개선은 전부 **E-402 한 질문**에서 나왔다. 왜 하필 E-402인가? `E-401`·`E-402`·`E-403`·`E-404` 문서는
"오류 코드 E-40X: … 하세요" 로 문장 구조가 거의 판박이라, bi-encoder는 벡터 거리만으로 이들을 잘 못
가른다 — 질문의 `E-402`라는 정확 토큰이 벡터에 충분히 안 실려 진짜 E-402 문서가 4위로 밀린다(§1의
첫 번째 약점). 재랭커는 질문과 후보를 **함께 읽어** `E-402`가 정확히 일치하는 문서를 집어 맨 위로
올린다.

> **Phase 3·4와의 연결.** 이 E-402는 Phase 3에서 키워드 하이브리드 검색으로, Phase 4에서 측정으로
> 이미 만난 케이스다(그때도 벡터 4위 → 하이브리드 1위). **같은 약점을 다른 도구로 푼다.** 하이브리드는
> "E-402"라는 글자가 문서에 있는지 키워드로 매칭해 살렸고, 재랭킹은 질문·문서를 함께 읽는 재랭커로
> 순위를 다시 매겨 살린다. 재랭킹이 더 일반적이다 — 정확 토큰뿐 아니라 키워드로는 안 잡히는 의미적
> 관련도까지 다시 따질 수 있다. 대신 (LLM/cross-encoder를 매 후보마다 돌리니) 더 비싸다.

### 정직한 스코프 — 전용 cross-encoder와의 거리

우리가 LLM으로 재랭킹한 건 **설치가 가볍기 때문**이다(이미 깔린 qwen2.5:7b 재사용). 실무에서 가장
흔한 선택은 재랭킹 전용으로 학습된 **cross-encoder 모델**(예: `BAAI/bge-reranker-v2-m3`, Cohere Rerank)이고,
**LLM 기반 재랭커**(RankGPT류 listwise, 상용 rerank API)도 함께 쓰인다 — 즉 우리가 쓴 접근 자체도 실무의
한 갈래다. 전용 cross-encoder는 관련도 점수를 더 안정적으로 내고 더 빠르지만, `sentence-transformers`와
`torch`를 함께 끌어와 설치가 무겁다. 그래서 이 데모에는 넣지 않고 개념과 코드만 남긴다.

실제로 전용 cross-encoder로 바꾸려면 이렇게 한다(선택).

```bash
pip install sentence-transformers   # torch 등을 함께 설치 — 용량이 크다
```

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")   # 첫 실행에 모델 다운로드

def cross_encoder_rerank(question, cand_ids, cand_docs):
    pairs = []
    for doc in cand_docs:
        pairs.append([question, doc])          # 질문과 문서를 '함께' 넣는다
    scores = reranker.predict(pairs)           # 쌍마다 관련도 점수 하나

    scored = []
    for i in range(len(cand_ids)):
        scored.append((scores[i], cand_ids[i]))
    scored.sort(reverse=True)                  # 점수 높은 순

    ranked_ids = []
    for score, doc_id in scored:
        ranked_ids.append(doc_id)
    return ranked_ids
```

`llm_rerank`와 자리는 같다(후보를 받아 재정렬한 id 리스트를 돌려줌). 다른 건 **누가 채점하느냐, 그리고
채점 방식이다.** 전용 cross-encoder는 `[질문, 문서]` 쌍마다 **따로** 점수를 내 그 점수로 정렬한다(pointwise).
우리 `llm_rerank`는 후보 **전체를 한 프롬프트에 놓고** 순서를 매긴다(listwise, RankGPT류). 둘 다 질문·문서를
함께 읽는다는 상위 역할은 같지만, 채점 메커니즘은 이렇게 갈린다. 파이프라인에서 `llm_rerank` 호출을 이
함수로 바꾸기만 하면 된다.

### Self-Query — 자연어를 메타데이터 필터로 자동 변환

Phase 3에서 메타데이터 필터(`where`)를 직접 손으로 걸었다("category가 error인 문서만"). **Self-Query**는
그 필터를 **LLM이 질문에서 자동으로 뽑아** 준다.

예: "6시간짜리 태블릿 배터리 궁금해요" 라는 질문을 LLM이 (1) 벡터 검색용 문장("태블릿 배터리 지속
시간")과 (2) 메타데이터 필터(`type = 태블릿`, `battery_hours = 6`)로 분해한다. 그다음 필터로 후보를
좁히고 그 안에서 벡터 검색을 한다. 사용자는 필터 문법을 몰라도 자연어로 묻고, 시스템이 "이 질문엔
이런 조건이 숨어 있다"를 알아서 구조화한다. Phase 3의 수동 필터에 LLM 변환기를 앞에 붙인 것이라고
보면 된다.

### Conversational RAG — 대화 이력으로 후속 질문 재작성

지금까지 질문은 전부 **독립적**이었다("교환하고 싶어요"). 하지만 실제 대화는 앞말에 기댄다.

```
사용자: 환불하면 배송비 내가 내요?
봇: 단순 변심이면 3000원을 부담하셔야 합니다.
사용자: 그건 언제까지 신청해야 돼요?     ← "그건"이 뭔지, 이 문장만으론 검색 불가
```

"그건 언제까지 신청해야 돼요?"를 그대로 임베딩하면 무엇에 대한 질문인지 검색기가 알 수 없다.
**Conversational RAG**는 검색 전에 LLM으로 **대화 이력을 반영한 독립 질문으로 재작성**한다 — "그건
언제까지 신청해야 돼요?" → "환불은 언제까지 신청해야 하나요?". 이렇게 self-contained(그 자체로 뜻이
통하는) 질문으로 바꾼 뒤 평소처럼 검색·생성한다. 핵심은 **검색기에 넘기기 전에 질문을 다시 쓰는**
단계 하나를 앞에 끼우는 것이다. §2의 Multi-Query가 "한 질문 → 여러 질문"이라면, 이건 "대화 맥락 +
후속 질문 → 완결된 한 질문"이다.

### Phase 7 완료 체크리스트

- [ ] 기본 RAG가 물려받는 벡터 검색의 세 약점(정확 토큰 · 짧고 애매한 질문 · 어휘 불일치)을 각각 예로 설명할 수 있다.
- [ ] Multi-Query가 "질문 여러 개로 변형 → 각자 검색 → 합집합(중복 제거)"임을 알고, `multi_query_search`가 id 합집합을 돌려주는 걸 짚을 수 있다.
- [ ] HyDE가 질문 대신 가상 답변을 임베딩하는 이유(질문–문서 어휘 불일치를 메움)와, 그 가상 답변이 사실이 아니어도 되는 이유를 말할 수 있다.
- [ ] 재랭킹의 2단계(bi-encoder로 넓게 top-N → 재랭커로 정밀 정렬)에서 각 단계가 recall/precision 중 무엇을 맡는지 안다.
- [ ] bi-encoder(따로 임베딩→거리)와 cross-encoder(함께 넣어 채점)의 차이와, 왜 하나는 빠르고 하나는 정확한지(비용–정확도 트레이드오프)를 설명할 수 있다.
- [ ] cross-encoder는 (질문,문서) 쌍마다 돌려야 해서 전체 코퍼스엔 못 쓰고 1단계가 좁힌 후보에만 쓴다는 걸 안다.
- [ ] `llm_rerank`가 응답에서 `\d+`로 순번을 뽑아 재배열하고, 빠진 후보를 원래 순서로 뒤에 붙여 누락을 막는 걸 안다.
- [ ] 우리가 전용 cross-encoder 대신 LLM으로 재랭킹한 이유(설치 무게)와, 실무에서 전용 cross-encoder(`bge-reranker-v2-m3` 등)와 LLM 재랭커(RankGPT류)가 함께 쓰인다는 걸 안다. 그리고 전용 모델은 pointwise, `llm_rerank`는 listwise 채점임을 구분할 수 있다.
- [ ] 벡터 검색만 recall@1=0.833/MRR=0.875 → 재랭킹 후 1.000/1.000의 계산(5/6, 5.25/6)과, 개선이 E-402 한 질문(4위→1위)에서 나왔음을 짚을 수 있다.
- [ ] E-402가 왜 bi-encoder에서 4위로 밀리는지(비슷한 오류코드 문서 + 정확 토큰 약점)와, 이게 Phase 3 하이브리드와 같은 약점을 다른 도구로 푸는 것임을 설명할 수 있다.
- [ ] Self-Query(자연어→메타 필터, Phase 3 필터에 LLM 변환기)와 Conversational RAG(대화 이력→후속 질문 재작성)가 각각 무슨 문제를 푸는지 말할 수 있다.
- [ ] `python main.py`를 돌려 `[1]`~`[3]`의 변형 질문·가상 답변·재랭킹 지표를 직접 확인했다.

전부 체크됐다면, 기본 RAG 루프의 **검색 단계를 세 각도로 보강**하는 법을 손에 넣은 것이다 — 질문을
넓히고(Multi-Query), 어휘를 맞추고(HyDE), 뽑은 뒤 다시 정밀 정렬한다(재랭킹). 남은 Phase 8은 이 검색·생성
루프를 **LangGraph 에이전트가 스스로 돌리게** 하는 이야기다 — 언제 검색할지, 재검색할지, 답을 낼지를
그래프가 판단한다.
