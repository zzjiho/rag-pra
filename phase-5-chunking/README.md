## 1. 왜 청킹을 "심화"하나 — 문단 단위의 한계

청킹(chunking)은 **긴 문서를 검색·저장 단위로 자르는 일**이다. 임베딩은 텍스트 한 덩어리를 벡터 하나로
바꾸므로, 무엇을 한 덩어리로 묶느냐가 곧 "검색의 최소 단위"를 정한다. 너무 크게 자르면 벡터 하나에
여러 주제가 뭉개져 정밀도가 떨어지고, 너무 잘게 자르면 문맥이 끊겨 답변에 쓸 재료가 부실해진다.

Phase 2에서는 **문단 단위**로 잘랐다. 잘 정리된 FAQ 문서라면 문단 하나가 사실 하나라서 이게 잘 먹힌다.
문제는 실무 문서가 그렇게 얌전하지 않다는 것이다.

- **글자 수로만 잘라야 할 때가 있다.** 문단 구분이 없는 긴 로그, 자막, OCR 결과처럼 구조가 없는
  텍스트가 온다. 이때 "그냥 N글자씩" 자르면 **문장·단어 중간에서 잘려** 뜻이 깨진 조각이 나온다.
- **한 문단에 여러 주제가 섞여 있을 때가 있다.** 문단으로 자르면 서로 다른 주제가 한 벡터에 뭉쳐
  검색이 뭉툭해진다. "의미가 바뀌는 자리"에서 끊고 싶어진다.
- **정밀 매칭과 문맥을 동시에 원할 때가 있다.** 딱 맞는 **한 문장**으로 정확히 찾되, 답변에는 그 문장이
  속한 **문단 전체**를 넘겨 LLM이 충분한 문맥을 보게 하고 싶다. 작게 찾고 크게 돌려주는 구조다.

이 세 가지 요구가 이 장의 네 전략에 그대로 대응한다.

| 요구 | 전략 | 기준 |
| --- | --- | --- |
| 구조가 없어 일단 크기로 자를 때(그리고 그 함정을 보기) | **fixed-size** | 글자 수 (경계 무시) |
| 경계를 지키며 크기를 제한하고 싶을 때 | **recursive** | 문장 경계 + 최대 크기 |
| 의미가 바뀌는 자리에서 끊고 싶을 때 | **semantic** | 인접 문장 임베딩 유사도 |
| 정밀 매칭 + 문맥을 동시에 원할 때 | **parent-child** | 문장(자식) + 문단(부모) |

실습 문서는 하나다(`corpus.py`의 `DOC`). 고객 정책 안내문으로, 문장 5개가 각각 다른 사실을 담는다 —
환불 기한, 반품 배송비, 교환·색상 변경, 멤버십 갱신, 고객센터 운영시간. 이 5개 문장을 네 방식으로
잘라 보면 방식별 성격이 눈에 보인다.

```
0  환불은 상품 수령 후 7일 이내에 신청할 수 있습니다.
1  단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.
2  교환은 하자가 있을 때만 무료로 가능하며 색상 변경은 1회만 허용됩니다.
3  멤버십 등급은 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다.
4  고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.
```

## 2. 전략 4종

네 전략 모두 `chunkers.py`에 있다. 파라미터는 `main.py` 위쪽에 모여 있다 — `FIXED_SIZE=40`,
`RECURSIVE_MAX=90`, `SEMANTIC_DROP=0.5`, `PARENT_MAX=90`.

### 2.1 fixed-size — 글자 수로만, 경계는 무시

가장 단순하다. `size` 글자씩 앞에서부터 잘라낸다. 문장이든 단어든 신경 쓰지 않는다.

```python
def fixed_char(text, size):
    chunks = []
    start = 0
    while start < len(text):
        chunks.append(text[start:start + size])
        start = start + size
    return chunks
```

`DOC`를 `size=40`으로 자르면 이렇게 나온다(총 5개).

```
[0] 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다. 단순 변심으로 환
[1] 불할 경우 반품 배송비 3000원은 고객이 부담합니다. 교환은 하자가 있
[2] 을 때만 무료로 가능하며 색상 변경은 1회만 허용됩니다. 멤버십 등급은
[3] 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다. 고객센터 운영
[4] 시간은 평일 오전 9시부터 오후 6시까지입니다.
```

문제가 바로 보인다. `[0]`은 "단순 변심으로 **환**"에서 끊기고 `[1]`은 "**불할** 경우…"로 시작한다.
`환불할`이라는 단어가 `환` / `불할`로 두 조각에 쪼개졌다. 사실 하나("단순 변심 환불 시 배송비 3000원")가
`[0]`과 `[1]`에 걸쳐 잘려, **어느 한 조각에도 온전히 담기지 않는다.** 이렇게 단어 중간에서 시작하는
조각은 그 자체로 읽어도 뜻이 깨져 있고, 검색으로 뽑아 LLM에 문맥으로 넘기면 품질이 나쁘다.

fixed-size는 "구조가 전혀 없는 텍스트라 일단 크기로라도 잘라야 한다"는 상황의 최소 기본값이다. 실무에선
보통 여기에 **overlap**(조각끼리 몇 글자 겹치게 자르기)을 얹어 경계에서 잘린 정보를 옆 조각이 일부라도
갖게 한다. 우리 구현은 overlap 없는 naive 버전이라 경계 손실이 그대로 드러난다 — 그 손실을 §3에서
숫자로 본다.

### 2.2 recursive — 문장 경계를 지키며 크기 제한

fixed의 문제는 "경계를 무시한다"였다. recursive는 **경계를 지키면서** 크기를 제한한다. 먼저 문장으로
쪼갠 뒤, 문장을 순서대로 담다가 다음 문장을 더하면 `max_size`를 넘길 것 같으면 거기서 끊고 새 조각을
시작한다. **문장 중간은 절대 자르지 않는다.**

```python
def recursive_split(text, max_size):
    sentences = split_sentences(text)
    chunks = []
    current = ""
    for s in sentences:
        if current and len(current) + 1 + len(s) > max_size:
            chunks.append(current)
            current = s
        elif current:
            current = current + " " + s
        else:
            current = s
    if current:
        chunks.append(current)
    return chunks
```

`max=90`으로 자르면 3개가 나온다(각 문장이 통째로 유지되는 걸 확인하라).

```
[0] 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다. 단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.   (70자)
[1] 교환은 하자가 있을 때만 무료로 가능하며 색상 변경은 1회만 허용됩니다. 멤버십 등급은 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다.   (80자)
[2] 고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.   (34자)
```

`3000원`, `7일` 같은 답이 온전한 문장 안에 담긴다. fixed에서 깨졌던 "단순 변심 환불" 사실이 `[0]`에
멀쩡히 들어 있다.

**이름의 "recursive"는 뭘까?** 실무의 진짜 recursive splitter(예: LangChain `RecursiveCharacterTextSplitter`)는
구분자 **우선순위 목록**을 놓고, 큰 경계부터 시도하다 조각이 `max`보다 크면 다음 경계로 내려가며 **점점
잘게 재귀적으로** 쪼갠다. LangChain 기본 구분자 순서는 이렇다.

```
문단(\n\n)  →  줄(\n)  →  단어(공백)  →  글자("")
```

큰 경계를 최대한 지키되 조각이 여전히 크면 필요한 만큼만 아래 단계로 내려간다는 발상이다. 여기서 주의할
점 하나 — 기본 구분자에는 **문장(`. `) 단계가 없다.** 문장 경계로 끊고 싶으면 구분자 목록을 직접 넘겨야
하는 opt-in이지 stock splitter의 기본 동작이 아니다.

우리 `recursive_split`은 이 아이디어에서 **문장 레벨 한 층**만 떼어 구현한 것이다. 그래서 문장 하나가
`max`보다 길면 우리 버전은 그 문장을 더 쪼개지 않고 그대로 한 조각으로 내보낸다(진짜 recursive라면
여기서 단어·글자로 더 내려간다). 우리 문서는 문장이 다 짧아 이 차이가 안 드러나지만, 개념은 알아 두자.

### 2.3 semantic — 의미가 멀어지는 자리에서 끊기

recursive는 "크기"로 끊는 자리를 정했다. 하지만 90자라는 숫자는 내용과 무관하다 — 우연히 서로 다른
두 주제가 한 조각에 묶일 수도 있다. semantic 청킹은 끊는 자리를 **의미**로 정한다. 문장을 하나씩
임베딩해서, **바로 옆 문장과의 코사인 유사도**를 본다. 유사도가 높으면 같은 이야기니 이어 붙이고,
유사도가 `drop` 아래로 떨어지면 "화제가 바뀌었다"고 보고 거기서 끊는다.

```python
def semantic_split(text, embed_fn, drop):
    sentences = split_sentences(text)
    embs = embed_fn(sentences)
    chunks = []
    current = sentences[0]
    for i in range(1, len(sentences)):
        if cosine(embs[i - 1], embs[i]) < drop:
            chunks.append(current)
            current = sentences[i]
        else:
            current = current + " " + sentences[i]
    chunks.append(current)
    return chunks
```

여기서 `embed_fn`은 `OllamaEmbeddingFunction` 객체 그 자체다. 이 객체는 호출 가능해서
`ollama_ef(["문장1","문장2"])`로 넘기면 문장별 벡터 리스트를 돌려준다. 그 벡터로 우리가 Phase 0에서
손으로 짠 `cosine`을 인접 문장쌍마다 계산한다.

`DOC`의 인접 문장 유사도를 bge-m3로 재면 이렇게 나온다(`drop=0.5` 기준). 소수값은 환경에 따라 조금 다를 수 있으니, `main.py`가 실행할 때 찍는 실제 값을 기준으로 보면 된다.

| 경계 | 문장쌍 | 코사인 유사도 | 판정 |
| --- | --- | --- | --- |
| 0→1 | 환불 기한 → 반품 배송비 | 0.647 | 유지 (0.5 이상) |
| 1→2 | 반품 배송비 → 교환·색상 | 0.572 | 유지 (0.5 이상) |
| 2→3 | 교환·색상 → 멤버십 갱신 | 0.488 | **끊김** (0.5 미만) |
| 3→4 | 멤버십 갱신 → 고객센터 시간 | 0.445 | **끊김** (0.5 미만) |

앞의 세 문장(환불/배송비/교환)은 서로 "구매 후 반품·교환 규정"이라 유사도가 높아 한 덩어리로 묶이고,
멤버십과 고객센터는 화제가 뚝 떨어져 각각 분리된다. 결과는 3개 조각이다.

```
[0] 환불은 … 신청할 수 있습니다. 단순 변심으로 … 3000원은 고객이 부담합니다. 교환은 … 1회만 허용됩니다.   (문장 0·1·2 묶임)
[1] 멤버십 등급은 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다.
[2] 고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.
```

주의 깊게 볼 점: semantic이 항상 "문장 하나씩 정확히" 떼어내는 게 아니다. 여기서는 오히려 앞 세 문장을
**하나로 합쳤다.** 그게 semantic의 본질이다 — 잘게 쪼개는 게 목적이 아니라 **의미가 이어지는 구간을
한 덩어리로 묶고, 화제가 바뀌는 곳에서만 끊는** 것.

**threshold(drop)는 경험적이다 — 정답이 하나로 안 정해진다.** `0.5`는 이 문서·이 모델(bge-m3)에서
경계들이 0.647 / 0.572 / 0.488 / 0.445로 나왔기에 "뒤 두 곳만 끊기게" 맞춘 값이다. 만약 `drop=0.6`으로
올리면 1→2(0.572)도 끊겨 조각이 더 잘게 나뉘고, `0.4`로 낮추면 아무 데도 안 끊겨 문서 전체가 한 조각이
된다. 데이터가 바뀌거나 임베딩 모델이 바뀌면 유사도 분포 자체가 달라져 이 값을 **다시 잡아야** 한다.
Phase 2에서 검색 threshold를 데이터에 맞춰 조정해야 했던 것과 같은 교훈이다 — threshold는 상수로
외워 두는 값이 아니라 데이터를 보고 맞추는 손잡이다.

참고로 실무 semantic chunker(예: LangChain `SemanticChunker`)는 우리처럼 절대 유사도 컷을 박는 대신,
유사도(거리) **분포의 백분위수**로 끊는 자리를 적응적으로 고른다. 이유는 방금과 같다 — `0.5` 같은 절대값은
모델·데이터가 바뀌면 분포째 어긋나니, 그 분포에 맞춰 경계를 다시 잡는 것이다.

### 2.4 parent-child — 작게 찾고 크게 돌려주기

정밀 매칭과 문맥은 서로 당긴다. 작게 자르면(문장) 검색은 정밀해지지만 답변에 넘길 문맥이 빈약하고,
크게 자르면(문단) 문맥은 풍부하지만 검색이 뭉툭해진다. parent-child는 **둘을 분리**해서 둘 다 가진다.
문장을 **자식(child)** 으로 만들어 검색에만 쓰고, 그 문장이 속한 문단을 **부모(parent)** 로 따로 보관해
답변에 돌려준다.

```python
def parent_child_split(text, parent_max):
    parents = recursive_split(text, parent_max)
    children = []
    for pi in range(len(parents)):
        for sent in split_sentences(parents[pi]):
            children.append((sent, pi))
    return parents, children
```

부모는 `recursive_split`으로 만든 문단(위 §2.2의 3개)이고, 자식은 각 부모를 문장으로 쪼갠 것이다.
각 자식은 `(문장, 부모_인덱스)`로 자기 부모가 누구인지 기억한다. 그래서 **자식 5개, 부모 3개**가 된다.

동작 흐름은 이렇다. 검색은 자식 컬렉션에 대고 한다(정밀). 자식을 저장할 때 metadata에 `{"parent": 인덱스}`를
넣어 두었으니, 자식이 매칭되면 그 metadata에서 부모 인덱스를 읽어 **부모 문단을 문맥으로 꺼내 돌려준다.**

```
질문: 반품 배송비 얼마?
  찾은 자식(정밀 매칭) : 단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.
  자식의 부모 인덱스   : 0
  돌려줄 부모(문맥)    : 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다. 단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.
```

정확히 "어느 문장"인지는 자식으로 좁혀 찾고, LLM에는 그 문장 하나만 던지는 게 아니라 문장이 속한
문단 전체(환불 기한 + 배송비)를 문맥으로 함께 넘긴다. 검색 정밀도와 답변 문맥을 동시에 챙기는 구조다.

### 2.5 overlap(겹침) — 전략이 아니라 "옵션"

overlap은 새 전략이 아니라 위 청커에 얹는 **옵션**이다. 새 청크를 시작할 때 이전 청크의 **끝 문장 몇 개를
물고** 시작한다. 경계에 걸친 내용이 양쪽 청크에 다 들어가, 검색에서 놓치지 않게 하려는 것이다.

`main.py`의 `[5]`가 recursive를 overlap 0 vs 1로 비교한다.

```
overlap=0 → 3개:
  [0] 환불…있습니다. 단순 변심…부담합니다.
  [1] 교환…허용됩니다. 멤버십…갱신됩니다.
  [2] 고객센터…까지입니다.

overlap=1 → 4개:
  [0] 환불…있습니다. 단순 변심…부담합니다.
  [1] 단순 변심…부담합니다. 교환…허용됩니다.    ← [0]의 끝 문장을 반복하고 이어감
  [2] 교환…허용됩니다. 멤버십…갱신됩니다.
  [3] 멤버십…갱신됩니다. 고객센터…까지입니다.
```

인접 청크가 문장 하나씩 겹쳐, 경계 문장이 두 청크에 모두 담긴다. 대신 **청크 수·저장·검색 중복이
늘어난다** — 그래서 보통 chunk_size의 10~20%만 겹친다. 실무에선 직접 짜지 않고 LangChain
`chunk_overlap` 같은 **파라미터 하나**로 준다. (`chunkers.py`의 `recursive_split_overlap`가 이 개념의
최소 구현이다.)

## 3. 측정 — answer_recall로 전략 비교

전략을 눈으로 보는 것과 "검색이 실제로 나아지는가"는 다른 문제다. Phase 4에서 만든 자를 여기서도 쓴다.
다만 이 장의 골든셋은 정답이 **문서 id**가 아니라 **정답 문자열**이라, 지표를 살짝 바꿔 쓴다 —
**answer_recall@k**.

```
answer_recall@k = (top-k 청크 중 하나라도 정답 문자열을 포함하면 1, 아니면 0)  을 골든셋에서 평균
```

골든셋(`corpus.py`의 `GOLDEN`)은 (질문, 정답에 반드시 들어갈 문자열) 6쌍이다 — 예: `("멤버십 등급은
언제 갱신되나요?", "매월 1일")`. 검색해 온 top-k 청크 안에 `"매월 1일"`이라는 글자가 들어 있으면 그
질문은 1점이다. 문자열 포함 여부라 LLM도 참조 답변도 필요 없다(Phase 4의 id 대조와 같은 정신).

```python
def answer_recall_at_k(col, k):
    hit_sum = 0.0
    for question, answer in corpus.GOLDEN:
        result = col.query(query_texts=[question], n_results=k)
        docs = result["documents"][0]
        hit = 0
        for d in docs:
            if answer in d:
                hit = 1
        hit_sum = hit_sum + hit
    return hit_sum / len(corpus.GOLDEN)
```

세 전략(fixed / recursive / semantic)으로 각각 컬렉션을 만들어 같은 6개 질문으로 재면 이렇게 나온다.

| 방식 | recall@1 | recall@3 |
| --- | --- | --- |
| fixed_char | **0.500** | 1.000 |
| recursive | **1.000** | 1.000 |
| semantic | **1.000** | 1.000 |

recursive와 semantic은 recall@1부터 만점이다. 잘린 문장 없이 사실이 온전한 조각에 담기니, top-1
청크가 곧바로 정답 문자열을 품는다. 반면 **fixed_char는 recall@1이 0.5로 확 낮다.**

### 정직한 해석 — recall@3=1.0을 액면가로 믿지 마라

표를 순진하게 읽으면 "fixed도 recall@3은 1.0이니 top-3까지 보면 괜찮잖아?"가 된다. 이 해석은 위험하다.

- **recall@1이 0.5로 낮은 이유**는 사실이 청크 경계에서 잘려(§2.1의 `환`/`불할`) top-1 청크 하나에
  정답이 온전히 안 담기기 때문이다. 답을 품은 조각이 다른 조각보다 아래로 밀려 top-1을 놓친다.
- **recall@3에서 fixed가 1.0이 되는 건** 그 잘린 조각이 어쨌든 top-3 **안에는** 나타나기 때문이다.
  하지만 그 조각은 `"불할 경우 반품 배송비 3000원은…"`처럼 **단어 중간에서 시작하는 깨진 조각**이다.
  정답 문자열 `3000원`이 글자로는 그 안에 들어 있어 지표는 1점을 주지만, 이 조각을 LLM에 문맥으로
  넘기면 "불할"로 시작하는 문장 파편이라 읽기 나쁘다.
- 즉 fixed는 **두 가지 모두에서** 불리하다. (1) top-1 정확도가 낮고(0.5), (2) 설령 top-3에 잡혀도
  **조각 자체의 품질**이 나쁘다. answer_recall 문자열 지표는 (2)를 못 잡아낸다 — 지표가 1.0이어도
  실제 답변 품질은 나쁠 수 있다.

교훈: 지표는 자일 뿐, 자가 못 재는 축(조각의 문맥 품질)이 있다. 숫자 하나만 보고 "동점이네" 하지 말고,
그 숫자가 **무엇을 세고 무엇을 못 세는지**까지 봐야 한다.

## 4. HNSW 인덱스 튜닝 — 개념과 Chroma 설정법

여기까지는 "무엇을 저장하나(청킹)"였다. HNSW는 "저장한 벡터를 **어떻게 빨리 찾나**"의 문제다.
Chroma가 안에서 쓰는 근사 최근접 이웃(ANN) 인덱스가 HNSW(Hierarchical Navigable Small World)다.
벡터가 많아지면 전부와 코사인을 비교하는 건 느리므로, 벡터들을 그래프로 엮어 두고 그 그래프를 타고
내려가며 "가까운 것"을 빠르게 **근사** 탐색한다. 정확도를 조금 내주고 속도를 얻는 구조다.
그 트레이드오프를 조절하는 손잡이가 셋이다.

| 파라미터 | 조절 대상 | 올리면 | 내리면 |
| --- | --- | --- | --- |
| **M** | 그래프에서 각 노드의 연결 수 | 정확도·메모리 ↑, 빌드 느려짐 | 메모리·정확도 ↓ |
| **ef_construction** | 인덱스를 **만들 때** 탐색 폭 | 인덱스 품질 ↑, 빌드 느려짐 | 빌드 빠름, 품질 ↓ |
| **ef_search** | **검색할 때** 탐색 폭 | recall ↑, 쿼리 느려짐 | 쿼리 빠름, recall ↓ |

직관: `M`과 `ef_construction`은 **한 번 낼 비용**(인덱스를 얼마나 촘촘히 지어 둘까)이고, `ef_search`는
**매 쿼리마다 낼 비용**(찾을 때 얼마나 넓게 뒤질까)이다. `ef_search`는 인덱스를 다시 안 짓고도 쿼리
시점에 바꿀 수 있어 가장 만만한 손잡이다 — "검색이 좀 부실한데 느려도 되니 정확도 올리자"면 이걸
키운다.

Chroma에서는 컬렉션을 만들 때 metadata로 넘긴다(우리가 `hnsw:space`를 넣던 바로 그 자리).

```python
col = client.get_or_create_collection(
    name="my_docs",
    embedding_function=ollama_ef,
    metadata={
        "hnsw:space": "cosine",
        "hnsw:M": 32,                  # 그래프 연결 수 (기본 16)
        "hnsw:construction_ef": 200,   # 빌드 시 탐색 폭 (기본 100)
        "hnsw:search_ef": 100,         # 검색 시 탐색 폭 (기본 10)
    },
)
```

위 키 4개는 이 폴더의 chromadb 1.5.9에서 **에러 없이 받아들여진다.** 다만 "에러 없이 받는다"와 "실제로
인덱스에 반영된다"는 다른 얘기다. 1.5.9에서 지금 권장되고 반영이 보장되는 경로는 별도 `configuration`
인자(`configuration={"hnsw": {...}}`)이고, metadata의 `hnsw:*` 키는 **하위 호환용 레거시 형태**라
버전에 따라 조용히 무시될 수도 있다. **Chroma는 버전마다 HNSW 설정 위치·키 이름이 바뀌어 왔으니**,
코드에 박기 전에 설치된 버전 문서에서 현재 경로를 확인하는 습관을 들이자.

**정직하게: 우리 데모엔 이 튜닝 코드가 없다.** HNSW 파라미터의 효과는 벡터가 **수천~수만 개**는 돼야
드러난다. 우리 코퍼스는 청크가 3~5개다. 이 규모에선 `ef_search`를 10으로 두든 200으로 두든 어차피
전수에 가깝게 훑어 결과가 똑같다 — 억지 데모를 만들면 "효과 있는 척"하는 가짜 그림만 나온다. 그래서
`main.py`는 HNSW를 건드리지 않고 `hnsw:space` 기본 설정만 쓴다. 이 절은 **개념과 설정법**까지만
다루고, 실제 튜닝은 큰 코퍼스를 만나는 날 Phase 4의 자(recall@k, 그리고 쿼리 지연시간)로 전후를 재며
하면 된다.

## 6. `main.py`가 보여주는 것 — [1]~[5] 지도

스크립트는 Ollama·모델 점검(`check_ollama`) 뒤 네 단계를 차례로 찍는다.

| 단계 | 화면 제목 | 하는 일 | 대응 절 |
| --- | --- | --- | --- |
| **[1]** | 청킹 방식 비교 (눈으로) | fixed·recursive·semantic으로 같은 문서를 잘라 조각을 나란히 출력 | §2 |
| **[2]** | 검색 품질 비교 (answer_recall@k) | 세 전략으로 컬렉션을 만들어 6개 질문으로 recall@1·@3을 재고 정직한 해석까지 출력 | §3 |
| **[3]** | Semantic 청킹 원리 | 인접 문장 코사인 유사도(0.647/0.572/0.488/0.445)를 찍고 어디서 끊기는지 표시 | §2.3 |
| **[4]** | Parent-Child 시연 | 부모 3·자식 5를 만들고, "반품 배송비 얼마?"로 자식을 찾아 그 부모 문단을 문맥으로 돌려줌 | §2.4 |
| **[5]** | Overlap 비교 | recursive를 overlap 0 vs 1로 잘라, 인접 청크가 문장 하나씩 겹치는 걸 보여줌(경계 문장이 양쪽에) | §2.5 |

읽는 순서의 뜻: [1]에서 **조각을 눈으로** 보고(fixed가 단어 중간에서 잘리는 걸 직접 확인), [2]에서 그게
**검색 숫자로** 어떻게 나타나는지(fixed recall@1=0.5) 잰다. [3]은 semantic이 왜 그 자리에서 끊었는지
**유사도 근거**를 펼치고, [4]는 parent-child의 "작게 찾고 크게 돌려주기"를 한 번의 실제 쿼리로 보여준다.

## 7. Phase 5 완료 체크리스트

- [ ] Phase 2의 문단 청킹으로 부족한 세 상황(구조 없는 텍스트 · 한 문단 다주제 · 정밀+문맥 동시)을 말할 수 있다.
- [ ] fixed / recursive / semantic / parent-child가 각각 무엇을 기준으로 끊는지 한 줄씩 말할 수 있다.
- [ ] fixed-size가 단어·사실을 경계에서 잘라(`환`/`불할`) 조각 품질을 망치는 걸 실제 출력으로 확인했다.
- [ ] recursive가 문장 경계를 지키며 max 이하로 모으는 걸 알고, 진짜 recursive splitter의 "구분자 우선순위" 개념도 안다.
- [ ] semantic이 인접 문장 유사도로 끊고, threshold(drop=0.5)가 데이터·모델마다 다시 잡아야 하는 경험값임을 안다.
- [ ] 우리 문서에서 semantic이 앞 세 문장을 오히려 하나로 **묶는다**는 걸 유사도 표(0.647/0.572/0.488/0.445)로 설명할 수 있다.
- [ ] parent-child의 "작게 찾고(자식 문장) 크게 돌려준다(부모 문단)"를 metadata `parent` 인덱스와 함께 설명할 수 있다.
- [ ] fixed recall@1=0.5 vs recursive·semantic 1.0의 표를 읽고, recall@3=1.0이어도 fixed 조각 품질이 나쁜 이유를 말할 수 있다.
- [ ] HNSW의 M · ef_construction · ef_search가 각각 무엇을 조절하는지, Chroma metadata로 어떻게 설정하는지 안다.
- [ ] 왜 우리 작은 코퍼스엔 HNSW 튜닝 코드를 안 만드는지(효과는 수천~수만 벡터부터) 설명할 수 있다.
- [ ] overlap(겹침)이 경계 문장을 인접 청크에 함께 담아 문맥 손실을 줄이는 **옵션**임을 알고, 청크 수·중복이 느는 트레이드오프를 안다.
- [ ] `python main.py`를 돌려 [1]~[5]와 위 숫자들을 직접 확인했다.

전부 체크됐다면, "어떻게 자르냐"가 검색 품질을 바꾼다는 걸 숫자로 확인한 것이고, 그 변화를 Phase 4의
자로 재는 습관까지 든 것이다. 다음 Phase에서 무엇을 바꾸든 원리는 같다 — 바꾸고, 재고, 개선인지 확인한다.
