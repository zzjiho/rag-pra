# Phase 6 — RAG 파이프라인 & LLM 결합 (드디어 G)

> Phase 0부터 5까지 우리가 만든 건 전부 **R(검색)** 이었다. 임베딩으로 텍스트를 벡터로 바꾸고,
> ChromaDB에 넣고, 청킹을 바꿔 가며 "질문에 맞는 청크를 잘 뽑는가"를 재고 튜닝했다. 그런데 사용자가
> 원하는 건 청크 목록이 아니라 **답 한 문장**이다. "단순 변심 환불이면 배송비 얼마예요?"에 대해
> `[c0] 환불은 상품 수령 후 7일…` 같은 청크를 던져 주는 게 아니라 "3000원을 부담하셔야 합니다"라고
> 말해 줘야 한다.
>
> 그 마지막 한 걸음이 **G(생성)** 다. 검색해 온 청크를 LLM에게 "이 문맥만 근거로 답해"라고 넘기면,
> LLM이 그 문맥을 읽고 자연어 답을 쓴다. 이걸 붙이면 **RAG 전체 루프가 완성된다** — Retrieval(검색)
> 로 재료를 찾고, Augmented(증강)로 그 재료를 프롬프트에 얹고, Generation(생성)으로 답을 만든다.
> RAG라는 이름 자체가 이 세 글자다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "지금까지 R만 했다"는 게 무슨 뜻이고, G를 붙이면 뭐가 달라지나?
- RAG 파이프라인의 다섯 단계(인제스트 · 검색 · 증강 · 생성 · 인용)는 각각 코드 어느 함수인가?
- SYSTEM 프롬프트의 세 지시("문맥만 근거로" · "없으면 '문서에서 찾을 수 없습니다'" · "인용 번호")는 왜 필요한가?
- grounding이 어떻게 LLM의 할루시네이션(환각)을 줄이나? 주차장 질문이 왜 거부되나?
- 왜 임베딩은 bge-m3, 생성은 qwen2.5:**7b**인가? 3b는 왜 탈락했나? `temperature=0`은 왜 쓰나?
- 답변 끝의 `[1]`은 무엇을 가리키나 — 청크 id(c0/c1/c2)인가 프롬프트 번호인가?

---

## 1. R만 했다 — 이제 G를 붙인다

RAG = **R**etrieval **A**ugmented **G**eneration. 이름 순서대로 세 부분이다.

- **R(검색)** — 질문과 관련된 문서 조각을 벡터 DB에서 찾는다. Phase 0~5가 전부 여기였다.
- **A(증강)** — 찾아 온 조각을 LLM 프롬프트의 `[문맥]`으로 붙인다. LLM에게 "이걸 보고 답하라"고 재료를 쥐여 주는 단계.
- **G(생성)** — LLM이 그 문맥을 읽고 자연어 답을 쓴다. 이번 Phase에서 처음 붙인다.

왜 굳이 검색을 먼저 하고 LLM에 넘기나? LLM만 단독으로 쓰면 두 가지 문제가 있다.

- **모르는 걸 지어낸다(할루시네이션).** "우리 회사 환불 배송비 얼마?"는 LLM이 학습한 적 없는 우리
  내부 정책이다. 그냥 물으면 그럴듯한 숫자를 지어낸다.
- **최신·비공개 정보를 모른다.** LLM은 학습 시점에 고정돼 있고, 우리 사내 문서는 학습 데이터에 없다.

RAG는 이 둘을 "먼저 우리 문서에서 근거를 찾아, 그 근거만 주고 답하게" 해서 푼다. LLM의 언어 능력은
빌리되, **사실은 우리가 검색해서 넘긴 문맥에서만** 가져오게 하는 구조다. 그래서 Phase 0~5의 검색
품질이 그대로 답변 품질이 된다 — 엉뚱한 청크를 검색하면 LLM은 엉뚱한 근거로 답한다. R을 이렇게 오래
다진 이유가 여기서 드러난다.

## 2. RAG 파이프라인 5단계 — 어느 함수가 무엇을 하나

코드는 `pipeline.py`에 있고, 다섯 단계가 함수 하나씩에 대응한다. 큰 흐름은 두 덩어리다 —
**인제스트(문서를 미리 넣어 두기)** 는 서비스 시작할 때 한 번, **질의응답(검색→증강→생성→인용)** 은
질문이 올 때마다.

| 단계 | 하는 일 | 함수 |
| --- | --- | --- |
| ① 인제스트 (ingest) | 문서를 청킹 → 임베딩 → 벡터 DB에 저장 | `pipeline.ingest` |
| ② 검색 (retrieve) | 질문으로 관련 청크를 꺼냄 | `pipeline.retrieve` |
| ③ 증강 (augment) | 청크 + 질문을 프롬프트로 조립 | `pipeline.build_prompt` |
| ④ 생성 (generate) | 프롬프트를 LLM에 넣어 답을 받음 | `pipeline.generate` |
| ⑤ 인용 (cite) | 답에 근거 문맥 번호 `[1]`을 붙임 | SYSTEM 프롬프트 지시 (④가 만들어 냄) |

②~⑤를 한 번에 묶은 게 `pipeline.answer`다 — 이 함수 하나가 "질문 하나 → 답 하나"의 전체 질의응답이다.

### ① 인제스트 — 청킹 + 임베딩 + 저장

```python
def ingest(collection, doc, max_size):
    chunks = recursive_split(doc, max_size)
    ids = []
    for i in range(len(chunks)):
        ids.append("c%d" % i)
    collection.add(ids=ids, documents=chunks)
    return chunks
```

Phase 5에서 만든 `recursive_split`(문장 경계를 지키며 `max_size` 이하로 모으기)으로 문서를 청킹하고,
`c0`, `c1`… 아이디를 붙여 `collection.add`로 넣는다. **임베딩은 여기서 자동으로 일어난다** —
컬렉션에 `OllamaEmbeddingFunction(bge-m3)`을 걸어 뒀기 때문에, `add`가 문서를 저장하기 직전에 각 청크를
bge-m3로 벡터화한다. 우리가 벡터를 직접 다루지 않아도 되는 이유다.

`MAX_SIZE=90`으로 이 장의 문서(`documents.DOC`, 문장 5개)를 자르면 청크 3개가 나온다(실제 실행 출력).

```
[c0] 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다. 단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.
[c1] 교환은 하자가 있을 때만 무료로 가능하며 색상 변경은 1회만 허용됩니다. 멤버십 등급은 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다.
[c2] 고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.
```

### ② 검색 — 질문으로 청크 꺼내기

```python
def retrieve(collection, question, k):
    result = collection.query(query_texts=[question], n_results=k)
    ids = result["ids"][0]
    docs = result["documents"][0]
    return ids, docs
```

`collection.query`가 질문을 bge-m3로 벡터화하고, 저장된 청크 중 코사인 거리가 가까운 순으로 `k`개를
돌려준다. `query`는 질문 여러 개를 한 번에 받게 설계돼 결과가 `[[...]]`로 한 겹 더 싸여 나온다 — 우리는
질문 하나만 넣으니 `[0]`으로 벗겨 첫 질문 결과만 꺼낸다.

> **작은 코퍼스의 솔직한 한계.** 이 장은 청크가 3개인데 `TOP_K=3`이다. 그래서 어떤 질문을 넣든
> **세 청크가 전부 검색된다** — 검색이 뭔가를 걸러 내는 게 아니라 **순서만 바꾼다.** 관련 청크가 맨 앞으로
> 올라올 뿐이다("고객센터"를 물으면 `c2`가 1등, "색상 변경"을 물으면 `c1`이 1등). 진짜 서비스는 청크가
> 수천~수만 개라 top-k가 관련 없는 대다수를 실제로 잘라 낸다. 여기서는 규모가 작아 그 "잘라 냄"이 안
> 드러나지만, **관련 청크를 맨 위로 끌어올린다**는 검색의 핵심 동작은 그대로 확인된다. 이 순서가
> 왜 중요한지는 §2 끝(인용)과 §3에서 이어진다.

### ③ 증강 — 문맥 + 질문을 프롬프트로

```python
def build_prompt(context_docs, question):
    lines = ["[문맥]"]
    for i in range(len(context_docs)):
        lines.append("[%d] %s" % (i + 1, context_docs[i]))
    lines.append("")
    lines.append("[질문] %s" % question)
    lines.append("답변:")
    return "\n".join(lines)
```

검색해 온 청크마다 `[1]`, `[2]`… 번호를 붙여 `[문맥]` 아래 나열하고, 그 밑에 `[질문]`과 `답변:`을 둔다.
"환불 배송비" 질문이면 실제로 이런 문자열이 만들어진다.

```
[문맥]
[1] 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다. 단순 변심으로 환불할 경우 반품 배송비 3000원은 고객이 부담합니다.
[2] 교환은 하자가 있을 때만 무료로 가능하며 색상 변경은 1회만 허용됩니다. 멤버십 등급은 최근 3개월 구매액으로 산정되며 매월 1일에 갱신됩니다.
[3] 고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.

[질문] 단순 변심으로 환불하면 배송비 얼마 내요?
답변:
```

여기서 붙이는 `[1]`, `[2]` 번호는 **검색 결과 순서대로** 매겨진다는 점이 중요하다. `retrieve`가 관련
청크를 맨 앞에 뒀으니 `[1]`이 곧 "가장 관련 있는 청크"다. 이 번호가 뒤에서 인용의 근거가 된다.

### ④ 생성 — LLM 호출

```python
def generate(system, user):
    res = ollama.chat(
        model=CHAT_MODEL,
        messages=[
            {"role": "system", "content": system},
            {"role": "user", "content": user},
        ],
        options={"temperature": 0},
    )
    return res["message"]["content"]
```

`ollama.chat`에 **역할 두 개**를 넘긴다. `system`은 "너는 이렇게 행동하라"는 규칙(다음 절의 grounding
지시), `user`는 방금 조립한 문맥+질문 프롬프트다. LLM은 system 규칙을 지키며 user에 답하고, 답 텍스트는
`res["message"]["content"]`에 들어 있다. `temperature=0`은 §5에서 설명한다(같은 입력이면 같은 답이
나오게 하는 재현성 설정).

### ⑤ 인용 — 근거 번호 붙이기

인용은 별도 함수가 없다. LLM이 SYSTEM 지시("근거로 쓴 문맥 번호를 `[1]`처럼 표시")를 따라 **답 안에
직접** 번호를 써 준다. 실제 답을 보면 이렇다.

```
질문: 단순 변심으로 환불하면 배송비 얼마 내요?
LLM 답변: 3000원을 부담해야 합니다.[1]
```

이 `[1]`은 **프롬프트 `[문맥]`의 1번**을 가리킨다 — 청크 id `c0`이 아니라 **이번 프롬프트에서 1번 자리에
놓인 청크**다. `retrieve`가 환불 청크(`c0`)를 맨 앞에 뒀으니 프롬프트 1번 = `c0`이고, LLM은 거기서 근거를
찾았다고 `[1]`을 붙였다. 그래서 답을 검증할 때 "이 답이 정말 `[1]`번 문맥에 있는 말인가?"를 사람이 바로
대조할 수 있다. `pipeline.answer`가 돌려주는 `sources`(=(id, 청크) 목록)가 프롬프트 번호 순서 그대로라,
`[N]`번은 `sources`의 N번째 항목과 일치한다.

`answer`가 이 다섯을 엮는다.

```python
def answer(collection, question, k):
    ids, docs = retrieve(collection, question, k)   # ②
    user = build_prompt(docs, question)             # ③
    text = generate(SYSTEM, user)                   # ④ (+ ⑤ 인용은 LLM이 답에 포함)
    sources = []
    for i in range(len(ids)):
        sources.append((ids[i], docs[i]))
    return {"answer": text, "sources": sources}
```

## 3. 프롬프트 설계 — grounding은 SYSTEM에 있다

RAG의 답변 품질을 실제로 결정하는 건 화려한 코드가 아니라 **SYSTEM 프롬프트 세 문장**이다.

```python
SYSTEM = ("당신은 문서 기반 고객지원 어시스턴트입니다. 아래 [문맥]에 실제로 있는 내용만 근거로 답하세요. "
          "[문맥]에 답의 근거가 없으면 반드시 정확히 '문서에서 찾을 수 없습니다.'라고만 답하고 절대 지어내지 마세요. "
          "답에 근거로 쓴 문맥 번호를 [1] 처럼 표시하세요.")
```

세 개의 지시가 각각 하나씩 문제를 막는다.

- **"[문맥]에 실제로 있는 내용만 근거로 답하세요"** — 이게 **grounding(근거 고정)** 이다. LLM이 자기가
  학습한 일반 지식이나 상상으로 답하지 말고, 이번에 넘긴 문맥 안에서만 답을 찾으라는 지시. 이 한 줄이
  "LLM이 우리 문서를 근거로 답하는 어시스턴트"와 "아무 말이나 하는 챗봇"을 가른다.
- **"근거가 없으면 정확히 '문서에서 찾을 수 없습니다.'라고만 답하고 절대 지어내지 마세요"** — LLM에게
  **모른다고 말할 권한**을 준다. 이 지시가 없으면 LLM은 문맥에 답이 없어도 어떻게든 그럴듯한 답을 지어
  내려 한다(할루시네이션). "없으면 없다고 해도 된다, 그게 올바른 답이다"라고 명시해야 지어내기를 멈춘다.
  문구를 **정확히 고정**한 건, 답할 수 없을 때 항상 똑같은 문장이 나오게 해서 후처리·모니터링에서 "거부"를
  기계적으로 구분하려는 것이다(뒤의 API에서 이 문자열로 거부 케이스를 잡을 수 있다).
- **"근거로 쓴 문맥 번호를 [1]처럼 표시하세요"** — 답의 **출처를 추적**하게 한다. 사용자와 우리 둘 다
  "이 답이 몇 번 문맥에서 나왔나"를 확인할 수 있어, 틀린 답이 나와도 어느 청크가 문제인지 짚어 고칠 수
  있다. 출처 없는 답은 맞아도 못 믿고, 틀려도 원인을 못 찾는다.

user 프롬프트(§2 ③)와 SYSTEM은 역할이 다르다. SYSTEM은 **매 질문마다 안 바뀌는 규칙**(어떻게
행동하라), user는 **질문마다 바뀌는 재료**(이번 문맥과 질문)다. 규칙을 SYSTEM에 따로 두면 LLM이
"이건 지켜야 할 지침"으로 더 강하게 받아들인다.

## 4. Grounding · 할루시네이션 차단 — 주차장 질문

grounding이 실제로 작동하는지는 **답할 수 없는 질문**을 던져 보면 안다. `documents.QUESTIONS`의 마지막
질문 "주차장 있나요?"는 우리 문서에 관련 내용이 **전혀 없다.** 문서는 환불·교환·멤버십·고객센터 얘기뿐
주차장은 한 글자도 없다.

실제 실행 결과다.

```
질문: 주차장 있나요?
검색된 문맥(sources):
  [c2] 고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지
  [c1] 교환은 하자가 있을 때만 무료로 가능하며 색상 변경은
  [c0] 환불은 상품 수령 후 7일 이내에 신청할 수 있습니다.
LLM 답변: 문서에서 찾을 수 없습니다.
```

주목할 점: **세 청크가 다 문맥으로 넘어갔는데도** LLM은 지어내지 않고 거부했다. 검색이 걸러 준 게
아니다(작은 코퍼스라 셋 다 넘어감). 문맥 안에 주차장 근거가 없다는 걸 LLM이 읽고, SYSTEM 지시대로
"찾을 수 없습니다"로 답한 것이다. 만약 SYSTEM의 두 번째 지시가 없었다면, LLM은 "네, 지하 주차장이
있습니다" 같은 말을 그럴듯하게 지어냈을 수 있다 — 우리 문서엔 없는 정보를.

**RAG가 할루시네이션을 줄이는 원리**가 이 한 케이스에 다 들어 있다.

- LLM 단독은 "모르는 것도 아는 척" 지어내는 경향이 있다. 학습 데이터의 통계로 "그럴듯한 다음 말"을
  만드는 게 본업이라, 사실 여부와 무관하게 매끄러운 문장을 낸다.
- RAG는 (1) **먼저 우리 문서에서 근거를 찾아** 문맥으로 주고, (2) SYSTEM 지시로 **그 문맥 밖으로 나가지
  말라**고 못박고, (3) **없으면 없다고 말할 길**을 열어 준다. 세 장치가 겹쳐 "지어내기"의 여지를 좁힌다.
- 그래도 **0으로 만들진 못한다.** 검색이 엉뚱한 청크를 물어 오면 LLM은 그 엉뚱한 근거로 성실히 답하고,
  드물게는 지시를 어기고 지어내기도 한다. 그래서 grounding은 "환각을 없앤다"가 아니라 **"크게 줄인다"** 다.
  검색 품질(Phase 2~5)과 프롬프트 설계(§3)가 함께 좋아야 이 효과가 커진다.

나머지 세 질문은 문맥에 근거가 있어 정상적으로 근거 답변 + 인용이 나온다(실제 출력).

| 질문 | 1등 검색 청크 | LLM 답변 |
| --- | --- | --- |
| 단순 변심으로 환불하면 배송비 얼마 내요? | c0 (환불) | `3000원을 부담해야 합니다.[1]` |
| 고객센터 몇 시까지 해요? | c2 (고객센터) | `고객센터 운영 시간은 평일 오전 9시부터 오후 6시까지입니다.[1]` |
| 색상 변경은 몇 번까지 되나요? | c1 (교환·색상) | `색상 변경은 1회만 허용됩니다. [1]` |
| 주차장 있나요? | (근거 없음) | `문서에서 찾을 수 없습니다.` |

세 답 모두 `[1]`을 인용하는 건 우연이 아니다. `retrieve`가 관련 청크를 항상 맨 앞(프롬프트 `[1]`)에
올려놓으니, 답의 근거도 늘 1번 자리에 있다(인용 번호의 정체는 §2⑤ 참고).

## 5. 모델 — bge-m3(임베딩) + qwen2.5:7b(생성), 둘 다 Ollama 로컬

RAG에는 성격이 다른 모델 **두 개**가 필요하다. 둘을 헷갈리지 말자.

| 역할 | 모델 | 하는 일 | 쓰이는 곳 |
| --- | --- | --- | --- |
| **임베딩** | `bge-m3` | 텍스트 → 벡터 (검색용) | 인제스트(청크 저장)와 검색(질문 벡터화) |
| **생성** | `qwen2.5:7b` | 문맥 → 자연어 답 (채팅) | 생성(`ollama.chat`) |

**임베딩 모델은 답을 못 쓴다.** bge-m3는 텍스트를 1024차원 벡터로 바꿀 뿐, 문장을 생성하지 못한다.
Phase 0~5가 이 모델만으로 굴러간 이유이자, 이번에 채팅 LLM을 따로 붙여야 하는 이유다. Korean RAG라
임베딩은 다국어에 강한 bge-m3를 쓴다(Phase 0에서 영어 위주 nomic 모델이 한국어 검색을 망쳤던 이유와
같다).

**생성은 왜 7b인가 — 3b는 과잉 거부(false refuse) 때문에 탈락했다.** 처음엔 더 가벼운 `qwen2.5:3b`를 써
봤는데, 문맥에 **근거가 분명히 있는** 질문(특히 "색상 변경 몇 번?")을 반복 실행하면 "문서에서 찾을 수
없습니다"로 거부하는 일이 이 4개 질문 세트에서 종종 나왔다. 답할 수 있는 것도 안 답하는 이 실패를
**false refuse(거짓 거부)** 라 한다 — 할루시네이션(없는데 지어냄)의 반대 방향이고, 고객지원에선 "멀쩡한
질문에 못 찾겠다고 하는" 것도 똑같이 나쁘다. `qwen2.5:7b`로 올리니 근거 있는 질문엔 제대로 답하고, 근거
없는 질문(주차장)만 정확히 거부했다. 이건 "3b는 항상 나쁘다"가 아니라, **이 grounding 지시를 3b가 더
엄격하게(=보수적으로) 해석하는 경향** 차이로 보는 게 맞다. 근거 답변 · 정당한 거부 · 한국어 · 인용 네
가지가 모두 안정적인 쪽이 7b라 7b를 택했다. **모델 크기는 "클수록 좋다"가 아니라 "이 작업에서 원하는
행동이 나오는 최소 크기"로 고른다.**

**`temperature=0` — 재현성.** temperature는 LLM이 다음 단어를 고를 때의 무작위성이다. 높이면 답이
다양·창의적이지만 매번 달라지고, 0으로 두면 확률이 가장 높은 단어를 매번 고르는 **결정적(greedy)
디코딩**이라 같은 입력에 **사실상 같은 답**이 나온다(부동소수점 연산 순서 등으로 실행 환경에 따라 미세한
차이는 있을 수 있다). 고객지원 RAG는 창의성이 아니라 **일관성**이 중요하고(같은 질문엔 같은 답이 나와야
신뢰), 우리처럼 답을 검증·재현하려면 0이 맞다. 이 README가 인용한 답들이 대체로 그대로 재현되는 것도
`temperature=0` 덕이다.

**둘 다 로컬(Ollama).** 외부 API로 안 보내고 내 컴퓨터의 Ollama가 두 모델을 돌린다. 문서와 질문이 밖으로
나가지 않아 프라이버시에 유리하고, 호출 비용이 없어 마음껏 실험할 수 있다. 대신 첫 실행에서 모델을 받아야
하니 `ollama pull`이 필요하다(§7).

## 6. (선택) FastAPI로 API화 — serve.py

`main.py`는 정해진 질문 목록을 한 번 돌려 보는 스크립트다. 실제 서비스는 "외부에서 아무 질문이나 넘기면
답을 돌려주는" 형태여야 한다. `serve.py`는 `pipeline.answer`를 **HTTP API로 감싼** 최소 예시다.

```python
app = FastAPI()
collection = build_collection()   # 서버 뜰 때 인제스트 한 번

@app.get("/ask")
def ask_get(q: str):
    return pipeline.answer(collection, q, TOP_K)
```

핵심은 **인제스트와 질의응답의 분리**다. `build_collection()`(청킹+임베딩+저장)은 서버가 **뜰 때 딱 한 번**
돌고, 그 뒤로는 요청이 올 때마다 `/ask`가 이미 준비된 컬렉션에 `answer`만 호출한다. 매 요청마다 문서를
다시 넣지 않는다 — 실제 서비스도 이 구조다(무거운 인덱싱은 미리, 가벼운 질의는 실시간).

`serve.py`에는 `POST /ask`도 있는데 같은 `answer`를 부르는 동일 동작이다. 이 최소 예시에선 GET/POST 둘 다
본문이 아니라 쿼리 파라미터 `q`로 질문을 받는다(전형적인 REST는 POST에서 JSON 본문을 받지만, 여기선
단순화를 위해 그러지 않았다).

실행법(선택 패키지 설치 후):

```bash
pip install fastapi uvicorn
uvicorn serve:app --reload
```

띄운 뒤 다른 터미널이나 브라우저에서:

```bash
curl "http://localhost:8000/ask?q=색상 변경은 몇 번까지 되나요?"
# -> {"answer":"색상 변경은 1회만 허용됩니다. [1]","sources":[["c1","교환은 ..."],...]}
```

`main.py`와 완전히 같은 `pipeline.answer`를 부르므로 답도 같다. 파이프라인 로직(`pipeline.py`)을 실행
방식(스크립트 `main.py` / 서버 `serve.py`)과 분리해 둔 덕에, 같은 코어를 CLI로도 API로도 재사용한다.

## 7. 파일 구조 & 설치·실행

### 파일 구조

| 파일 | 역할 |
| --- | --- |
| `documents.py` | **데이터.** 실습 문서 `DOC`(문장 5개)와 질문 목록 `QUESTIONS`(마지막은 근거 없는 거부 케이스). 로직 없음. |
| `pipeline.py` | **RAG 코어.** `SYSTEM` 프롬프트 + 5단계 함수(`ingest`·`retrieve`·`build_prompt`·`generate`) + 이를 엮는 `answer`. DB 연결·실행은 모름(순수 파이프라인). |
| `main.py` | **실행(CLI).** Ollama·모델 점검 → 컬렉션 준비 → 인제스트 → 네 질문에 답하며 검색·증강·생성·인용을 화면에 펼침. |
| `serve.py` | **실행(API, 선택).** 같은 `pipeline.answer`를 FastAPI `/ask`로 감싼 최소 서버. |

`pipeline.py`를 데이터·실행과 떼어 둔 덕에, 파이프라인만 따로 테스트하거나 `main.py`(CLI)와
`serve.py`(API)가 **같은 코어를 재사용**한다.

### 설치

이 폴더(`phase-6-rag-pipeline`)에서:

```bash
python3 -m venv .venv
source .venv/bin/activate        # 새 터미널을 열 때마다 이 줄로 활성화
pip install -r requirements.txt  # chromadb, ollama 설치
```

### 모델 준비 — 이번엔 채팅 LLM도 받아야 한다

Ollama 서버와 임베딩 모델 `bge-m3`는 앞 Phase에서 준비했다. **이번 Phase는 채팅 LLM이 새로 필요하다.**

```bash
brew services start ollama   # 서버가 꺼져 있으면
ollama pull bge-m3           # 임베딩 (이미 있으면 넘어감)
ollama pull qwen2.5:7b       # 채팅 LLM — 이번에 꼭 받아야 함 (약 4.7GB, 첫 다운로드는 몇 분 걸림)
```

`main.py`가 실행 첫머리(`check_ollama`)에서 이 둘이 다 있는지 자동 점검하고, 빠졌으면 어떤
`ollama pull` 명령을 치면 되는지 알려 준다.

### 실행

```bash
python main.py
```

- 실행하면 이 폴더에 `./chroma_db`가 생긴다(벡터가 파일로 저장되는 자리).
- 스크립트는 컬렉션(`phase6_support`)을 매번 지웠다 새로 만든다(`build_collection` 첫머리의
  `delete_collection`). 항상 깨끗한 상태에서 같은 결과를 재현하기 위해서다.
- `temperature=0`이라 답은 재현되지만, LLM 답변의 문장 표현은 모델·환경에 따라 미세하게 다를 수
  있다. **근거 있는 질문엔 근거 답변+인용이 나오고, 주차장 질문은 "문서에서 찾을 수 없습니다"로
  거부된다**는 방향은 그대로다.

## 8. `main.py`가 보여주는 것 — 단계 지도

스크립트는 Ollama·모델 점검(`check_ollama`) 뒤 세 블록을 차례로 찍는다.

| 블록 | 화면 제목 | 하는 일 | 대응 절 |
| --- | --- | --- | --- |
| **[1]** | 인제스트 | `recursive_split(max=90)`으로 문서를 3개 청크로 잘라 벡터 DB에 저장, 청크를 출력 | §2 ① |
| **[2]** | RAG 질의응답 | 네 질문마다 검색된 문맥(sources)과 LLM 답변을 나란히 출력 — 검색(R)→증강(A)→생성(G)이 한눈에 | §2 ②③④⑤ |
| **[3]** | 정리 | RAG 전체 루프와 grounding(주차장 거부)의 의미를 텍스트로 요약 | §1·§4 |

읽는 순서의 뜻: [1]에서 **문서가 어떻게 청크로 저장되는지** 보고(§2①), [2]에서 그 청크가 **질문마다 검색
→ 증강 → 생성 → 인용을 거치는지** 본다(§2②~⑤). 특히 [2]의 네 번째 질문(주차장)은 §4에서 짚은
"문맥은 다 채워졌는데도 거부"를 화면으로 확인하는 자리다.

## 9. Phase 6 완료 체크리스트

- [ ] "지금까지 R만 했다"가 무슨 뜻인지, G를 붙여 RAG 전체 루프가 완성된다는 걸 설명할 수 있다.
- [ ] RAG 5단계(인제스트·검색·증강·생성·인용)가 각각 `pipeline.py`의 어느 함수인지 짚을 수 있다.
- [ ] 임베딩은 `collection.add`/`query` 안에서 자동으로 일어난다(bge-m3)는 걸 안다.
- [ ] 청크 3개에 `TOP_K=3`이라 검색이 걸러 내지 않고 순서만 바꾼다는 작은-코퍼스 한계를 정직하게 말할 수 있다.
- [ ] SYSTEM 프롬프트 세 지시(문맥만 근거 · 없으면 정확히 거부 · 인용 번호)가 각각 무슨 문제를 막는지 설명할 수 있다.
- [ ] user 프롬프트와 SYSTEM 프롬프트의 역할 차이(매번 바뀌는 재료 vs 안 바뀌는 규칙)를 안다.
- [ ] 주차장 질문이 문맥을 다 받고도 거부되는 걸 보고, grounding이 할루시네이션을 줄이는 원리를 설명할 수 있다.
- [ ] grounding이 환각을 "없애는" 게 아니라 "줄이는" 것이고, 검색 품질이 나쁘면 답도 나빠진다는 걸 안다.
- [ ] 임베딩(bge-m3)과 생성(qwen2.5:7b)이 서로 다른 역할의 두 모델임을 구분한다.
- [ ] 왜 3b가 과잉 거부(false refuse)로 탈락하고 7b를 택했는지, `temperature=0`을 왜 쓰는지 말할 수 있다.
- [ ] 답변 끝의 `[1]`이 청크 id가 아니라 프롬프트 문맥 번호(=sources의 N번째)임을 안다.
- [ ] (선택) `serve.py`가 인제스트를 서버 기동 시 한 번, 질의를 요청마다 하도록 나눠 둔 이유를 안다.
- [ ] `ollama pull qwen2.5:7b`로 채팅 LLM을 받고 `python main.py`를 돌려 네 답을 직접 확인했다.

전부 체크됐다면, R만 있던 파이프라인에 G를 붙여 **질문 하나가 답 한 문장이 되는** RAG 전체 루프를 처음
완성한 것이다. 남은 Phase(재랭킹·쿼리 재작성·LangGraph 통합)는 전부 이 루프의 어느 단계를 더 좋게
만드는 이야기다 — 검색을 더 정밀하게, 프롬프트를 더 똑똑하게, 루프를 에이전트가 스스로 돌게.
