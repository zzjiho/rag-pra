# Phase 4 — 검색 평가: recall@k · MRR · nDCG

> Phase 3에서 검색기 v2(필터 + 하이브리드)를 만들었다. E-402를 물으면 순수 벡터는 정답을 4위로
> 밀었는데, 하이브리드가 1위로 끌어올렸다. 그때 우리는 그걸 **눈으로 보고** "좋아졌다"고 말했다.
> 그런데 질문이 6개, 60개, 600개로 늘어나면? 한 질문에서 좋아지고 다른 질문에서 나빠지면? 눈으로는
> 못 센다. **검색기가 나아졌는지 나빠졌는지를 숫자 하나로 말할 수 있어야** 한다. 그게 이 장의 일이다.
>
> Phase 4의 결과물은 새 검색 기능이 아니라 **자(ruler)** 다. "튜닝 전후 recall@k가 얼마→얼마"를
> 뽑아내는 평가 코드. 이 자는 이후 Phase 5(청킹·인덱스 튜닝)에서 바꾼 것이 개선인지 개악인지를
> 판정하는 데 그대로 쓰인다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "왜 '좋아진 느낌'으로는 안 되고 숫자로 재야 하나?"
- "골든 데이터셋이 뭔가? 왜 그게 있어야 점수를 낼 수 있나? 어떻게 만드나?"
- "recall@k, MRR, nDCG@k는 각각 무엇을 보나? 셋은 어떻게 다른가?"
- "정답이 4위면 recall@3, MRR, nDCG@3는 각각 얼마가 되나?"
- "우리 실측에서 하이브리드가 벡터보다 나은 게 맞나? 어디서 갈렸나?"
- "그럼 하이브리드는 항상 쓰는 게 맞나?"
- "생성(답변)의 품질은 왜 이 장에서 안 재나?"

## 1. 왜 평가가 필요한가 — "좋아진 느낌"으로는 모른다

검색기를 손보는 일은 계속 생긴다. 임베딩 모델을 바꾸고, 청킹 크기를 조절하고, 하이브리드를 켜고,
가중치를 튜닝한다. 매번 우리는 묻게 된다 — **"이거 정말 나아진 거야?"**

이 질문에 "느낌상 좋아진 것 같아"로 답하면 안 된다. 이유가 세 가지다.

- **느낌은 몇 개의 예시에만 기댄다.** 내가 방금 던져본 질문 두세 개에서 잘 나왔다고 전체가 좋아진 게
  아니다. 어떤 변경은 한쪽 질문을 살리면서 다른 쪽 질문을 죽인다(trade-off). 예시 몇 개로는 그
  손해가 안 보인다.
- **개선인지 개악인지 방향조차 모른다.** 재지 않으면 "바꿨더니 나빠졌다"를 배포하고 나서야 알게 된다.
  숫자가 있으면 배포 **전에** "recall@1이 0.83에서 0.79로 내려갔네, 이 변경은 되돌리자"를 판단한다.
- **비교의 기준이 없다.** A안과 B안 중 뭘 고를지, 어제 버전과 오늘 버전 중 뭐가 나은지 — 같은 자로
  잰 숫자가 있어야 비교가 된다.

그래서 이 장은 검색기에 **점수를 매기는 장치**를 만든다. 장치의 재료는 두 가지다: (1) 무엇이 정답인지
적어둔 **골든 데이터셋**(§2), (2) 검색 결과와 정답을 비교해 점수로 바꾸는 **지표**(§3). 이 둘이 있으면
검색기를 넣고 숫자를 뽑을 수 있고, 튜닝 전후를 같은 자로 비교할 수 있다(§4).

## 2. 골든 데이터셋 — 정답표(ground truth)

### (질문, 정답 문서 id) 짝

점수를 매기려면 "무엇이 맞는 답인지"가 먼저 정해져 있어야 한다. 그 정답표가 **골든 데이터셋**이다.
형식은 단순하다 — **질문 하나에, 그 질문에 대해 나와야 할 정답 문서의 id 목록**을 짝지어 둔다.

`golden.py`가 우리 정답표다. 검색 대상 문서 10개(`CORPUS`)와, 질문 6개의 정답표(`GOLDEN`)가 들어있다.

```python
GOLDEN = [
    ("E-402 문제가 발생했어요", ["err-402"]),
    ("E-403 이라고 나옵니다",   ["err-403"]),
    ("E-401 계속 떠요",         ["err-401"]),
    ("ZX-9 관련해서 궁금해요",  ["prod-zx9"]),
    ("돈 언제 돌려받아요",       ["faq-refund"]),
    ("교환하고 싶어요",         ["faq-exchange"]),
]
```

읽는 법: `"돈 언제 돌려받아요"`라고 물으면 `faq-refund` 문서가 나와야 정답이다. 우리 골든셋은 질문마다
정답이 **1개**지만, 형식은 리스트(`["err-402"]`)다 — 한 질문에 정답 문서가 여럿일 수도 있기 때문이다
(예: "환불 절차" 질문에 환불 관련 문단이 두세 개 다 맞는 답일 수 있다).

이 정답표는 **이진 관련성(binary relevance)** 을 쓴다. 어떤 문서는 정답이거나(1) 아니거나(0), 그
중간(0.5쯤 관련)은 없다. 우리 지표는 전부 이 이진 판정 위에서 계산한다.

### 골든셋은 어떻게 만드나

정답표는 하늘에서 안 떨어진다. 사람이 만든다. 실무에서 만드는 방법은 크게 둘이다.

- **수작업 라벨링** — 대표 질문들을 뽑아, 각 질문에 대해 우리 문서 중 무엇이 정답인지 사람이 직접
  붙인다. 우리 `golden.py`가 이 방식이다. 정확하지만 손이 많이 간다. 그래서 **적더라도 다양하게**
  만드는 게 요령이다 — 오류 코드처럼 정확한 토큰이 중요한 질문, "돈 언제 돌려받아요"처럼 동의어로
  물어보는 질문, 상품명 질문 등 **성격이 다른 케이스를 골고루** 넣어야 검색기의 약점이 드러난다.
- **실제 로그에서 뽑기** — 서비스가 돌고 있다면 사용자가 실제로 던진 질문 로그가 쌓인다. 그중 자주
  나오는 질문을 골라 정답을 붙이면, 현실 분포를 닮은 골든셋이 된다. 사용자가 정답 문서를 클릭했다거나
  "도움이 됐어요"를 눌렀다는 신호를 약한 정답 라벨로 쓰기도 한다.

크기 감각: 처음부터 완벽할 필요는 없다. **20~50개짜리 작은 골든셋도 없는 것보다 훨씬 낫다.**
우리처럼 6개로 시작해서, 검색이 틀리는 케이스가 보일 때마다 그 질문을 골든셋에 추가하며 키우면 된다.
골든셋은 한 번 만들고 끝이 아니라 **계속 자라는 자산**이다.

## 3. 검색 지표 3종 — recall@k · MRR · nDCG@k

검색기는 질문을 받아 문서를 **순위 매겨** 돌려준다(1위, 2위, 3위…). 지표는 이 순위 목록을 골든셋의
정답과 대조해 0~1 사이 점수로 바꾼다. 세 지표는 같은 순위 목록을 **서로 다른 관점**에서 본다.
`metrics.py`에 셋 다 구현돼 있다.

아래 세 지표는 전부 이 한 줄 예시로 설명한다: 정답이 `A` 하나인 질문에, 검색기가
`[B, A, C, D, E]`를 돌려줬다고 하자. **정답 A가 2위**다.

### 3.1 recall@k — 정답이 top-k 안에 들어왔나

가장 단순하다. **상위 k개 안에 정답이 몇 개나 들어왔는지**를, 정답 총 개수로 나눈다.

```
recall@k = (top-k 안에 든 정답 개수) / (정답 총 개수)
```

예시(`[B, A, C, D, E]`, 정답 `A`가 2위):
- `recall@1` → top-1은 `[B]`. `A`가 없다 → **0/1 = 0**
- `recall@3` → top-3은 `[B, A, C]`. `A`가 있다 → **1/1 = 1**

recall@k는 **위치를 안 본다.** top-3 안에만 있으면 그게 1위든 3위든 recall@3는 똑같이 1이다.
"놓쳤나, 안 놓쳤나"의 이진 질문이다. `k`를 바꿔가며 보면 "어느 깊이까지 봐야 정답이 잡히나"를 안다 —
recall@1은 "정답이 바로 1위인가", recall@3은 "top-3 안 어딘가엔 있는가".

```python
def recall_at_k(retrieved_ids, relevant_ids, k):
    top_k = retrieved_ids[:k]
    hit = 0
    for doc_id in relevant_ids:
        if doc_id in top_k:
            hit = hit + 1
    return hit / len(relevant_ids)
```

### 3.2 MRR — 첫 정답의 역순위

MRR(Mean Reciprocal Rank, 평균 역순위)은 **첫 번째 정답이 몇 위에 나왔는지**를 본다. 한 질문에서
첫 정답의 순위가 `r`이면 그 질문의 점수는 `1/r` — 이걸 **역순위(RR, Reciprocal Rank)** 라 한다.
1위면 `1/1 = 1.0`, 2위면 `1/2 = 0.5`, 4위면 `1/4 = 0.25`. 정답이 결과에 아예 없으면 0. 이 RR을
**전체 질문에 걸쳐 평균**낸 게 MRR이다. 즉 이름의 M(Mean)이 이 평균 단계다.

예시(`A`가 2위): 이 한 질문의 RR은 `r = 2` → **`1/2 = 0.5`**. 질문이 하나뿐이면 MRR도 그대로 0.5지만,
여러 질문이면 각 RR을 평균낸다 — 예컨대 두 질문이 1위·2위였다면 MRR = `(1.0 + 0.5) / 2 = 0.75`.

recall@k와 다른 점: MRR은 **위치를 본다.** 정답이 1위냐 3위냐에 따라 점수가 달라진다(1.0 vs 0.33).
"정답을 얼마나 위에 올렸나"에 상을 준다. 대신 **'첫' 정답 하나만** 본다 — 정답이 여러 개여도 두 번째,
세 번째 정답의 위치는 무시한다. 사용자가 보통 맨 위 결과부터 읽는다는 점에서, "첫 정답까지 얼마나
빨리 닿나"를 재는 지표다.

```python
def mrr(retrieved_ids, relevant_ids):
    for i in range(len(retrieved_ids)):
        rank = i + 1
        if retrieved_ids[i] in relevant_ids:
            return 1.0 / rank
    return 0.0
```

### 3.3 nDCG@k — 순위 가중 합, log2 할인

nDCG(normalized Discounted Cumulative Gain)는 **top-k 안 모든 정답의 위치를 순위 가중으로 합산**한다.
가중치는 아래쪽일수록 완만하게 깎인다 — 이 깎는 걸 log2 **할인(discount)** 이라 한다.

이름의 G는 **이득(gain)** — 그 자리 문서가 정답이면 얻는 점수다. §2에서 관련성을 이진(정답 1, 아니면
0)으로 정했으니, 우리 이득은 1 아니면 0뿐이다. 그래서 DCG는 "정답인 자리마다 할인값을 더한다"로 단순해진다.

먼저 DCG@k(할인 누적 이득)를 구한다. top-k를 훑으며, 그 자리가 정답이면 이득 1에 할인을 곱한
`1/log2(위치+1)`을 더한다(정답이 아니면 이득 0이라 더할 게 없다).

```
DCG@k = Σ (정답인 자리마다)  1 / log2(위치 + 1)     (위치는 1-based)
```

위치별 가중치를 펼치면: 1위 → `1/log2(2) = 1.0`, 2위 → `1/log2(3) ≈ 0.631`, 3위 → `1/log2(4) = 0.5`.
아래로 갈수록 값이 줄지만, MRR의 `1/r`(2위 0.5)보다 **덜 가파르게** 준다(2위 0.631).

DCG는 정답 개수에 따라 최대값이 달라져서 질문끼리 비교가 안 된다. 그래서 **IDCG**(정답들을 top-k 맨
위에 몰아넣었을 때 나오는 최선의 DCG)로 나눠 0~1로 정규화한다. 정답이 1개면 IDCG는 `1.0`(정답을 1위에
둔 경우)이다.

```
nDCG@k = DCG@k / IDCG@k
```

예시(`A`가 2위, 정답 1개, k=3): DCG@3 = `1/log2(2+1) = 1/log2(3) ≈ 0.631`. IDCG@3 = `1.0`.
→ **nDCG@3 ≈ 0.631**.

정답이 1개일 때는 식이 깔끔해진다: **정답이 순위 `r`(≤k)이면 nDCG@k = `1/log2(r+1)`**, `r`이 k보다
크면 0. nDCG가 MRR과 갈리는 진짜 지점은 **정답이 여러 개일 때** — nDCG는 그 정답들이 각각 얼마나 위에
분포하는지까지 합산해 반영한다. MRR은 첫 하나만 보고 끝낸다.

```python
def ndcg_at_k(retrieved_ids, relevant_ids, k):
    top_k = retrieved_ids[:k]

    dcg = 0.0
    for i in range(len(top_k)):
        position = i + 1
        if top_k[i] in relevant_ids:
            dcg = dcg + 1.0 / math.log2(position + 1)

    ideal_hits = len(relevant_ids)
    if ideal_hits > k:
        ideal_hits = k

    idcg = 0.0
    for i in range(ideal_hits):
        position = i + 1
        idcg = idcg + 1.0 / math.log2(position + 1)

    if idcg == 0.0:
        return 0.0
    return dcg / idcg
```

### 세 지표를 나란히 — 정답 1개짜리 질문의 순위별 점수

우리 골든셋은 질문마다 정답이 1개다. 이 경우 **한 질문의** 세 지표는 전부 첫 정답의 순위 `r` 하나로
결정된다(아래 표는 질문 하나짜리 값이라, MRR 자리에는 그 평균 전 값인 RR을 적는다). `r`을 바꿔가며
셋이 어떻게 움직이는지 보면 성격 차이가 한눈에 들어온다.

| 첫 정답 순위 r | recall@1 | recall@3 | RR (=1/r) | nDCG@3 (=1/log2(r+1)) |
| --- | --- | --- | --- | --- |
| 1위 | 1 | 1 | 1.000 | 1.000 |
| 2위 | 0 | 1 | 0.500 | 0.631 |
| 3위 | 0 | 1 | 0.333 | 0.500 |
| 4위 | 0 | 0 | 0.250 | 0 (top-3 밖) |
| 5위 | 0 | 0 | 0.200 | 0 (top-3 밖) |

읽는 법:
- **recall@1**은 "1위인가"만 본다(1위만 1, 나머지 0). **recall@3**은 "top-3 안인가"만 본다(1~3위 1,
  4위부터 0) — 3위든 1위든 구분 없이 1.
- **RR**(1/r)은 순위가 내려갈수록 계속 점수를 깎는다. recall@3의 절벽(3위까지 1, 4위 0)과 달리
  매끄럽게 준다. 단, RR엔 k 컷오프가 없다 — 우리 코드는 검색 상위 5개를 대상으로 재므로 4위 정답도
  `0.25`로 잡힌다(5위 밖이면 0). 이 RR을 질문마다 구해 평균낸 것이 MRR이다.
- **nDCG@3**은 MRR처럼 위치를 보되 **더 완만하게** 깎고(2위 0.631 vs MRR 0.5), recall처럼 **k에서
  잘린다**(4위부터 0). MRR과 recall@k의 성격을 섞은 모양이다.

주의: 이 표는 정답이 **1개**라서 셋이 나란히 움직이는 것이다. 정답이 여러 개인 질문에서는 recall(몇
개나 담겼나)·MRR(첫 정답 위치)·nDCG(정답들의 분포)가 서로 다른 값을 준다. 그래서 셋을 다 본다.

| E-401 계속 떠요 | err-401 | 1위 | 1위 |
| ZX-9 관련해서 궁금해요 | prod-zx9 | 1위 | 1위 |
| 돈 언제 돌려받아요 | faq-refund | 1위 | 1위 |
| 교환하고 싶어요 | faq-exchange | 1위 | 1위 |

6개 중 **딱 한 질문(E-402)에서만 갈렸다.** 순수 벡터는 E-402를 4위로 밀었고(Phase 3 §4에서 본 바로 그
현상 — `E-401`·`E-402`·`E-403`·`E-404`가 의미로는 거의 같아 벡터가 못 가린다), 하이브리드는 키워드
신호(`E-402` 정확 토큰)를 얹어 1위로 올렸다. 나머지 5개는 두 검색기 모두 1위라 차이가 없다.

### 지표 표

위 순위들을 §3의 지표로 요약하면 이렇게 된다.

| 지표 | 순수 벡터 | 하이브리드 |
| --- | --- | --- |
| recall@1 | **0.833** | **1.000** |
| recall@3 | 0.833 | 1.000 |
| MRR | **0.875** | **1.000** |
| nDCG@3 | 0.833 | 1.000 |

숫자가 어디서 나왔는지 손으로 따라가 보자(정답 5개는 1위, E-402만 4위).

- **recall@1 = 0.833** — 6개 중 5개가 정답을 1위로 냈다 → `5/6 = 0.833`. E-402만 1위가 아니라 실패.
- **recall@3 = 0.833** — recall@1과 같다. E-402는 **4위**라 top-3에도 못 든다. 즉 k를 1에서 3으로
  넓혀도 E-402는 여전히 못 잡는다 — 이 실패는 하이브리드로만 풀린다.
- **MRR = 0.875** — 정답 5개는 `1/1 = 1.0`, E-402는 `1/4 = 0.25`. `(1.0×5 + 0.25) / 6 = 5.25/6 = 0.875`.
- **nDCG@3 = 0.833** — 정답 5개는 `1.0`, E-402는 4위(>3)라 `0`. `(1.0×5 + 0) / 6 = 5/6 = 0.833`.

하이브리드 쪽은 6개 전부 1위라 네 지표 모두 **1.000**이다.

읽는 법: **모든 지표가 하이브리드에서 올랐다.** recall@1이 `0.833 → 1.000`, MRR이 `0.875 → 1.000`.
그리고 표의 모든 상승분은 **오직 E-402 한 질문**에서 나왔다. 다른 5개는 이미 만점이라 더 오를 데가
없었다. "튜닝 전후 recall@k 0.83 → 1.0" — 이게 이 장이 뽑아내려던 개선 리포트의 실체다.

## 5. 정직한 해석 — bge-m3는 이미 강하다

숫자만 보면 "하이브리드가 벡터를 모든 지표에서 이겼다, 하이브리드가 정답이다"로 읽기 쉽다. 하지만 표를
정직하게 읽으면 결론이 좀 더 조심스럽다.

- **bge-m3(좋은 다국어 임베딩)는 이미 대부분을 1위로 맞힌다.** 6개 중 5개는 순수 벡터만으로도 정답이
  바로 1위였다. "돈 언제 돌려받아요 → 환불"처럼 단어가 안 겹치는 동의어 질문도 벡터가 잘 잡는다.
  그게 좋은 임베딩의 힘이다.
- **하이브리드가 살린 건 단 하나, exact-token 케이스다.** 개선은 전부 E-402에서 왔다. 벡터가 원리적으로
  약한 자리(코드·SKU처럼 정확한 토큰이 곧 정답인 것)를 키워드가 메운 것이지, 하이브리드가 전반적으로
  더 똑똑해서가 아니다.
- **그래서 "하이브리드가 항상 낫다"는 착각일 수 있다.** 하이브리드는 공짜가 아니다 — 키워드 검색을
  한 번 더 돌리고 순위를 합치는 비용이 든다. 우리 데이터에선 exact-token 질문이 있어서 그 비용이
  값어치를 했지만, 정확 토큰이 거의 없는 코퍼스라면 벡터가 이미 다 맞혀서 하이브리드가 **아무것도
  못 올리고 비용만 더할** 수도 있다. 심지어 키워드가 엉뚱한 문서를 끌어올려 **점수를 깎는** 경우도
  있다.

여기서 이 장의 핵심 교훈이 나온다. **개선인지 아닌지는 반드시 '측정'해야 안다.** "하이브리드가 좋다더라"
같은 일반론이 아니라, 내 데이터·내 골든셋에 대고 재 봐서 recall@1이 `0.83 → 1.0`으로 올랐다는 숫자를
확인했기 때문에 우리는 "이 경우엔 하이브리드가 낫다"고 말할 수 있다. 다른 데이터에선 반대일 수도 있고,
그건 또 재 봐야 안다. **그게 평가가 존재하는 이유다** — 어떤 기법이 좋은지 미리 정해진 답은 없고,
매번 자로 재서 확인하는 것.

## 6. 생성 평가(RAGAS 등)는 왜 여기서 안 하나

RAG의 평가는 크게 두 층이다. Phase 4는 그중 **검색 층**만 다뤘다.

- **검색 평가(retrieval)** — "질문에 맞는 문서를 잘 골라왔나?" 정답 문서 id라는 명확한 ground truth가
  있고, 검색 결과와 대조하면 recall/MRR/nDCG가 기계적으로 나온다. **LLM이 필요 없다.** 이게 Phase 4다.
- **생성 평가(generation)** — "그 문서로 만든 **답변**이 좋은가?" 여기엔 정답 문자열이 딱 하나로
  정해지지 않는다. 같은 뜻을 여러 문장으로 쓸 수 있으니 단순 문자열 비교로는 못 잰다. 그래서 답변의
  품질을 **또 다른 LLM에게 판정시킨다**(LLM-as-a-judge). RAGAS 같은 도구가 이걸 자동화한다.

RAGAS의 대표 지표는 무엇을 보느냐에 따라 두 갈래다.

- 답변 자체를 보는 것:
  - **faithfulness(충실도)** — 답변이 검색해온 문서에 실제로 근거하나, 아니면 지어냈나(환각).
  - **answer relevancy** — 답변이 질문에 실제로 대답하나.
- 검색해온 문맥을 보는 것(문맥 품질이라 층으로는 retrieval에 가깝지만, 판정에 LLM이나 참조 답변이 든다):
  - **context precision** — 검색된 문맥 중 실제로 쓸모 있는 것이 위쪽에 잘 배치됐나(순위 품질).
  - **context recall** — 정답에 필요한 내용이 검색된 문맥에 다 담겼나.

recall@k처럼 문맥 품질을 재는데도 이들을 Phase 4에서 못 돌리는 이유는, 판정 기준이 "정답 문서 id"가
아니라 **참조 답변**이고 그 대조를 **LLM이** 하기 때문이다. faithfulness·answer relevancy는 애초에
**답을 생성하는 LLM이 파이프라인에 붙어 있어야** 잴 수 있다. 우리 파이프라인엔 아직 LLM이 없다(검색기
까지만 만들었다). LLM은 **Phase 6(RAG 파이프라인 & LLM 결합)** 에서 붙인다.

참고로 이 커리큘럼의 Phase 4 계획에도 생성 지표(RAGAS: faithfulness, context precision/recall)가
적혀 있다. 다만 위 이유로 **개념만 여기서 소개하고 실측은 Phase 6 이후로 미룬다.** Phase 4는 LLM
없이도 재는 **검색 평가에 집중**한다 — 애초에 답변이 좋으려면 검색이 먼저 맞는 문서를 물어와야 하니,
이 층을 단단히 재는 게 먼저다.

## 7. 파일 구조 & 설치·실행

### 파일 구조 — 역할별로 나눴다

이번엔 한 파일에 몰지 않고 역할별로 4개로 나눴다. 평가 코드는 "데이터 / 지표 / 검색기 / 실행"이
자연스럽게 분리되기 때문이다.

| 파일 | 역할 |
| --- | --- |
| `golden.py` | **데이터.** 검색 대상 문서 10개(`CORPUS`)와 정답표 6개(`GOLDEN`). 순수 데이터라 로직이 없다. |
| `metrics.py` | **지표.** `recall_at_k` · `mrr` · `ndcg_at_k` 세 함수. 순위 목록과 정답을 받아 점수를 낸다. 검색기·DB를 모른다(순수 계산). |
| `search.py` | **검색기.** `vector_search`(순수 벡터)와 `hybrid_search`(Phase 3의 RRF 결합). 컬렉션과 질문을 받아 순위 매긴 id 목록을 낸다. |
| `main.py` | **실행.** 위 셋을 엮는다 — 코퍼스 적재 → 두 검색기를 골든셋으로 평가 → 지표 계산 → 전후 비교 출력. |

이렇게 나누면 지표를 고칠 때 `metrics.py`만, 검색기를 바꿀 때 `search.py`만 건드리면 된다. `metrics.py`는
검색기나 DB를 전혀 모르기 때문에, 나중에 다른 검색 파이프라인이 와도 지표 코드는 그대로 재사용된다.

### 설치

이 폴더(`phase-4-evaluation`)에서:

```bash
python3 -m venv .venv
source .venv/bin/activate        # 새 터미널을 열 때마다 이 줄로 활성화
pip install -r requirements.txt  # chromadb, ollama 설치
```

Ollama와 `bge-m3` 모델은 Phase 0에서 준비했다. 안 돼 있다면 `brew services start ollama`로 서버를 켜고
`ollama pull bge-m3`로 모델을 받으면 된다. `main.py`가 실행 첫머리(`check_ollama`)에서 이 둘을 자동
점검하고, 빠졌으면 무엇을 하면 되는지 알려준다.

### 실행

```bash
python main.py
```

- 실행하면 이 폴더에 `./chroma_db` 폴더가 생긴다(벡터가 파일로 저장되는 자리).
- 스크립트는 매 실행마다 `phase4_eval` 컬렉션을 지웠다 새로 만든다(`reset_collection`). 항상 깨끗한
  상태에서 같은 숫자를 재현하기 위해서다.
- 지표 값은 모델·환경에 따라 소수점 아래가 약간 달라질 수 있으나, **E-402가 순수 벡터에선 top-3 밖,
  하이브리드에선 1위**라는 방향은 그대로다. 그래서 recall@1 `0.833 → 1.000`의 개선도 그대로 재현된다.

## 8. `main.py`가 보여주는 것 — [1]~[5] 지도

스크립트는 먼저 **Ollama 서버와 `bge-m3` 모델을 점검**(`check_ollama`)한 뒤, 아래 5단계를 차례로 찍는다.
각 단계가 위 개념 어디에 대응하는지 정리하면 이렇다.

| 단계 | 화면 제목 | 하는 일 | 대응 절 |
| --- | --- | --- | --- |
| **[1]** | 준비 & 코퍼스 적재 | `golden.CORPUS` 10개 문서를 컬렉션에 넣음 | §2·§7 |
| **[2]** | 골든셋 소개 | `golden.GOLDEN` 6개 (질문, 정답 id) 짝을 출력 | §2 |
| **[3]** | 평가: 순수 벡터 | 6개 질문을 `vector_search`로 → 질문별 첫 정답 순위 + 지표 4종 | §3·§4 |
| **[4]** | 평가: 하이브리드 | 같은 6개를 `hybrid_search`로 → 순위 + 지표 4종 | §3·§4 |
| **[5]** | 튜닝 전후 비교 | 두 지표를 나란히 표로, 어디서 갈렸는지(E-402), 정직한 해석 | §4·§5 |

### 평가 루프의 뼈대 — `evaluate`

[3]·[4]가 부르는 `evaluate(col, search_fn)`가 이 스크립트의 알맹이다. 하는 일은 단순하다.

```python
# 골든셋 질문을 하나씩 돌면서:
#   retrieved = search_fn(col, question, k=5)      # 검색기로 상위 5개를 받고
#   recall@1, recall@3, MRR, nDCG@3 을 각각 계산해   # metrics.py의 세 함수로 점수를 내고
#   질문별 '첫 정답 순위'도 기록                      # 어디서 맞고 틀렸는지 보려고
# 마지막에 지표들을 질문 수로 평균낸다
```

여기서 검색기(`search_fn`)를 **인자로 받는다**는 게 핵심이다. 같은 평가 루프에 `vector_search`를 넣으면
[3]이, `hybrid_search`를 넣으면 [4]가 된다. 검색기만 바꿔 끼우면 같은 자로 잰 숫자가 나오니, 공정한
비교가 된다. 나중에 어떤 검색기를 만들어도 이 루프에 넣기만 하면 평가된다.

### [5] 출력, 이렇게 읽는다

```
지표            순수 벡터   하이브리드
  recall@1     0.833       1.000
  ...
어떤 질문에서 갈렸는가:
  - E-402 문제가 발생했어요 : 벡터 4위 -> 하이브리드 1위
```

- 위 표는 §4의 지표 표 그대로. 두 검색기를 같은 골든셋으로 재서 나란히 놓은 것.
- "어떤 질문에서 갈렸는가"는 두 검색기의 순위가 **다른 질문만** 추려 보여준다. 우리 경우 E-402 하나뿐 —
  개선의 출처가 어디인지 한 줄로 드러난다.
- 그 아래 "정직한 해석"이 §5의 결론(bge-m3가 이미 강하고, 하이브리드는 exact-token 하나를 살렸을 뿐,
  개선 여부는 측정해야 안다)을 찍는다.

## 9. Phase 4 완료 체크리스트

- [ ] "좋아진 느낌"으로는 왜 안 되는지(예시 편향·방향 모름·기준 없음) 설명할 수 있다.
- [ ] 골든 데이터셋이 (질문, 정답 문서 id) 짝의 ground truth임을 알고, 만드는 두 방법(수작업·로그)을 말할 수 있다.
- [ ] recall@k가 "top-k 안에 정답이 들었나"의 이진 지표이고 위치를 안 본다는 걸 안다.
- [ ] MRR이 "첫 정답의 역순위(1/r)" 평균이고 위치에 상을 주는 걸 안다.
- [ ] nDCG@k가 log2 할인으로 순위 가중 합을 내고 IDCG로 정규화하는 걸 안다. 정답 1개면 `1/log2(r+1)`(r≤k)임을 안다.
- [ ] 정답이 4위일 때 recall@3=0, MRR=0.25, nDCG@3=0이 되는 이유를 각각 설명할 수 있다.
- [ ] 실측에서 recall@1 `0.833→1.0`, MRR `0.875→1.0`이 나온 계산(5/6, 5.25/6)을 따라갈 수 있다.
- [ ] 개선이 전부 E-402 한 질문(벡터 4위→하이브리드 1위)에서 나왔다는 걸 표로 짚을 수 있다.
- [ ] "하이브리드가 항상 낫다"가 왜 착각일 수 있는지, 왜 매번 측정해야 하는지 말할 수 있다.
- [ ] 생성 평가(RAGAS/faithfulness)는 LLM 판정이 필요해 Phase 6 이후임을 안다.
- [ ] `python main.py`를 돌려 [1]~[5]와 위 숫자들을 직접 확인했다.

전부 체크됐다면 검색기에 점수를 매기는 자가 손에 들어온 것이고, 이 자를 들고 **Phase 5(청킹 심화 &
인덱스 튜닝)** 로 넘어갈 준비가 된 것이다. Phase 5부터는 무언가를 바꿀 때마다 이 자로 재서 개선인지
확인한다.
