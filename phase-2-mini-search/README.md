# Phase 2 — 유사도 검색 & 미니 검색기

> Phase 1에서 `query`로 의미 검색을 하고 결과에 딸려 오는 **거리(distance)** 까지 봤다.
> Phase 2에서는 두 가지를 붙인다.
> ① 긴 문서를 **청킹(chunking)** 으로 잘게 쪼개 검색 정확도를 끌어올리고,
> ② 그 거리 점수를 **"관련 있음 / 없음"으로 판정**하는 규칙(threshold)을 세운다.
> 이 둘을 합치면 검색기 함수 `search()` 하나가 되고, 그게 Phase 2의 결과물이다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "왜 긴 문서를 통짜로 임베딩하면 안 되나? 청킹이 뭘 해결하나?"
- "거리 0.27은 좋은 점수인가 나쁜 점수인가? 어떻게 판단하나?"
- "무관한 질문(문서에 답이 없는 질문)을 어떻게 걸러내나?"
- "threshold(경계선)는 어떻게 정하나? 왜 코드에 박힌 상수가 정답이 아닌가?"
- "청크를 너무 크게/작게 나누면 각각 뭐가 문제인가?"

---

## 1. 복습, 그리고 이번에 풀 두 물음

Phase 1에서 `query`를 던지면 이런 게 돌아왔다.

```python
result = collection.query(query_texts=["환불 언제 돼요?"], n_results=3)
result["distances"][0]   # [0.21, 0.44, 0.58] 같은 거리 리스트
```

거리는 **낮을수록 가깝다**(코사인 거리 = 1 − 코사인 유사도). 여기까지는 배웠다.
그런데 실제로 검색기를 만들려니 두 가지가 막힌다.

- **물음 ①** — 1위 거리가 `0.44`로 나왔다고 하자. **이게 좋은 건가?** 관련 문서를 잘 찾은 건지,
  아니면 억지로 가장 가까운 걸 하나 집어준 것뿐인지, 숫자만 봐서는 모른다.
- **물음 ②** — Phase 1의 FAQ는 문단 하나가 문서 하나였다. 그런데 현실 문서는 **길다.**
  배송·교환·멤버십·영업시간·환불이 **한 문서에 다 들어있으면** 어떻게 검색하나?

이 장은 이 두 물음에 답한다. ②는 **청킹**으로(§2), ①은 **threshold**로(§3).

---

## 2. 청킹(chunking)이 필요한 이유

### 통짜로 임베딩하면 의미가 뭉개진다

임베딩은 텍스트 한 덩어리를 **하나의 벡터(좌표 하나)** 로 바꾼다. 짧고 주제가 하나면 그 좌표가
그 뜻을 또렷하게 가리킨다. 그런데 **여러 주제가 섞인 긴 문서**를 통째로 넣으면, 그 하나의 벡터는
여러 주제를 **한 자리에 뭉뚱그린** 흐릿한 좌표가 된다. 배송도 조금, 환불도 조금, 멤버십도 조금 —
어느 쪽도 선명하지 않다. 여기서 "뭉뚱그린다"는 비유이지 계산이 아니다. 조각 벡터 5개를 산술
평균한 값이 나오는 게 아니라, 모델이 문서 전체를 한꺼번에 읽어 여러 주제를 한 벡터에 담다 보니
어느 쪽도 또렷하지 않게 흐려지는 것이다.

그러면 두 가지가 나빠진다.

1. **원하는 부분만 못 준다.** 문서가 통짜 하나뿐이니, 검색 결과로 줄 수 있는 것도 **문서 전체**뿐이다.
   "환불 문단만 딱" 돌려줄 수가 없다. 통짜인 이상 **늘** 생기는 손해다.
2. **거리도 뜨기 쉽다.** "환불 며칠 걸려요?"라고 물어도, 문서 벡터가 여러 주제를 뭉뚱그린 흐린
   좌표라 환불 쪽으로 딱 붙지 못하는 경향이 있다. 다만 이 쪽은 질문·데이터에 따라 폭이 들쭉날쭉해서
   (1)만큼 확실한 손해는 아니다.

### 쪼개면 각 조각이 뚜렷한 의미가 된다

문서를 주제 단위(여기서는 문단)로 나눠 **각 조각을 따로 저장**하면, 조각마다 벡터가 하나씩 생긴다.
환불 문단은 환불 좌표에, 배송 문단은 배송 좌표에 또렷하게 찍힌다. 질문이 오면 **그 조각만 콕 집어**
돌려줄 수 있고, 거리도 대개 더 낮게(더 가깝게) 나온다.

`main.py`의 청킹은 특별할 게 없다. **빈 줄(`\n\n`) 기준으로 문단을 나누는** 게 전부다.

```python
def split_into_paragraphs(text):
    raw_chunks = text.split("\n\n")
    chunks = []
    for chunk in raw_chunks:
        cleaned = chunk.strip()
        if cleaned:
            chunks.append(cleaned)
    return chunks
```

### 코드로 직접 대비 — [2] 통짜 vs [3] 청킹

`main.py`는 같은 질문 **"환불은 며칠 걸리나요?"** 를 두 방식으로 검색해 나란히 보여준다.

- **[2] 통짜**: 문서 전체를 `document` **한 개**로 저장하고 검색.
- **[3] 청킹**: 문단 5개를 각각 저장하고 검색.

이 환경에서 관측된 결과다(거리 값은 모델·데이터에 따라 조금씩 달라진다).

| | 저장 방식 | 1위로 돌려준 것 | 1위 거리 |
| --- | --- | --- | --- |
| **[2] 통짜** | 문서 전체 1개 | 문서 **전체**(5개 주제 통째로) | `0.2670` |
| **[3] 청킹** | 문단 5개 | **환불 문단만** (`chunk-5`) | `0.2154` |

두 가지가 좋아졌는데, 무게가 다르다.

- **정확히 환불 문단만** 1위로 나온다. 이게 청킹의 **결정적 이득**이다 — 통짜는 줄 게 문서 전체뿐이었다.
- 거리도 `0.2670 → 0.2154`로 낮아졌다(더 가까워졌다). 벡터가 환불 하나만 가리키니 대개 이렇게
  되지만, 폭은 이번처럼 소폭(약 0.05)일 때가 많고 질문에 따라 들쭉날쭉하다. 늘 믿을 이득은 위의
  "환불 문단만 반환" 쪽이다.

> ⚠️ 거리 값은 **같은 질문 안에서** 통짜와 청킹을 나란히 견주는 숫자다. 서로 **다른 질문**의 거리끼리
> 직접 비교하면 안 된다. 예컨대 통짜 `0.2670`이 뒤 §3의 교환 질문 1위 거리 `0.3206`보다 낮다고 해서
> "통짜가 교환보다 낫다"는 뜻이 아니다. 질문이 다르면 거리의 출발선 자체가 달라지기 때문이다.

> 💡 통짜 검색이 돌려준 "문서 전체"의 앞부분은 공교롭게 배송 문단으로 시작한다. 하지만 그건
> 그냥 **문서의 맨 앞**일 뿐, 환불을 찾아준 게 아니다. 통짜 컬렉션에는 애초에 나눠줄 조각이 없다.

## 3. 거리 점수 해석 — threshold로 "관련 있음/없음" 판정

### 거리에는 절대 기준선이 없다

`0.2154`는 가깝고 `0.6330`은 멀다 — 이 정도는 상대 비교로 안다. 하지만 **"거리 0.4면 관련 있는 건가?"**
같은 절대 판정은 숫자 하나만 봐서는 못 한다. 왜냐하면 거리의 스케일은 **임베딩 모델과 데이터에 따라
달라지기** 때문이다. 어떤 모델은 관련 문서가 0.1대, 어떤 모델은 0.4대에서 나온다. **"0.3 미만이면 관련"**
같은 만고불변의 기준선은 존재하지 않는다.

### 그래서 threshold를 경험적으로 정한다

대신 우리가 관측할 수 있는 건 **경향**이다. **관련 있는 질문은 거리가 낮게, 무관한 질문은 높게** 나온다.
그 사이 어딘가에 선을 하나 그으면 "이보다 가까우면 관련, 멀면 무관"이라고 **판정**할 수 있다. 그 선이
threshold다. `main.py`는 상수 하나로 둔다.

```python
DISTANCE_THRESHOLD = 0.55
```

이 값은 **하늘에서 떨어진 정답이 아니다.** 이 문서·이 모델(bge-m3)로 여러 질문을 돌려보고,
관련 질문 무리와 무관 질문 무리 사이에 손으로 그은 선이다. 이 환경의 관측값을 보면 왜 0.55인지 보인다.

| 질문 | 성격 | 1위 거리 | 0.55 기준 판정 |
| --- | --- | --- | --- |
| 환불은 며칠 걸리나요? | 관련 | `0.2154` | 관련 있음 ✅ |
| 교환하려면 어떻게 하나요? | 관련 | `0.3206` | 관련 있음 ✅ |
| 로켓 발사 절차를 알려줘 | 무관 | `0.6330` | 관련 없음 ❌ |

관련 질문은 `0.2~0.36`, 무관 질문은 `0.63` 위에서 나왔다. 그 사이 빈 구간에 `0.55`를 그은 것이다.
데이터나 모델이 바뀌면 이 무리들의 위치가 통째로 움직이고, threshold도 다시 잡아야 한다.

### 무관 질문 걸러내기 — [4]에서 하는 일

이 판정의 진짜 쓸모는 **"문서에 답이 없는 질문을 없다고 말하는 것"** 이다. 벡터 검색은 무조건 가장
가까운 문서를 하나 돌려준다 — 심지어 "로켓 발사 절차"를 물어도 배송 문단을 1위로 내민다(거리 `0.6330`).
threshold가 없으면 이 엉뚱한 문단을 답이라고 우길 판이다. threshold를 넘으면 **"관련 문서 없음"** 이라고
잘라주는 게 [4]가 하는 일이다.

> ⚠️ threshold는 **딱 떨어지는 경계가 아니다.** 위 관측에서 "교환" 질문의 2위는 환불 문단이고 거리가
> `0.4982`였다 — 0.55보다 낮아 "관련 있음" 쪽이다. 실제로 교환과 환불은 주제가 닿아 있으니 억지는
> 아니다. 경계 근처(0.5 안팎)의 문서는 애매할 수 있다는 것, 그래서 threshold는 **칼이 아니라 눈금**
> 이라는 감각을 갖는 게 중요하다.

## 4. 미니 검색기(v1)의 구조 — `search()`

§2(청킹)와 §3(거리 판정)을 하나로 합치면 재사용 가능한 함수가 된다. `main.py`의 `search()`다.
하는 일은 세 가지 — **임베딩 검색 → 진단 출력 → 거리 해석(판정)**. (코드도 이 순서 그대로다.)

```python
def search(collection, query, k):
    print("  질문: %s" % query)

    # (1) 임베딩 검색 — 질문을 던지면 Chroma가 자동 임베딩해 가까운 k개를 준다
    result = collection.query(query_texts=[query], n_results=k)
    result_docs = result["documents"][0]
    result_distances = result["distances"][0]

    # (2) 진단 출력 — 순위·거리·문단을 눈으로 확인
    for rank in range(len(result_docs)):
        print("    %d위 | 거리 %.4f" % (rank + 1, result_distances[rank]))
        print("         %s" % result_docs[rank])

    # (3) 거리 해석 — 1위 거리를 threshold와 비교해 판정
    top_distance = result_distances[0]
    print("  1위 거리 %.4f  (기준 threshold %.2f)" % (top_distance, DISTANCE_THRESHOLD))
    if top_distance < DISTANCE_THRESHOLD:
        print("  판정: 관련 문서를 찾았습니다.")
        print("        답이 될 문단 -> %s" % result_docs[0])
    else:
        print("  판정: 관련 문서를 찾지 못했습니다. (문서에 없는 내용으로 보입니다)")
```

읽는 순서는 이렇다.

1. **검색** — `collection.query(...)`로 가까운 `k`개를 받는다. 반환이 질문별로 한 겹 감싸져 있으니
   `[0]`으로 벗겨 쓴다(Phase 1에서 본 그대로).
2. **진단** — 각 순위의 거리와 문단을 그대로 찍는다. 사람이 "왜 이게 1위지?"를 눈으로 확인하는 용도다.
3. **판정** — **1위 거리 하나만** threshold와 비교한다. 넘지 않으면 그 1위 문단을 답으로 내밀고,
   넘으면 "관련 문서 없음"이라고 답한다.

> 💡 이게 RAG의 **R(검색)** 부분의 뼈대다. 지금은 찾은 문단을 `print`로 보여줄 뿐이지만, 뒤 Phase에서
> 이 "답이 될 문단"을 LLM 프롬프트에 넣어주면 **G(생성)** 로 이어진다. Phase 2의 `search()`는 그
> 앞단을 미리 세워둔 것이다.

## 5. 청킹 트레이드오프 — 맛보기

"그럼 잘게 쪼갤수록 좋은가?" 아니다. 청크 크기에는 **양쪽으로 손해**가 있다.

- **너무 크게** 자르면 — §2에서 본 문제 그대로다. 한 조각에 여러 주제가 섞여 벡터가 뭉개진다.
- **너무 작게** 자르면 — 이번엔 **문맥이 끊긴다.** 예컨대 환불 문단을 문장 단위로 더 쪼개면
  "왕복 배송비는 고객님이 부담하십니다"라는 조각만 검색될 수 있는데, 이게 **무엇의** 배송비인지
  (환불? 교환?) 그 조각만 봐서는 모른다. 답에 필요한 맥락이 옆 조각으로 떨어져 나간 것이다.

그래서 청크 크기는 **뭉개짐과 문맥 손실 사이의 균형**을 잡는 문제다. `main.py`는 가장 단순한 선택
(문단 단위)을 썼고, 이 문서에는 그게 잘 맞았다.

> 🔧 조각 사이를 조금씩 **겹쳐 잘라(overlap)** 문맥 손실을 줄이는 기법, 문장·토큰 기준의 더 정교한
> 청킹 전략은 **Phase 5**에서 다룬다. 지금은 "청크 크기가 검색 품질을 좌우하는 손잡이"라는 감각만
> 챙기면 된다.

## 6. 설치 & 실행

### 1) 가상환경 & 패키지 설치

이 폴더(`phase-2-mini-search`)에서:

```bash
python3 -m venv .venv
source .venv/bin/activate        # 새 터미널을 열 때마다 이 줄로 활성화
pip install -r requirements.txt  # chromadb, ollama 설치
```

Ollama와 `bge-m3` 모델은 Phase 0에서 준비했다. 안 돼 있다면 `brew services start ollama`로 서버를
켜고 `ollama pull bge-m3`로 모델을 받으면 된다. `main.py`가 실행 첫머리(`check_ollama`)에서 이 둘을
자동 점검하고, 빠졌으면 무엇을 하면 되는지 알려준다.

### 2) 실행

```bash
python main.py
```

### 3) 무슨 일이 일어나나

- 첫 실행이 끝나면 이 폴더에 **`./chroma_db` 폴더가 생긴다**(벡터가 파일로 저장되는 자리).
- 스크립트는 매 실행마다 `whole`·`chunks` 컬렉션을 **지웠다 새로 만든다**(`reset_collection`). 지난
  실행에서 남은 데이터 없이, 항상 깨끗한 상태에서 [2]·[3]을 비교해 보여주기 위해서다.

## 7. `main.py`가 보여주는 것 — [1]~[4] 지도

스크립트는 먼저 **Ollama 서버와 `bge-m3` 모델을 점검**(`check_ollama`)한 뒤, 아래 4단계를 차례로
재현한다. 각 단계가 위 개념 어디에 대응하는지 정리하면 이렇다.

| 단계 | 화면 제목 | 하는 일 | 대응 개념 |
| --- | --- | --- | --- |

### [4] 출력, 이렇게 읽는다

```
  (가) 관련 질문:
  질문: 교환하려면 어떻게 하나요?
    1위 | 거리 0.3206
         교환은 상품에 하자가 있거나 ...
    2위 | 거리 0.4982
         환불은 상품을 받으신 후 ...
  1위 거리 0.3206  (기준 threshold 0.55)
  판정: 관련 문서를 찾았습니다.
        답이 될 문단 -> 교환은 상품에 하자가 있거나 ...

  (나) 무관 질문:
  질문: 로켓 발사 절차를 알려줘
    1위 | 거리 0.6330
         주문하신 상품은 결제가 완료되면 ...
    2위 | 거리 0.6714
         교환은 상품에 하자가 있거나 ...
  1위 거리 0.6330  (기준 threshold 0.55)
  판정: 관련 문서를 찾지 못했습니다. (문서에 없는 내용으로 보입니다)
```

(문단 본문은 지면상 `...` 으로 줄였다. 실제로는 각 문단 전체가 그대로 출력된다.)

- **(가) 관련 질문**은 1위 거리가 `0.3206`으로 threshold `0.55` 아래 → "관련 있음", 교환 문단을 답으로 내민다.
- **(나) 무관 질문**은 벡터 검색이 억지로 배송 문단을 1위로 주지만(2위 교환 문단도 `0.6714`로 멀다),
  1위 거리가 `0.6330`으로 threshold를 넘음 → "관련 문서 없음"으로 잘라낸다. threshold로 이렇게 무관
  질문을 잘라내는 동작이 바로 [4]가 존재하는 이유다.

## 8. Phase 2 완료 체크리스트

- [ ] 긴 문서를 통짜로 임베딩하면 왜 의미가 뭉개지는지(여러 주제를 한 벡터에 뭉뚱그려서) 설명할 수 있다.
- [ ] 청킹이 무엇을 해결하는지(조각별 뚜렷한 벡터 + 원하는 조각만 반환) 설명할 수 있다.
- [ ] `[2]` 통짜와 `[3]` 청킹의 결과 차이(결정적 이득은 정확한 문단 반환, 거리는 대개 소폭 감소)를 직접 돌려서 봤다.

- [ ] threshold를 **경험적으로**(관련/무관 무리 사이에) 정한다는 걸 알고, `0.55`가 왜 그 자리인지 설명할 수 있다.
- [ ] 무관한 질문을 threshold로 **"관련 문서 없음"** 이라고 잘라내는 이유와 방법을 안다.
- [ ] `search()`가 하는 세 가지(임베딩 검색 → 진단 출력 → 거리 해석)를 내 말로 설명할 수 있다.
- [ ] 청크를 너무 크게/작게 나눌 때의 손해(뭉개짐 / 문맥 손실)를 각각 안다.
- [ ] `python main.py`를 돌려 `[1]`~`[4]`를 확인했다.
