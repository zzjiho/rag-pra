# Phase 1 — ChromaDB 기본기

> Phase 0에서는 문서들을 **파이썬 리스트에 담아 손으로 전수 비교**해서 의미 검색을 했다.
> Phase 1에서는 그 일을 **진짜 벡터 DB(ChromaDB)** 에게 맡긴다.
> 이 장이 끝나면 "문서를 넣고, 꺼내고, 고치고, 지우고, 뜻으로 검색하는" 벡터 저장소를
> 직접 다룰 수 있게 된다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "Phase 0에서 손으로 하던 검색을 왜 벡터 DB로 바꾸나?"
- "Client · Collection · Document · id · metadata · 임베딩 함수가 각각 뭔가?"
- "영속(Persistent) 모드가 뭐고, 껐다 켜도 데이터가 남는 이유는?"
- "임베딩 함수를 컬렉션에 붙이면 add/query 때 무슨 일이 자동으로 일어나나?" ← **핵심**
- "add / get / update / delete 를 각각 언제 쓰나?"
- "query가 돌려주는 `distances`(거리)는 뭐고, 왜 낮을수록 가까운가?"
- "`get`(정확 id)과 `query`(의미 검색)는 뭐가 다른가?"

---

## 1. 복습: 왜 이제 벡터 DB가 필요한가

### Phase 0에서 우리가 했던 일

Phase 0의 의미 검색은 이런 순서였다.

1. 문서 6개를 **직접** `bge-m3`로 임베딩해 벡터로 만든다 (`embed()`를 손으로 호출).
2. 질문도 임베딩해 벡터로 만든다.
3. 질문 벡터와 문서 벡터 6개를 **하나씩 전부** 코사인 유사도로 비교한다.
4. 점수가 높은 순으로 정렬한다.

이게 **전수 비교(brute force)** 다. 문서가 6개일 땐 완벽하게 잘 돌아간다.

### 그런데 문서가 많아지면?

문제는 규모다.

- 문서 6개 → 검색 한 번에 6번 계산. 순식간이다.
- 문서 **100만 개** → 검색 한 번에 **100만 번** 계산. 매번 이러면 느려서 못 쓴다.

게다가 Phase 0 방식은 **프로그램을 끄면 벡터가 다 날아간다.** 리스트는 메모리에만 있으니까.
다시 실행할 때마다 100만 개를 처음부터 또 임베딩해야 한다. 현실에서 이건 불가능하다.

> 💡 그래서 필요한 게 **벡터 DB**다. 벡터 DB는 두 가지를 대신 해준다.
> ① 벡터를 **디스크에 저장**해두고(껐다 켜도 남는다),
> ② 전부 비교하지 않고도 가까운 것들을 **빠르게 찾아준다**(색인, Phase 3에서 자세히).
> 우리가 쓸 벡터 DB가 바로 **ChromaDB**다.

## 2. ChromaDB 구성요소

ChromaDB의 부품은 6개뿐이다. **도서관**에 비유해보자.

| 부품 | 정체 | 도서관 비유 | 우리 예제 값 (`main.py`) |
| --- | --- | --- | --- |
| **Client** | DB 전체에 접속하는 손잡이 | 도서관 **건물** (여기부터 들어간다) | `PersistentClient(path="./chroma_db")` |
| **Collection** | 문서들이 모여 사는 한 묶음 | 건물 안의 **책장 하나** ("FAQ 책장") | `name="faq"` |
| **Document** | 저장하는 실제 텍스트 한 덩어리 | 책장에 꽂힌 **책 한 권** | `"환불은 상품 수령 후 7일 이내에..."` |
| **id** | 문서마다 붙는 고유 이름표 | 책의 **청구기호**(딱 하나뿐, 중복 불가) | `"faq-1"` … `"faq-6"` |
| **metadata** | 문서에 딸린 부가정보(딕셔너리) | 책 표지의 **라벨**("분야: 환불") | `{"topic": "환불"}`, `{"topic": "배송"}` … |
| **Embedding function** | 텍스트를 벡터로 바꾸는 변환기 | 책 내용을 **좌표로 바꿔주는 사서** | `OllamaEmbeddingFunction(model_name="bge-m3")` |

핵심 관계는 이렇다.

```
Client (건물)
  └─ Collection "faq" (책장)
        ├─ Document "환불은 7일 이내..."   id=faq-1  metadata={topic:"환불"}
        ├─ Document "결제 후 2~3일..."      id=faq-2  metadata={topic:"배송"}
        └─ ...
     (이 책장에는 '임베딩 함수(사서)'가 한 명 배정돼 있다)
```

- **Client** 하나 안에 **Collection**이 여러 개 들어갈 수 있다(우리는 `faq` 하나만 쓴다).
- **Collection** 하나 안에 **Document**가 여러 개 들어간다.
- Document는 저마다 **id 하나**(중복 불가)와 **metadata 하나**(선택)를 가진다.
- 그리고 Collection에는 **임베딩 함수**가 붙는다 (4장에서 다룬다).

`main.py`에서 이 부품들이 그대로 등장한다.

```python
client = chromadb.PersistentClient(path="./chroma_db")            # Client (건물)
collection = client.get_or_create_collection(name="faq", ...)     # Collection (책장)
collection.add(
    ids=["faq-1", ...],                                            # id (청구기호)
    documents=["환불은 7일 이내...", ...],                          # Document (책)
    metadatas=[{"topic": "환불"}, ...],                            # metadata (라벨)
)
```

## 3. 영속(Persistent) 모드 vs 임시(in-memory) 모드

Client를 만드는 방법이 두 가지다. **어디에 저장하느냐**가 다르다.

| | 임시 모드 | 영속 모드 (우리가 쓰는 것) |
| --- | --- | --- |
| 코드 | `chromadb.Client()` | `chromadb.PersistentClient(path="./chroma_db")` |
| 저장 위치 | **메모리(RAM)** 에만 | **디스크(`./chroma_db` 폴더)** 에 |
| 프로그램 종료 후 | **싹 사라진다** | **그대로 남는다** |
| Phase 0의 리스트와 같은가? | 같다 (끄면 날아감) | 다르다 (파일로 살아남음) |

우리는 당연히 **영속 모드**를 쓴다.

```python
client = chromadb.PersistentClient(path="./chroma_db")
```

이 한 줄 덕분에, 넣은 문서들이 `./chroma_db` 폴더에 **파일로 저장**된다.
프로그램을 껐다가 `python main.py`를 다시 돌려도 데이터가 **그 자리에 남아있다.**

> 💡 `main.py`의 `[1]` 단계가 이걸 눈으로 보여준다. 실행하면 맨 먼저
> **"지난 실행에서 남아있던 문서 수"** 를 출력한다.
> - 처음 실행: `0 개` (아직 저장한 게 없다)
> - 두 번째 실행: `0보다 큰 수` ← **저번 데이터가 디스크에 살아남았다는 증거다.**
>
> 이게 Phase 0 리스트와의 차이다. 리스트는 매번 0에서 시작했지만, 벡터 DB는 기억한다.

## 4. 임베딩 함수 연결

### Phase 0에서는 손으로 임베딩했다

Phase 0에선 검색할 때마다 우리가 직접 `embed()`를 불러서 텍스트를 벡터로 바꿨다.
문서를 넣을 때도, 질문을 검색할 때도, **매번 손으로** 임베딩 함수를 호출해야 했다.

### Chroma는 그걸 자동으로 해준다

ChromaDB에서는 **컬렉션에 임베딩 함수를 한 번 붙여두면**, 그다음부터는
`add`나 `query`를 할 때 Chroma가 **알아서** 그 함수를 불러 임베딩을 만든다.
우리는 **텍스트만 건네면 되고, 벡터 변환은 신경 쓸 필요가 없다.**

```python
# ① 임베딩 함수(사서)를 만든다 — "bge-m3 모델로 임베딩하라"
ollama_ef = embedding_functions.OllamaEmbeddingFunction(
    url="http://localhost:11434",
    model_name="bge-m3",
)

# ② 컬렉션을 만들 때 그 함수를 붙인다
collection = client.get_or_create_collection(
    name="faq",
    embedding_function=ollama_ef,     # ← 여기! 이 책장 전담 사서로 배정
    metadata={"hnsw:space": "cosine"},
)
```

이렇게 붙여두면, 이제부터 이런 일이 **자동으로** 벌어진다.

```
collection.add(documents=["환불은 7일 이내..."])
        │
        └─(Chroma가 자동으로)─▶ ollama_ef 호출 ─▶ bge-m3 ─▶ 벡터 [0.02, -0.14, ...] ─▶ 디스크에 저장
```

```
collection.query(query_texts=["환불 언제 돼요?"])
        │
        └─(Chroma가 자동으로)─▶ ollama_ef 호출 ─▶ bge-m3 ─▶ 질문 벡터 ─▶ 가까운 문서 검색
```

> ⭐ **핵심 한 줄:** Phase 0에서 손으로 `embed()`를 부르던 일을, 이제는
> **컬렉션에 붙여둔 임베딩 함수가 add/query 때마다 대신 불러준다.**
> 우리 코드에는 벡터가 아예 등장하지 않는다 — 텍스트만 넣고 텍스트로 검색한다.

> 🔧 왜 하필 `OllamaEmbeddingFunction` + `bge-m3`인가? Phase 0의 교훈 그대로다.
> Ollama는 모델을 **로컬에서 돌리는 실행기**이고, `bge-m3`는 **다국어 임베딩 모델**이다.
> 한국어 FAQ를 다루니 다국어 모델이 필수다(영어 모델 `nomic`으로 한국어를 검색했다가
> 정답을 꼴찌로 내놓았던 그 교훈). 컬렉션에 이 함수를 붙였으니, 저장·검색 모두 `bge-m3`로 일관되게 처리된다.

## 5. 문서 CRUD — add / get / update / delete

CRUD는 **C**reate(생성)·**R**ead(조회)·**U**pdate(수정)·**D**elete(삭제)의 앞글자다.
데이터를 다루는 기본 4동작이고, ChromaDB에서는 이렇게 대응한다.

| 동작 | 메서드 | 하는 일 |
| --- | --- | --- |
| Create | `collection.add(...)` | 새 문서 저장 (자동 임베딩) |
| Read | `collection.get(ids=[...])` | **id로 정확히** 꺼내기 |
| Update | `collection.update(...)` | 기존 문서 내용 교체 (자동 재임베딩) |
| Delete | `collection.delete(ids=[...])` | 문서 삭제 |

### add — 생성

id, documents, metadatas를 **길이가 같은 리스트**로 나란히 넘긴다. 같은 순서로 짝지어진다.

```python
collection.add(
    ids=["faq-1", "faq-2", ...],
    documents=["환불은 7일 이내...", "결제 후 2~3일...", ...],
    metadatas=[{"topic": "환불"}, {"topic": "배송"}, ...],
)
```

임베딩은? **우리가 안 한다.** 4장에서 붙인 함수가 자동으로 각 문서를 벡터로 바꿔 저장한다.

> ⚠️ **이미 있는 id로 다시 `add`하면 어떻게 될까?** 흔한 오해와 달리 **에러가 나지는 않는다.**
> Chroma는 `Add of existing embedding ID: faq-1` 같은 **경고만 로그로 남기고 그 문서를 조용히 무시한다**
> — 프로그램이 죽지도 않고, 기존 내용이 덮어써지지도 않는다.
> 그래서 **내용을 갈아끼우려면 `add`가 아니라 `update`(또는 `upsert`)를 써야 한다.**
>
> 이 성질 때문에 `main.py`는 `[1]`에서 컬렉션을 **통째로 지웠다가 새로 만든다**
> (`client.delete_collection(name="faq")` 후 다시 `get_or_create_collection`). **에러를 피하려는 게 아니라**,
> 지난 실행에서 남은 문서나 경고 없이 **매번 깨끗한 상태에서 데모를 보여주기 위해서**다.

### get — 조회 (정확한 id로)

```python
result = collection.get(ids=["faq-2"])
print(result["documents"][0])    # 그 문서의 텍스트
print(result["metadatas"][0])    # 그 문서의 메타데이터
```

`get`은 **"청구기호로 정확히 그 책을 꺼내는 것"** 이다. 뜻이 비슷한 걸 찾는 게 아니라,
**정확히 그 id의 문서**를 돌려준다. (반환은 `{"ids":[...], "documents":[...], "metadatas":[...]}`.)

### update — 수정

```python
collection.update(ids=["faq-5"], documents=["...새 내용..."])
```

id로 대상을 찾아 내용을 갈아끼운다. **내용이 바뀌면 벡터도 자동으로 다시 계산**돼 저장된다
(임베딩 함수가 또 일한다). 그래서 수정 후에는 검색 결과도 새 내용 기준으로 바뀐다.

### delete — 삭제

```python
collection.delete(ids=["faq-4"])
```

id로 문서를 지운다. 지운 만큼 `collection.count()`(총 문서 수)가 줄어든다.

## 6. query = 의미 검색

CRUD의 R에는 사실 두 종류가 있다. 방금 본 `get`(정확 id)과, 지금 볼 `query`(의미 검색)다.
**query가 Phase 0에서 손으로 하던 전수 비교를 대신한다.**

### 쓰는 법

```python
result = collection.query(query_texts=["환불은 언제 돼요?"], n_results=3)
```

질문을 텍스트로 던지면, Chroma가 질문을 자동 임베딩해서 **가장 뜻이 가까운 문서 `n_results`개**를
가까운 순으로 돌려준다.

### 반환 구조 — 리스트가 한 겹 더 감싸져 있다

이 부분이 처음에 헷갈린다. `query`는 **질문 여러 개를 한꺼번에** 받을 수 있게 설계돼서,
결과가 **질문별로 한 겹 더 감싸진 리스트**로 온다.

```python
result["ids"]        # [["faq-1", "faq-2", "faq-5"]]   ← 바깥 리스트 = 질문 목록
result["documents"]  # [["환불은...", "결제 후...", "..."]]
result["distances"]  # [[0.21, 0.44, 0.58]]
result["metadatas"]  # [[{"topic":"환불"}, {"topic":"배송"}, ...]]
```

우리는 질문이 하나뿐이니 **맨 앞 `[0]`을 벗겨** 쓴다. `main.py`가 이렇게 한다.

```python
ids       = result["ids"][0]
documents = result["documents"][0]
distances = result["distances"][0]
metadatas = result["metadatas"][0]
```

> 💡 `get`은 한 겹(`result["documents"][0]` = 그 문서 텍스트), `query`는 두 겹(`result["documents"][0]`
> = 첫 질문의 결과 리스트). **`get`은 안 감싸고, `query`는 질문별로 한 겹 감싼다**는 것만 기억하자.

### distances = 코사인 거리 (낮을수록 가깝다)

query 결과에는 유사도 대신 **`distances`(거리)** 가 온다. **거리는 낮을수록 가깝다** — 방향이 반대다.

우리는 컬렉션을 만들 때 `metadata={"hnsw:space": "cosine"}` 를 줬으므로, 이 거리는 **코사인 거리**다.

> **코사인 거리 = 1 − 코사인 유사도**

Phase 0의 유사도와 이렇게 연결된다.

| Phase 0 (코사인 유사도) | Phase 1 (코사인 거리) | 뜻 |
| --- | --- | --- |
| 1.00 (완전히 같은 방향) | 0.00 | 가장 가깝다 |
| **0.75** | **0.25** | 꽤 가깝다 |
| 0.50 | 0.50 | 중간 |
| 0.00 (직각, 무관) | 1.00 | 멀다 |

즉 **Phase 0에서 코사인 유사도 0.75였던 게 여기선 거리 0.25**로 나온다. 같은 이야기를 뒤집어 말할 뿐이다.
"유사도는 높을수록, 거리는 낮을수록 가깝다."

> 🔧 **왜 굳이 cosine으로 설정했나?** ChromaDB의 기본 거리 함수는 사실 **L2(유클리드)** 다.
> 하지만 Phase 0에서 "텍스트 의미 검색은 코사인이 기본"이라고 배웠으니, 그 연속성을 지키려고
> `metadata={"hnsw:space": "cosine"}` 로 **명시적으로 코사인을 선택**했다.
> 이 한 줄을 빼먹으면 거리 숫자의 스케일이 달라진다(L2 거리로 나온다).

### get vs query — 한눈에

| | `get` | `query` |
| --- | --- | --- |
| 찾는 기준 | **정확한 id** | **의미(뜻)의 가까움** |
| 질문 형태 | "faq-2를 다오" | "환불 언제 돼요?" |
| 임베딩 하나? | 안 함(그냥 id 매칭) | 함(질문을 벡터로) |
| 결과 | 그 id의 문서 | 가까운 순 top-k + 거리 |
| 도서관 비유 | 청구기호로 책 찾기 | 사서에게 "이런 내용 책 있어요?" 묻기 |

## 8. `main.py`가 보여주는 것 — [1]~[7] 지도

스크립트는 먼저 **Ollama 서버와 `bge-m3` 모델이 준비됐는지 점검**(`check_ollama`)한 뒤,
아래 7단계를 차례로 눈앞에서 재현한다. 각 단계가 위 개념 어디에 대응하는지 정리하면 이렇다.

| 단계 | 화면 제목 | 하는 일 | 대응 개념 |
| --- | --- | --- | --- |
| **[1]** | 준비 & 영속성 확인 | `get_or_create_collection`으로 `faq` 컬렉션 확보 → **지난 실행에 남은 문서 수** 출력 → 데모를 위해 `delete_collection` 후 재생성(초기화) | §3 영속 모드, §2 컬렉션 |
| **[2]** | 생성 (add) | FAQ 문서 6개를 `add` (자동 임베딩). `count()`로 저장 확인 | §5 add, §4 자동 임베딩 |
| **[3]** | 조회 (get) | `get(ids=["faq-2"])`로 그 문서와 메타데이터를 정확히 꺼냄 | §5 get, §6 get vs query |
| **[4]** | 의미 검색 (query) | "환불은 언제 돼요?"를 `query`로 검색 → 가까운 3개를 **거리·topic·문서**와 함께 순위 출력 | §6 query, distances |
| **[5]** | 수정 (update) | `update(ids=["faq-5"])`로 영업시간 문서를 새 내용으로 교체 → 다시 `get`으로 확인 | §5 update, 자동 재임베딩 |
| **[6]** | 삭제 (delete) | `delete(ids=["faq-4"])`로 노트북 문서 삭제 → 전후 `count()` 비교 | §5 delete |
| **[7]** | 마무리 안내 | 데이터가 `./chroma_db`에 남았고, 다시 실행하면 `[1]`에서 보인다고 안내 | §3 영속성 |

### [4] 의미 검색 출력, 이렇게 읽는다

`[4]`가 이 스크립트의 하이라이트다. 질문 하나로 top-3을 뽑아 이런 식으로 출력한다.

```
질문: 환불은 언제 돼요?
    1위 | 거리 0.21xx | topic=환불
         환불은 상품 수령 후 7일 이내에 신청하실 수 있으며, ...
    2위 | 거리 0.44xx | topic=배송
         주문하신 상품은 결제 완료 후 보통 2~3일 이내에 배송됩니다.
    3위 | ...
```

- **거리가 낮은 순 = 뜻이 가까운 순**으로 정렬돼 있다.
- 질문 "환불은 **언제** 돼요?"와 1위 문서에 **겹치는 단어가 거의 없는데도** 1위로 잡힌다.
  이게 키워드 검색은 못 하고 **의미 검색만 할 수 있는 일**이다(Phase 0에서 배운 그 감각).
- **1위가 환불 문서면 성공.** Phase 0에서 손으로 전수 비교하던 걸, 이제 Chroma가 대신 했다.

> ⚙️ **동작 원리 한 줄:** `[4]`에서 우리 코드는 질문 텍스트만 넘겼다. Chroma가 그걸 `bge-m3`로
> 임베딩하고, 저장된 문서 벡터들과 **코사인 거리**로 비교해 가까운 순으로 돌려줬다.
> Phase 0의 4단계(임베딩 → 비교 → 정렬)가 `query()` 한 줄 안에 통째로 들어간 셈이다.

## 9. Phase 1 완료 체크리스트

- [ ] Phase 0의 리스트 전수 비교 대비, 벡터 DB가 필요한 이유(규모·영속성)를 설명할 수 있다.
- [ ] Client · Collection · Document · id · metadata · 임베딩 함수를 각각 내 말로 설명할 수 있다.
- [ ] 영속(Persistent) 모드가 왜 껐다 켜도 데이터를 유지하는지 안다. (`[1]`의 "남은 문서 수"로 확인했다.)
- [ ] **컬렉션에 임베딩 함수를 붙이면 add/query 때 Chroma가 자동으로 임베딩한다**는 걸 설명할 수 있다.
- [ ] add / get / update / delete 를 각각 언제 쓰는지 안다. (같은 id로 `add`하면 에러가 아니라 **경고 후 무시**이고, 덮어쓰려면 `update`/`upsert`를 써야 한다는 것도.)
- [ ] `query`의 `distances`가 **코사인 거리(1 − 코사인유사도, 낮을수록 가까움)** 임을 안다. (거리 0.25 ≈ 유사도 0.75.)
- [ ] `get`(정확 id)과 `query`(의미 검색)의 차이를 설명할 수 있다.
- [ ] `python main.py`를 돌려 `[1]`~`[7]`을 확인했고, **한 번 더 실행해 `[1]`의 문서 수가 남는 것(영속성)** 도 봤다.

전부 체크됐다면 **Phase 2 (유사도 검색 & 첫 미니 데모)** 로 넘어갈 준비가 된 것이다.
Phase 1에서 다룬 `query`의 거리 점수를 "이게 좋은 점수인가?"까지 해석하고, 문서를 잘게 나누는
**청킹(chunking)** 으로 검색 품질을 끌어올리는 단계다.
