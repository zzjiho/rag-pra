# Phase 3 — 검색 품질: 필터 & 하이브리드

> Phase 2의 검색기 `search()`는 질문을 임베딩해서 **"가장 가까운 것"** 을 돌려줬다.
> 거리로 관련/무관을 판정하는 것까지 했다. 그런데 실무에서 검색기를 쓰다 보면 "가장 가까운 것"만으로
> 안 되는 두 상황이 나온다.
> ① **특정 조건으로 먼저 좁히고 싶을 때** — "환불 얘기만", "이 카테고리 안에서만" → **필터**.
> ② **정확한 단어가 중요한데 벡터가 그걸 놓칠 때** — 오류 코드 `E-402`, 상품 SKU, 사람 이름 → **하이브리드**.
> 이 둘을 붙이면 검색기 v2가 된다. 그게 Phase 3의 결과물이다.

**이 장을 마치면 이런 문장을 스스로 설명할 수 있다.**
- "`where`와 `where_document`는 뭐가 다른가? 각각 무엇을 매칭하나?"
- "필터는 검색 '전에' 거는 건가, '후에' 거는 건가?"
- "metadata에 어떤 걸 필드로 빼두고, 어떤 걸 본문에 남겨야 하나?"
- "벡터 검색은 왜 `E-402`를 물었는데 엉뚱한 코드를 1위로 주나?"
- "키워드 검색만 쓰면 뭐가 부족한가?"
- "RRF는 왜 점수가 아니라 **순위**를 더하나? 왜 `1/(60+순위)` 같은 이상한 식을 쓰나?"

## 1. 복습, 그리고 이번에 붙이는 두 도구

Phase 2까지의 검색기는 이런 모양이었다.

```python
result = collection.query(query_texts=["환불 언제 돼요?"], n_results=3)
# -> 질문과 가장 가까운 문서 3개 (거리 낮은 순)
```

질문을 벡터로 바꿔 **의미가 가까운 문서**를 준다. 이게 벡터 검색의 강점이다 — "환불"이라고 안 쓰고
"돈 언제 돌려받아요"라고 물어도 환불 문단을 찾아준다. 뜻으로 검색하니까.

그런데 두 가지 상황에서 이것만으로는 부족하다.

- **상황 ①** — 질문이 "신청 방법 알려줘"처럼 **여러 주제에 다 걸리는** 경우. 환불 신청, 교환 신청,
  멤버십 신청이 다 튀어나온다. "나는 **환불** 얘기만 보고 싶은데" → 주제를 미리 못 좁힌다.
- **상황 ②** — 질문에 **정확한 토큰**이 들어있는 경우. "`E-402` 문제가 발생했어요"라고 물으면,
  벡터는 `E-401`·`E-402`·`E-403`·`E-404`가 다 비슷하게 생겨서 못 가린다. 실제로 이 환경에서
  `E-402`를 물으면 정답이 꼴찌로 밀리고 엉뚱한 코드가 1위로 나온다(§4에서 직접 본다).

이 장은 이 둘을 각각 다른 도구로 푼다.

| 상황 | 도구 | 하는 일 |
| --- | --- | --- |
| ① 특정 조건으로 좁히고 싶다 | **필터** (`where` / `where_document`) | 후보를 먼저 잘라내고, 그 안에서만 의미 검색 |
| ② 정확한 단어를 벡터가 놓친다 | **하이브리드** (벡터 + 키워드) | 두 검색의 순위를 RRF로 합쳐 서로 보완 |

`main.py`는 한 컬렉션(`policy_and_errors`)에 **정책 FAQ 문단 5개**와 **오류 코드 문서 4개**를 같이
담아두고, 이 도구들을 차례로 보여준다.

## 2. 메타데이터 필터 `where` — 구조화된 필드로 좁히기

### 필터는 검색 '전에' 후보를 잘라낸다

의미 검색은 질문과 가까운 걸 찾아준다. 그런데 "가깝다"의 후보가 **처음부터 너무 넓으면** 잡음이 섞인다.
필터는 의미 검색을 하기 **전에** 후보 집합을 먼저 좁힌다. "이 조건에 안 맞는 문서는 아예 후보에서 빼고,
남은 것들 안에서만 가까운 걸 찾아라." 순서가 중요하다 — **먼저 거르고, 그 다음 의미 검색**이다.

`main.py`가 저장할 때 각 문서에 metadata를 붙여 뒀다. FAQ 문단에는 `topic`(환불/교환/배송/멤버십),
오류 문서에는 `topic="오류"`와 `code`(E-40X). 이 `topic`이 필터의 손잡이다.

### 같은 질문, 필터 유무 비교 — [2]에서 하는 일

질문은 **"신청 방법 알려줘"**. 여러 주제에 걸리는 애매한 질문이다.

**(가) 필터 없이** `n_results=3`:

```
1위 | topic=교환    교환 신청은 상품에 하자가 있거나 ...
2위 | topic=멤버십  멤버십 가입 신청은 앱 설정 메뉴에서 ...
3위 | topic=환불    환불을 원하시면 마이페이지 주문 내역에서 ...
```

"신청"이 들어간 문단들이 주제 구분 없이 섞여 나온다.

**(나) `where={"topic": "환불"}`** 로 좁히면:

```
1위 | topic=환불  환불을 원하시면 마이페이지 주문 내역에서 ...
2위 | topic=환불  환불은 상품을 받으신 후 7일 이내에 ...
```

`topic=환불` 문서만 남는다. 교환·멤버십은 **후보에서 아예 빠진다**(2개밖에 없어서 `n_results=3`을
요청해도 2개만 나온다). 주제가 분명할 때 잡음을 크게 줄인다.

```python
collection.query(query_texts=["신청 방법 알려줘"], n_results=3, where={"topic": "환불"})
```

`where`는 단순 일치 말고 연산자도 받는다(아래는 `main.py`에는 안 나오는 일반 ChromaDB 참고용이다). 자주 쓰는 것만:

```python
where={"topic": {"$in": ["환불", "교환"]}}   # 여러 값 중 하나
where={"code": {"$ne": "NONE"}}              # 오류 문서만 (code가 NONE이 아닌 것)
```

(`$eq $ne $in $nin $gt $gte $lt $lte`, 그리고 `$and $or`로 조건을 묶을 수 있다.)

### metadata 설계 감각

필터는 **미리 빼둔 필드가 있어야** 쓸 수 있다. 그래서 문서를 적재할 때 "나중에 무엇으로 좁힐까"를
생각해 필드를 정해야 한다. 기준은 단순하다.

- **좁힘의 축이 될 만한 것은 필드로 뺀다.** 카테고리, 날짜, 작성자, 상태, 언어, 문서 종류 —
  "이 값으로 걸러서 검색할 일이 있겠다" 싶으면 metadata 필드로 저장한다. `main.py`에서 `topic`과
  `code`가 그렇다.
- **본문은 본문대로 둔다.** 검색해서 사람이 읽을 실제 내용은 `document`에 그대로 넣는다. 필터용으로
  쪼개는 게 아니다.
- **필드 값은 예측 가능하게.** `"환불"`처럼 값의 종류가 정해져 있어야 `where`로 정확히 맞출 수 있다.
  자유 서술("고객이 환불을 원함")은 필터에 안 맞는다. 그건 본문의 몫이다.

> 💡 metadata를 안 빼두면 나중에 필터를 걸 수 없다. 그렇다고 아무 필드나 잔뜩 넣으면 관리가 어렵다.
> "이 값으로 검색을 좁힐 일이 실제로 있나?"를 기준으로 고른다.

## 3. `where_document` 키워드 필터 — 본문 부분문자열 매칭

### where와 where_document는 매칭 대상이 다르다

둘 다 "검색 전에 후보를 좁히는 필터"라는 점은 같다. 다른 건 **무엇을 보고 거르느냐**다.

- **`where`** — 우리가 저장해 둔 **metadata 필드**를 본다. `{"code": "E-402"}`는 `code` 필드가
  정확히 `"E-402"`인 문서를 남긴다.
- **`where_document`** — 문서 **본문(document) 그 자체**를 본다. `{"$contains": "E-402"}`는
  본문 문자열 안에 `"E-402"`가 부분문자열로 들어있는 문서를 남긴다.

### 같은 결과, 다른 경로 — [3]에서 하는 일

질문은 **"오류 해결 방법"**. `main.py`는 같은 `E-402` 문서를 두 가지 필터로 각각 집어낸다.

**(가) `where_document={"$contains": "E-402"}`** — 본문에 `E-402`가 있는 문서만:

```python
collection.query(query_texts=["오류 해결 방법"], n_results=5,
                 where_document={"$contains": "E-402"})
# -> 오류 코드 E-402: 결제가 거절되었습니다. ... (본문에 'E-402'가 박혀 있어서 걸림)
```

**(나) `where={"code": "E-402"}`** — metadata 필드가 `E-402`인 문서만:

```python
collection.query(query_texts=["오류 해결 방법"], n_results=5,
                 where={"code": "E-402"})
# -> 같은 E-402 문서
```

결과는 같은 문서 하나다. 하지만 **걸러낸 방식이 다르다.**

- (나)는 우리가 `code="E-402"`라는 필드를 **미리 저장해 뒀기 때문에** 가능하다. 필드가 없었으면 못 쓴다.
- (가)는 그런 필드가 **없어도** 된다. 본문에 `E-402`라는 글자가 들어있기만 하면 잡는다.

이게 `where_document`의 쓸모다. metadata를 미리 못 빼뒀어도, **본문 안의 정확한 토큰**(코드, 제품명,
전화번호 등)으로 걸러낼 수 있다. 부분문자열 매칭이라 한국어·영문·코드 다 된다.

> 참고: `where`와 `where_document`는 **동시에** 걸 수 있다. `where={"topic": "오류"}` +
> `where_document={"$contains": "결제"}` 처럼. metadata로 한 번, 본문으로 한 번, 두 겹으로 좁힌다.

여기까지가 **필터**다. 조건이 분명할 때 후보를 정확히 좁히는 도구. 이제 조건이 아니라 **랭킹 품질**
자체가 문제인 경우로 넘어간다.

## 4. 하이브리드가 필요한 이유 — 벡터의 약점

필터는 "무엇으로 좁힐지" 조건이 있을 때 쓴다. 그런데 조건 없이 그냥 검색하는데도 **벡터가 엉뚱한 걸
1위로 주는** 경우가 있다. [4]가 그걸 보여준다.

질문은 **"E-402 문제가 발생했어요"**. 필터 없이 순수 벡터 검색만 돌린 결과다(거리는 낮을수록 가깝다).

```
1위 | 거리 0.3510 | code=E-403   오류 코드 E-403: 접근 권한이 없습니다. ...
2위 | 거리 0.3592 | code=E-404   오류 코드 E-404: 요청하신 페이지를 찾을 수 없습니다. ...
3위 | 거리 0.3675 | code=E-401   오류 코드 E-401: 로그인 인증이 만료되었습니다. ...
4위 | 거리 0.3757 | code=E-402   오류 코드 E-402: 결제가 거절되었습니다. ...
```

**1위가 정답 `E-402`가 아니다 — 오히려 꼴찌(4위)로 밀렸다.** 게다가 네 문서의 거리가
`0.35~0.38`로 다닥다닥 붙어 있다.

왜 이럴까. 임베딩은 문장을 **의미**로 벡터화한다. 그런데 이 네 문서는 "오류 코드 E-40X: ...설명..."으로
꼴이 거의 같고, `E-401`·`E-402`·`E-403`·`E-404`는 모델이 보기에 **거의 같은 토큰**이다. 숫자 한 자리
차이를 의미로 구분하지 못한다. 그래서 넷이 한 덩어리로 뭉쳐 거리가 붙고, 그 안에서 1위는 사실상 운이다.

> 벡터(의미) 검색이 약한 지점: **코드, SKU, 사람 이름, 전화번호처럼 "정확한 토큰이 곧 정답"인 것.**
> 의미로는 다 비슷해 보여서 정확히 못 가른다. 반대로 벡터가 강한 지점은 동의어·문맥이다 —
> "돈 돌려받기"로 "환불"을 찾는 건 벡터가 잘한다.

그럼 키워드 검색으로 바꾸면 되지 않나? 본문에 `E-402`가 있는 문서만 정확히 집으면 된다(§3에서 봤다).
맞다. 하지만 **키워드만 쓰면 반대쪽이 약해진다.**

> 키워드(정확 일치) 검색이 약한 지점: **동의어와 문맥.** 사용자가 `E-402`라는 코드를 모르고
> "결제가 자꾸 막혀요"라고만 물으면, 본문의 "결제가 거절되었습니다"와 글자가 안 겹쳐서 못 찾는다.
> 뜻은 같은데 단어가 달라서 놓친다.

정리하면 **벡터는 뜻에 강하고 정확 토큰에 약하다. 키워드는 그 반대다.** 그래서 둘 중 하나만 고르는 게
아니라 **둘을 합친다.** 그게 하이브리드다.

## 5. 하이브리드 구현 — 벡터 순위 + 키워드 순위를 RRF로 결합

### 문제: 벡터 점수와 키워드 점수는 단위가 다르다

두 검색을 합치려면 점수를 더해야 할 것 같다. 그런데 못 더한다. 벡터는 **거리 0.3510** 같은 값을 주고,
키워드는 **겹친 단어 1개** 같은 값을 준다. 스케일도 방향도 다르다(거리는 낮을수록 좋고, 단어 수는
높을수록 좋다). `0.3510`과 `1`을 그냥 더하는 건 의미가 없다.

그래서 **점수 대신 순위를 쓴다.** 각 검색이 "1위, 2위, 3위…"를 매기게 하고, **순위를 합친다.**
순위는 두 검색의 **공통 화폐**다. 이 방식이 RRF(Reciprocal Rank Fusion, 역순위 결합)다.

### RRF 식과 직관

각 문서의 최종점수는 이렇게 매긴다.

```
최종점수 = 1/(60 + 벡터순위) + 1/(60 + 키워드순위)
```

한쪽 검색에만 나온 문서는 그쪽 항만 더한다. 직관은 두 가지다.

- **역수를 쓰는 이유** — 순위가 높을수록(1위에 가까울수록) 값이 커진다. 1위면 `1/61`, 4위면 `1/64`.
  **두 검색 모두에서 위에 있는 문서**가 양쪽 항이 다 커서 총합이 높아진다. 한 검색에서만 1등이고
  다른 검색에선 바닥이면 총합이 눌린다.
- **왜 `+60`인가** — 그냥 `1/순위`로 하면 1위(`1.0`)와 2위(`0.5`)의 차가 너무 커서, 한 검색의 1위
  항 하나가 결과를 좌우하기 쉽다. `60`을 더하면 `1/61` vs `1/62`로 간격이 촘촘해져, **"한 곳에서
  압도적 1등"보다 "양쪽에서 두루 상위"가 이기게** 기운다. `60`은 관례로 쓰는 값이고, 키우면 순위 간
  차이를 더 뭉갠다.
  (`+60`은 특정 예제를 뒤집는 장치가 아니라, 순위 간 격차를 눌러 "여러 검색에서 두루 상위인 문서"가
  이기기 쉽게 만드는 일반적 장치다.)

한 가지 더 — `+60`을 깔고 역수를 취하니 최종점수의 절대값은 늘 작다(`0.01`~`0.03` 언저리). 이건 정상이다.
RRF에서 중요한 건 점수의 크기가 아니라 문서들 사이의 상대적 대소(누가 더 큰가)뿐이다. `0.03202`가
절대적으로 "좋은 점수"라서가 아니라, 다른 문서보다 크다는 사실만 의미가 있다.

### 실제로 E-402가 어떻게 1위로 올라오나 — [5]에서 하는 일

같은 질문 **"E-402 문제가 발생했어요"** 를 `hybrid_search`에 넣은 결과다.

```
1위 | 최종점수 0.03202 | 벡터순위=4 키워드순위=1    | code=E-402
2위 | 최종점수 0.01639 | 벡터순위=1 키워드순위=None | code=E-403
3위 | 최종점수 0.01613 | 벡터순위=2 키워드순위=None | code=E-404
4위 | 최종점수 0.01587 | 벡터순위=3 키워드순위=None | code=E-401
```

계산을 펼치면 이렇다.

| 문서 | 벡터순위 | 키워드순위 | 1/(60+벡터) | 1/(60+키워드) | 최종점수 |
| --- | --- | --- | --- | --- | --- |
| **E-402** | 4 | **1** | 0.01563 | 0.01639 | **0.03202** |
| E-403 | **1** | 없음 | 0.01639 | — | 0.01639 |
| E-404 | 2 | 없음 | 0.01613 | — | 0.01613 |
| E-401 | 3 | 없음 | 0.01587 | — | 0.01587 |

이 표의 핵심은 **키워드 후보가 E-402 하나뿐**이라는 것이다. 본문에 `E-402`가 들어간 문서는 오직
E-402뿐이고, 질문의 나머지 단어(`문제가`, `발생했어요`)는 어느 문서에도 안 겹친다. 그래서 **E-402만
키워드 1위를 받고, 나머지 셋은 키워드 항이 아예 없어 벡터 항만 남는다.**

- **E-402**는 벡터에선 꼴찌(4위)였지만 **키워드에선 유일한 1위**다. 그 키워드 항(`1/61 ≈ 0.01639`)이
  통째로 얹혀 최종점수가 `0.03202`로 뛴다. 다른 문서엔 이 보너스가 없다.
- **E-403**은 벡터 1위(`1/61 ≈ 0.01639`)지만 키워드 항이 없어 그대로 `0.01639`에 머문다. E-402의 절반
  수준이다.

**§4에서 꼴찌였던 정답이 단숨에 1위로 올라왔다.** 벡터의 약점(정확 토큰)을 키워드가 메우고, RRF가
"양쪽 신호를 다 받은" E-402를 위로 올린 결과다. 이번엔 E-402가 유일한 키워드 후보라, 누가 키워드 2·3위인지
같은 동점 문제도 아예 생기지 않아 순위가 흔들릴 여지가 없다.

### 키워드 순위는 어떻게 매기나

`hybrid_search`의 키워드 쪽은 단순하다. 질문을 공백으로 쪼개(`"E-402 문제가 발생했어요"` →
`["E-402", "문제가", "발생했어요"]`) 각 단어가 문서 본문에 **부분문자열로 들어있는지** 세고,
많이 겹치는 순으로 순위를 매긴다. 한 단어도 안 겹치는 문서(여기선 FAQ 문단 5개와 나머지 오류 문서 3개)는 키워드 후보에서 뺀다.

이건 §3의 `where_document {"$contains": ...}`와 **같은 원리(본문 부분문자열 매칭)**다. 다만 §3에서는
조건에 맞는 문서만 남기는 **필터**로 썼고, 여기서는 걸러내는 게 아니라 **몇 위인지 순위**가 필요해서
`where_document`를 다시 부르지 않고 겹친 단어 수를 직접 세는 방식으로 바꿨을 뿐이다.

이 질문에서 본문에 `E-402`가 있는 문서는 하나뿐이라, `E-402`만 키워드 점수 1점으로 유일한 후보가
된다. `문제가`·`발생했어요`는 어느 문서 본문과도 안 겹친다 — 결정적이었던 건 정확한 코드 토큰
`E-402`다.

> 🔧 이 키워드 스코어는 개념을 드러내려고 **단어 포함 개수**로 단순화한 것이다. 실무에선 BM25처럼
> 단어 빈도·희소성까지 반영하는 정식 키워드 스코어를 쓴다. 결합 틀(RRF)은 그대로고, 키워드 순위를
> 매기는 부분만 더 정교해질 뿐이다.

### 코드 흐름 한눈에

`hybrid_search(collection, query, k)`는 세 덩어리다.

```python
# (a) 벡터 순위: 벡터 검색 상위 k개에 1~k위를 매긴다
# (b) 키워드 순위: 전체 문서에서 query 단어가 겹친 개수로 순위를 매긴다 (0점은 제외)
# (c) RRF 결합: 두 순위를 1/(60+순위)로 더해 최종점수 높은 순으로 정렬
```

두 검색을 각각 돌려 순위를 얻고(a, b), 그 순위를 합쳐(c) 다시 줄 세운다. 이 함수가 검색기 v2의 알맹이다.

## 6. HNSW 한 줄 복습

컬렉션을 만들 때 `metadata={"hnsw:space": "cosine"}`를 줬다. **HNSW**는 ChromaDB가 벡터를
저장하는 색인 구조 이름이고, 이게 있어서 "질문 벡터와 가까운 이웃"을 전체를 다 훑지 않고 **빠르게**
찾는다. `hnsw:space`는 그 색인이 "가깝다"를 잴 때 쓰는 거리(여기선 코사인)를 정한다.

지금은 "색인이 빠른 근접이웃 검색을 가능케 한다"까지만 알면 된다. 색인 파라미터(`M`,
`ef_construction` 등)를 만져 속도·정확도를 조율하는 상세 튜닝은 **Phase 5**에서 다룬다.

## 7. 설치 & 실행

### 1) 가상환경 & 패키지 설치

이 폴더(`phase-3-filter-hybrid`)에서:

```bash
python3 -m venv .venv
source .venv/bin/activate        # 새 터미널을 열 때마다 이 줄로 활성화
pip install -r requirements.txt  # chromadb, ollama 설치
```

Ollama와 `bge-m3` 모델은 Phase 0에서 준비했다. 안 돼 있다면 `brew services start ollama`로 서버를
켜고 `ollama pull bge-m3`로 모델을 받으면 된다. `main.py`가 실행 첫머리(`check_ollama`)에서 이 둘을
자동 점검하고, 빠졌으면 무엇을 하면 되는지 알려준다.

### 2) 실행

```bash
python main.py
```

### 3) 무슨 일이 일어나나

- 실행하면 이 폴더에 **`./chroma_db` 폴더가 생긴다**(벡터가 파일로 저장되는 자리).
- 스크립트는 매 실행마다 `policy_and_errors` 컬렉션을 **지웠다 새로 만든다**(`reset_collection`).
  지난 실행의 데이터 없이 항상 깨끗한 상태에서 [2]~[5]를 재현하기 위해서다.
- 거리·최종점수 값은 모델·환경에 따라 소수점 아래가 조금씩 달라질 수 있다. 하지만 **순위가 뒤집히는
  방향**(벡터에선 정답 E-402가 꼴찌, 하이브리드에선 E-402가 1위)은 그대로다. E-402가 **유일한 키워드
  후보**라 하이브리드 1위는 견고하게 유지된다(벡터 항만 있는 나머지 셋은 키워드 보너스가 없어 크게
  못 따라온다). 나머지 2·3·4위는 벡터순위만으로 갈려 환경에 따라 소폭 바뀔 수 있으나 중요치 않다.

## 8. `main.py`가 보여주는 것 — [1]~[5] 지도

스크립트는 먼저 **Ollama 서버와 `bge-m3` 모델을 점검**(`check_ollama`)한 뒤, 아래 5단계를 차례로
재현한다. 각 단계가 위 개념 어디에 대응하는지 정리하면 이렇다.

| 단계 | 화면 제목 | 하는 일 | 대응 절 |
| --- | --- | --- | --- |
| **[1]** | 준비 & 적재 | 한 컬렉션에 FAQ 문단 5개 + 오류 문서 4개를 metadata(`topic`, `code`)와 함께 넣음 | §1 |
| **[2]** | 메타데이터 필터 (`where`) | "신청 방법 알려줘"를 필터 없이 vs `where={"topic":"환불"}`로 비교 → 후보가 환불로 좁혀짐 | §2 |
| **[3]** | 키워드 필터 (`where_document`) | 같은 `E-402` 문서를 `where_document $contains`(본문)와 `where`(필드) 두 경로로 집어 비교 | §3 |
| **[4]** | 하이브리드가 필요한 이유 | "E-402 문제가…"를 순수 벡터로만 검색 → 정답 **E-402가 꼴찌(4위)**, 엉뚱한 E-403이 1위 | §4 |
| **[5]** | 하이브리드 검색 (검색기 v2) | 같은 질문을 `hybrid_search`로 → 벡터순위+키워드순위 RRF 결합 → **E-402가 1위로 교정** | §5 |

### [5] 출력, 이렇게 읽는다

```
1위 | 최종점수 0.03202 | 벡터순위=4 키워드순위=1    | code=E-402
2위 | 최종점수 0.01639 | 벡터순위=1 키워드순위=None | code=E-403
```

- 각 줄의 **벡터순위/키워드순위**가 그 문서가 두 검색에서 각각 몇 위였는지다. E-402는 (벡터 4위, 키워드
  1위), 나머지는 키워드 후보가 아니라 벡터순위만 있다.
- **최종점수**는 `1/(60+벡터순위) + 1/(60+키워드순위)`. E-402만 키워드 항이 더해져 총합에서 앞선다.
- [4]에서 벡터만으로는 밀렸던 E-402가 여기선 1위다. 이 뒤집힘이 [5]가 존재하는 이유다.

## 9. Phase 3 완료 체크리스트

- [ ] `where`(metadata 필드)와 `where_document`(본문 부분문자열)의 매칭 대상 차이를 설명할 수 있다.
- [ ] 필터가 검색 **전에** 후보를 좁히는 것(먼저 거르고, 그 안에서 의미 검색)임을 안다.
- [ ] metadata를 설계할 때 "무엇을 필드로 빼고 무엇을 본문에 둘지" 기준을 말할 수 있다.
- [ ] `where`의 연산자(`$in`, `$ne` 등)와 두 필터 동시 사용을 안다.
- [ ] 벡터 검색이 왜 `E-402`를 물어도 정답을 못 집는지(정확 토큰을 의미로 못 가림) 설명할 수 있다.
- [ ] 키워드 검색만 쓰면 왜 부족한지(동의어·문맥을 못 잡음) 설명할 수 있다.
- [ ] RRF가 점수가 아니라 **순위**를 더하는 이유(단위가 다른 두 검색의 공통 화폐)를 안다.
- [ ] `1/(60+순위)`에서 `+60`이 하는 일(순위 간격을 촘촘히 해 "양쪽에서 두루 상위"가 이기게)을 안다.
- [ ] [5]에서 E-402가 (벡터 꼴찌, 유일한 키워드 후보) 조합으로 어떻게 총합 1위가 되는지 표로 따라갈 수 있다.
- [ ] `hnsw:space`가 색인의 거리 척도를 정하는 것이고, 상세 튜닝은 Phase 5임을 안다.
- [ ] `python main.py`를 돌려 [1]~[5]를 확인했다.

전부 체크됐다면 검색기 v2가 완성된 것이고, **Phase 4(평가)** 로 넘어갈 준비가 된 것이다.
